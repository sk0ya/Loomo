# §35 構文木編集とマルチバッファ（ファイル単位の編集からの脱却）

> 状態: **§35.2（C# の構文木編集）は実装済み**（2026-10-08）。§35.3 以降は構想と前提工事の整理。
> 関連: §24.9（意味的な選択の拡大／縮小）、§24.3／§24.7（素材の流れ）、§27（軌跡）、§30（LSP の所有境界）、
> §32（リファクタリング）、§33（Rider 相当の C# 編集）。

## §35.1 何を目指すか

Zed の Multibuffer が示したのは「編集の単位はファイルでなくてよい」ということだった。検索結果・参照・
診断・変更ハンクを**抜粋のまま並べて、その場で直す**。もう一つの軸が「テキストの行や字ではなく
**構文木の要素**を掴んで操作する」こと。この2つは独立した機能ではなく、
「この引数」「このメソッド」「このシンボルの呼び出し元すべて」といった**意味の単位で素材を掴み、
運び、直す**という同じ目標の両面である。

Loomo の物差し（場所としての信頼：周辺視野・ペイン間の素材の流れ・復元の完全さ）に当てはめると:

- 抜粋ペインは**素材の流れ（§24.3／§24.7）の受け皿**であって、エディタ単体の小技ではない。
- 構文木の選択（§24.9）は「送る」「リファクタリング」の入口であり、構文木の編集はその先の出口になる。

## §35.2 構文木を単位にした編集（C#・実装済み）

### 操作

| コマンド Id | 名前 | 既定キー |
|---|---|---|
| `editor.csharp.structure.moveUp` | 文・メンバーを上へ移動 | `Ctrl+Shift+Up` |
| `editor.csharp.structure.moveDown` | 文・メンバーを下へ移動 | `Ctrl+Shift+Down` |
| `editor.csharp.structure.moveLeft` | 引数・要素を左へ移動 | `Ctrl+Alt+Shift+Left` |
| `editor.csharp.structure.moveRight` | 引数・要素を右へ移動 | `Ctrl+Alt+Shift+Right` |
| `editor.csharp.structure.delete` | 構文要素を区切りごと削除 | なし |

キーは Rider の Move Statement／Move Element に合わせた（§33 の方針）。`Ctrl+W` 系・`Alt+↑↓` は使わない
（前者は部屋の動線、後者は他エディタの「行の移動」と混同される）。右クリックは「C#」→「構造」の入れ子、
パレットは `CSharpEditorCommandCatalog` から自動で載る。

### 置き場所

- 判断は純関数 `Loomo.CSharp/Editor/CSharpStructuralEditing.cs`（`Move` / `Delete`）。1 ファイルの
  **構文だけ**を見る——意味解析もプロジェクト読込も要らないので、ソリューションを開いていない `.cs` でも即座に効く。
- 結線は `Views/Shell/Editor/ShellWindow.StructuralEditing.cs`。計算結果を `TryApplyLspTextEdits` で
  **1回の undo** として適用し、動かした要素を選択し直す（続けて押せば同じ要素がさらに動く）。
- Editor ライブラリは変更していない（§24.9 と同じく既存の口だけで足りる）。

### 「どの要素か」の決め方

- 選択があれば、選択（前後の空白を除く）を含む最も内側の要素。§24.9 の「意味的に広げる」で
  引数→文→メソッドと育ててから動かせば、狙う段を選べる。
- **選択が「生きている」かを確かめる。** `SelectRange` で付けた選択は Normal モードのまま残り、別の場所を
  クリックしてもキャレットだけが動いて選択は消えない。キャレットが選択の外へ出ていれば利用者が自分で
  動かしたとみなして選択を捨てる（`ShellWindow.StructuralEditing.LiveSelection`）。端ちょうどで比べないのは、
  エディタが選択を終端を含む形で持つため、利用者が作った選択ではキャレットが LSP の終端と1桁ずれうるから。
  ※実機で、動かした文の選択を残したまま引数をクリックして左右移動すると「動かせる要素が無い」になっていた
  （単体テストは純関数に選択を渡すので、この経路は実機でしか出ない）。
- 選択が無ければキャレット位置。`Foo(a|, b)` のようにキャレットが要素の**直後**にあるときはその要素を掴む
  （カンマや `;` を掴んで親へ外れない）。
- 並びは2種類で、コマンドごとに探す種類が決まっている（引数の中で `Ctrl+Shift+↑` を押せば、外側の文が動く）:
  - **行の並び**: Block／switch セクションの文、型・名前空間・コンパイル単位のメンバー、switch セクション、
    using、アクセサー。埋め込み文（`if (x) Foo();` の `Foo();`）は並びではないので親へ上がる。
  - **カンマの並び**: 構文の種類を列挙せず「親の子の並びでカンマに隣接している」で判定する。引数・
    パラメーター・型引数・初期化子・タプル・パターン・基底型・属性・enum メンバーを一律に扱える。
    要素が1つだけの並び（`Foo(x)`）は相手がいないので外側の並びへ上がる。
- 削除は種類を問わず最も内側の要素。

### 移動の塊

- 行の並びで、**両方の要素が行を独占している**ときは行単位で入れ替える。直前に付いたコメント
  （`///` を含む。空行を挟んだ先のコメントは別物）と行末コメントも連れていき、要素の間の空行は残す。
- どちらかが他の文と同じ行にあるとき（`A(); B();`）は、字下げを壊さないよう構文の範囲だけを入れ替える。
- カンマの並びは構文の範囲だけを入れ替え、カンマはその場に残す。

### 削除の塊

- カンマの並び: 後ろに要素があれば「要素, 」を（次の要素の頭まで消すので、複数行に並んだ引数でも
  改行と字下げが崩れない）、末尾なら「, 要素」を消す。
- 行の並び: 付随コメントと改行ごと消す。前後が空行なら空行が2つ続かないよう1つ詰め、型の最後の
  メンバーなら閉じ括弧の前に空行を残さない。

### 守ること

1. **構文エラーを増やす編集は返さない。** 適用後の本文を再パースし、エラー数が増えたら中止して理由を出す
   （インライン補完の `FimCandidateFilter` の「新しく壊したものだけを咎める」と同じ考え方）。
2. **ディレクティブをまたがない。** `#region`／`#if` などが入れ替え・削除の範囲に入るなら中止する
   （条件付きコンパイルや region の所属が黙って変わるため）。なお、無効な `#if` ブロックの中身は
   構文木に現れないので、そもそも兄弟として数えられない。
3. **黙らない。** 動かせる要素が無い・端に着いた・ディレクティブをまたぐ——すべて状態行に理由を出す。
4. **フォーカスの関門。** 本文を書き換えるので、キーからはエディタにフォーカスがあるときだけ実行する
   （`CanExecuteKeyboardCommand`）。ターミナルで押した `Ctrl+Shift+↑` が裏の C# タブの文を動かす事故を防ぎ、
   キーは内側のペインへ届く。

### 次の候補

- 兄弟の選択（次／前の要素を選ぶ）、子要素の一括マルチカーソル。
- 包む／外す（`if`／`try`／`using` で包む、外側のブロックを外す）。
- C# 以外: Core に `ISyntaxTreeProvider`（`NodeAt` / `Parent` / `Children` / 兄弟）を置き、
  Roslyn 実装（C#）・tree-sitter 実装（他言語）・`selectionRange` フォールバック（親方向のみ）を差し替える。
  tree-sitter は文法ごとのネイティブ DLL を同梱することになるが、RID が win-x64 固定なので配布は素直。

## §35.3 抜粋ペイン（マルチバッファ）— 構想

### 流し込み元

検索ペインの結果／LSP の参照・呼び出し階層・実装／診断一覧／Git の変更ハンク／構造検索（§35.2 の発展）。
AI の編集結果のレビューも流し込み元の1つになりうるが、主役ではない。

### 前提工事：共有文書モデル（Phase 0）

現在の Editor は `TextBuffer`（`List<string>`）をコントロールごとに持ち、分割ビューや切り離しウィンドウは
**複製＋同期**で成り立っている。抜粋で直した内容を元ファイルのタブへ即座に反映するには、
「1ファイル＝1文書、ビューは複数」の文書モデルがホスト側に要る。§30 で LSP 文書を
`LspDocumentTable`（1 URI に `didOpen` 1回、書き手／読み手、参照カウント）へ移したのと同じ形を、
本文そのものへ広げる。範囲の端は行番号でなく**アンカー**（編集で自分の位置を補正するもの）で持つ。
これは分割・切り離しの同期も単純にするので、マルチバッファが無くても得をする。§30 と同規模の設計判断になる。

### Phase 1：小さなエディタを縦に積む

抜粋1つに `VimEditorControl` 1枚、仮想化リストで並べる。どれも共有文書を見るので LSP・ハイライト・
Vim はそのまま効き、Editor ライブラリの変更はほぼ要らない。弱点は抜粋をまたぐ移動・置換と、
枚数が増えたときの重さ（ペイン切替の重さは再ペアレントだった、という教訓がそのまま当てはまる）。
一括操作はホストが `WorkspaceEdit` を組んで `ApplyLspWorkspaceEdit` へ流す。

### Phase 2：1枚に合成するビュー

Editor ライブラリに、読み取り専用の見出し行（ブロック装飾）、ガターの元行番号の対応表、
抜粋の境界をまたぐ編集の拒否、抜粋ごとの言語（ハイライトと LSP 位置の変換）を足す。ホストは
仮想文書↔元文書の `ExcerptMap` を持ち、編集を元文書への TextEdit 群に変換し、undo は複数ファイルに
またがるトランザクションとして記録する。

### 部屋としての約束

- **抜粋はシンボルでも定義できる**ようにする（「`Foo.Bar` メソッド全体」）。編集で行がずれても
  documentSymbol／Roslyn で引き直せる——§35.2 の構文木がここで効く。
- **復元**: `WorkspaceSnapshot` には中身ではなく生成元（検索語・参照元シンボル・診断フィルタ）と
  抜粋ごとのアンカー・キャレットを保存し、再オープン時に引き直す。
- **軌跡（§27）**: 抜粋内の移動は仮想位置ではなく**元ファイルの位置**として記録する。
- **マルチルート**: 見出しは `workspace.ToDisplayPath`、所属判定は `workspace.Contains`。
