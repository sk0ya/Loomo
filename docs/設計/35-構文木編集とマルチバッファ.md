# §35 構文木編集とマルチバッファ（ファイル単位の編集からの脱却）

> 状態: **§35.2（C# の構文木編集）と §35.3（抜粋タブ）は実装済み**（2026-10-08）。抜粋タブの復元・軌跡は未対応。
> 関連: §24.9（意味的な選択の拡大／縮小）、§24.3／§24.7（素材の流れ）、§27（軌跡）、§30（LSP の所有境界）、
> §32（リファクタリング）、§33（Rider 相当の C# 編集）。

## §35.1 何を目指すか

Zed の Multibuffer が示したのは「編集の単位はファイルでなくてよい」ということだった。検索結果・参照・
診断・変更ハンクを**抜粋のまま並べて、その場で直す**。もう一つの軸が「テキストの行や字ではなく
**構文木の要素**を掴んで操作する」こと。この2つは独立した機能ではなく、
「この引数」「このメソッド」「このシンボルの呼び出し元すべて」といった**意味の単位で素材を掴み、
運び、直す**という同じ目標の両面である。

Loomo の物差し（場所としての信頼：周辺視野・ペイン間の素材の流れ・復元の完全さ）に当てはめると:

- 抜粋ペインは**素材の流れ（§24.3／§24.7）の受け皿**であって、エディタ単体の小技ではない。
- 構文木の選択（§24.9）は「送る」「リファクタリング」の入口であり、構文木の編集はその先の出口になる。

## §35.2 構文木を単位にした編集（C#・実装済み）

### 操作

| コマンド Id | 名前 | 既定キー |
|---|---|---|
| `editor.csharp.structure.moveUp` | 文・メンバーを上へ移動 | `Ctrl+Shift+Up` |
| `editor.csharp.structure.moveDown` | 文・メンバーを下へ移動 | `Ctrl+Shift+Down` |
| `editor.csharp.structure.moveLeft` | 引数・要素を左へ移動 | `Ctrl+Alt+Shift+Left` |
| `editor.csharp.structure.moveRight` | 引数・要素を右へ移動 | `Ctrl+Alt+Shift+Right` |
| `editor.csharp.structure.delete` | 構文要素を区切りごと削除 | なし |

キーは Rider の Move Statement／Move Element に合わせた（§33 の方針）。`Ctrl+W` 系・`Alt+↑↓` は使わない
（前者は部屋の動線、後者は他エディタの「行の移動」と混同される）。右クリックは「C#」→「構造」の入れ子、
パレットは `CSharpEditorCommandCatalog` から自動で載る。

### 置き場所

- 判断は純関数 `Loomo.CSharp/Editor/CSharpStructuralEditing.cs`（`Move` / `Delete`）。1 ファイルの
  **構文だけ**を見る——意味解析もプロジェクト読込も要らないので、ソリューションを開いていない `.cs` でも即座に効く。
- 結線は `Views/Shell/Editor/ShellWindow.StructuralEditing.cs`。計算結果を `TryApplyLspTextEdits` で
  **1回の undo** として適用し、動かした要素を選択し直す（続けて押せば同じ要素がさらに動く）。
- Editor ライブラリは変更していない（§24.9 と同じく既存の口だけで足りる）。

### 「どの要素か」の決め方

- 選択があれば、選択（前後の空白を除く）を含む最も内側の要素。§24.9 の「意味的に広げる」で
  引数→文→メソッドと育ててから動かせば、狙う段を選べる。
- **選択が「生きている」かを確かめる。** `SelectRange` で付けた選択は Normal モードのまま残り、別の場所を
  クリックしてもキャレットだけが動いて選択は消えない。キャレットが選択の外へ出ていれば利用者が自分で
  動かしたとみなして選択を捨てる（`ShellWindow.StructuralEditing.LiveSelection`）。端ちょうどで比べないのは、
  エディタが選択を終端を含む形で持つため、利用者が作った選択ではキャレットが LSP の終端と1桁ずれうるから。
  ※実機で、動かした文の選択を残したまま引数をクリックして左右移動すると「動かせる要素が無い」になっていた
  （単体テストは純関数に選択を渡すので、この経路は実機でしか出ない）。
- 選択が無ければキャレット位置。`Foo(a|, b)` のようにキャレットが要素の**直後**にあるときはその要素を掴む
  （カンマや `;` を掴んで親へ外れない）。
- 並びは2種類で、コマンドごとに探す種類が決まっている（引数の中で `Ctrl+Shift+↑` を押せば、外側の文が動く）:
  - **行の並び**: Block／switch セクションの文、型・名前空間・コンパイル単位のメンバー、switch セクション、
    using、アクセサー。埋め込み文（`if (x) Foo();` の `Foo();`）は並びではないので親へ上がる。
  - **カンマの並び**: 構文の種類を列挙せず「親の子の並びでカンマに隣接している」で判定する。引数・
    パラメーター・型引数・初期化子・タプル・パターン・基底型・属性・enum メンバーを一律に扱える。
    要素が1つだけの並び（`Foo(x)`）は相手がいないので外側の並びへ上がる。
- 削除は種類を問わず最も内側の要素。

### 移動の塊

- 行の並びで、**両方の要素が行を独占している**ときは行単位で入れ替える。直前に付いたコメント
  （`///` を含む。空行を挟んだ先のコメントは別物）と行末コメントも連れていき、要素の間の空行は残す。
- どちらかが他の文と同じ行にあるとき（`A(); B();`）は、字下げを壊さないよう構文の範囲だけを入れ替える。
- カンマの並びは構文の範囲だけを入れ替え、カンマはその場に残す。

### 削除の塊

- カンマの並び: 後ろに要素があれば「要素, 」を（次の要素の頭まで消すので、複数行に並んだ引数でも
  改行と字下げが崩れない）、末尾なら「, 要素」を消す。
- 行の並び: 付随コメントと改行ごと消す。前後が空行なら空行が2つ続かないよう1つ詰め、型の最後の
  メンバーなら閉じ括弧の前に空行を残さない。

### 守ること

1. **構文エラーを増やす編集は返さない。** 適用後の本文を再パースし、エラー数が増えたら中止して理由を出す
   （インライン補完の `FimCandidateFilter` の「新しく壊したものだけを咎める」と同じ考え方）。
2. **ディレクティブをまたがない。** `#region`／`#if` などが入れ替え・削除の範囲に入るなら中止する
   （条件付きコンパイルや region の所属が黙って変わるため）。なお、無効な `#if` ブロックの中身は
   構文木に現れないので、そもそも兄弟として数えられない。
3. **黙らない。** 動かせる要素が無い・端に着いた・ディレクティブをまたぐ——すべて状態行に理由を出す。
4. **フォーカスの関門。** 本文を書き換えるので、キーからはエディタにフォーカスがあるときだけ実行する
   （`CanExecuteKeyboardCommand`）。ターミナルで押した `Ctrl+Shift+↑` が裏の C# タブの文を動かす事故を防ぎ、
   キーは内側のペインへ届く。

### 次の候補

- 兄弟の選択（次／前の要素を選ぶ）、子要素の一括マルチカーソル。
- 包む／外す（`if`／`try`／`using` で包む、外側のブロックを外す）。
- C# 以外: Core に `ISyntaxTreeProvider`（`NodeAt` / `Parent` / `Children` / 兄弟）を置き、
  Roslyn 実装（C#）・tree-sitter 実装（他言語）・`selectionRange` フォールバック（親方向のみ）を差し替える。
  tree-sitter は文法ごとのネイティブ DLL を同梱することになるが、RID が win-x64 固定なので配布は素直。

## §35.3 抜粋タブ（マルチバッファ）— 1枚に合成するビューで実装（2026-10-08）

### 流し込み元

検索ペインの結果／LSP の参照・呼び出し階層・実装／診断一覧／Git の変更ハンク／構造検索（§35.2 の発展）。
AI の編集結果のレビューも流し込み元の1つになりうるが、主役ではない。

### 前提工事：共有文書モデル（Phase 0）— 差分とアンカーは実装済み

**決定（2026-10-08）: Editor に差分イベントを足し、文書のハブは Loomo 側に置く。** 選択肢は
(a) Loomo 側だけで `EditorTextMirror` を一般化する（打鍵ごとの全文比較と、比較から推定するアンカーの
不正確さが残る）、(b) Editor に差分イベントを1つ足す、(c) Editor で TextBuffer を本当に共有する
（大改修）の3つで、(b) を選んだ。

- **Editor 1.0.98**: `TextBuffer.Changed` / `VimEditorControl.TextEdited`。全ての書き換えが LSP の
  contentChanges と同じ形（変更前の座標の範囲＋新しい文字列）で通知され、順に写しへ適用すれば本文と一致する
  （Editor 側に、全メソッドの端のケースと 2000 手のランダム操作で写しが一致するテストがある）。読み込みは
  `Reload` として区別し、undo やホストの全文置換は**変わった行だけ**を範囲にする（範囲の外の位置が
  文書の頭へ潰れないように）。購読者がいる間だけ計算するので、使わないビューの打鍵コストは変わらない。
- **アンカー**: `Loomo.Services/Editor/TextAnchors.cs`（`TextAnchorMath.Transform` / `AnchoredRange`）。
  本文を見ずに差分1つで位置を写すので、文書の大きさに比例するコストがかからない。始まりは前寄せ（始まり
  ちょうどへの挿入は範囲に入る）。終わりは使い方で選ぶ：文字の範囲なら後ろ寄せ、**抜粋のような行の半開区間
  （終わり＝次の行の行頭）なら前寄せ**（直後の行への挿入は範囲の外）。中身がまるごと消えたら `IsCollapsed`、
  読み直されたら `IsInvalidated`。
- **編集の関門と差分の保留（Editor 1.0.98）**: `VimEditorControl.EditGuard`（`HostEditGuard`：編集前後の全行を
  受け取り、断るなら理由を返す）。編集トランザクションの終わりの「変わっていたら戻す」一か所で判定するので、
  Ex コマンド・挿入の入力・`J`/`dd` を個別に洗い出さなくて漏れない。あわせて**トランザクション中の差分は
  確定まで溜め、巻き戻したら捨てる**——そうしないと、断った編集が「編集→巻き戻し」の2つの差分として
  外へ流れ、それを元ファイルへ写すホストが両方を写してしまう（読み取り専用で断った編集も同じ）。
- **`EditorTextMirror` は置き換えていない。** 受け側の `TryApplyLspTextEdits` が内部で本文全体を組み直す
  （`ApplyTextEdits` → `ApplyExternalText`）ので、送り側だけ差分にしても打鍵ごとの O(文書) は消えない。
  受け側にも差分のまま入れる口ができたら置き換える。

以下は当初の整理（目的）:

現在の Editor は `TextBuffer`（`List<string>`）をコントロールごとに持ち、分割ビューや切り離しウィンドウは
**複製＋同期**で成り立っている。抜粋で直した内容を元ファイルのタブへ即座に反映するには、
「1ファイル＝1文書、ビューは複数」の文書モデルがホスト側に要る。§30 で LSP 文書を
`LspDocumentTable`（1 URI に `didOpen` 1回、書き手／読み手、参照カウント）へ移したのと同じ形を、
本文そのものへ広げる。範囲の端は行番号でなく**アンカー**（編集で自分の位置を補正するもの）で持つ。
これは分割・切り離しの同期も単純にするので、マルチバッファが無くても得をする。§30 と同規模の設計判断になる。

### 形の決定：エディタのタブに、1枚に合成した仮想文書として置く

置き場所は**エディタのタブ**にした（新しいペイン種別・検索ペインの表示切替と比べて、タブ・分割・切り離しの
既存の仕組みに乗れる）。ただし `EditorTab` は `VimEditorControl` 1枚と強く結び付いているので、当初の
「小さなエディタを縦に積む Phase 1」はタブの形に合わない。そこで**当初の Phase 2（1枚に合成）を直接作った**。
合成に要る Editor 側の口は2つだけで済んだ：上の `EditGuard`（見出し行を守る）と、ガターの行番号の差し替え
（`VimEditorControl.SetLineNumberLabels`：行→表示する文字列。本文の行は元ファイルの行番号、見出しは空欄）。

**元ファイルへの反映は「元タブへ即時」**（決定 2026-10-08）。ファイルの持ち主は引き続きエディタタブで、
抜粋タブで打った変更はその場で元ファイルのタブへ入る。元ファイルが開いていなければ、抜粋に初めて書いた
時点で裏のタブで開く（前面には出さない）。読むだけならタブは増えない。保存は元タブ、または抜粋タブでの
Ctrl+S（＝結び付いた元ファイルのうち未保存のものを保存。全て保存済みになったら抜粋タブの印も消す）。

### 実装

- **モデル**: `Loomo.Services/Editor/ExcerptDocument.cs`（純粋。エディタにも WPF にも触れない）。
  - `ExcerptPlanner.Plan`：一覧の各行を前後2行に広げ、同じファイルで重なる・隣り合うものはまとめる。
  - `ExcerptDocument`：見出し行（`// ── 表示パス` のようにその言語のコメントに見せる。**行番号は入れない**
    ——ずれるたびに見出しを書き換えずに済むよう、行番号はガターで出す）＋本文の行を並べる。
    `Guard`（見出しに触れる編集・2つの抜粋にまたがる編集を断る。行の差分で判定）、`TranslateEdit`
    （抜粋タブの差分→元ファイルの座標）、`SourceChanged`／`Resync`（元ファイルの変化→抜粋タブへ写す編集）。
  - 見出しの行頭への「行の挿入」（見出しの上に `O`）は、元ファイルでは前の抜粋の最終行の行末に `"\n…"` を
    足す形に直す。そのまま入れると抜粋の終わり（次の行の行頭・前寄せ）ちょうどへの挿入になり、足した行が
    抜粋の外に出る。
- **結線**: `Loomo.App/Services/Editor/ExcerptTabController.cs`（抜粋タブ1枚と元タブの差分を両方向へ運ぶ）、
  `Views/Shell/Editor/ShellWindow.Excerpts.cs`（開く・裏で開く・保存・元の行へ飛ぶ）。
- **入口**: 参照一覧のポップアップの先頭に「▤ 抜粋タブで開く」。このポップアップは参照・grep・診断一覧・
  コール／型階層・ワークスペースシンボルが共用しているので、それら全てが入口になる。右クリックには
  「元のファイルのこの行を開く」。

### 守っていること（ここが緩むと元ファイルを壊す）

- **自分で入れた編集の通知は捨て、アンカーは自分の正確な編集で動かす。** 元タブはホストの編集
  （`TryApplyLspTextEdits` → `ApplyExternalText` → `ReplaceAll`）を**行単位の差分**として報告し直す。
  それでアンカーを動かすと、抜粋の境界の行がどちらに属するか曖昧になる（末尾に足した行が抜粋から外れる）。
- **元ファイル側から写した編集は、抜粋タブの undo に残さない**（写した直後に undo 履歴を捨てる）。残すと、
  undo で古い本文へ戻したものが差分として元ファイルへ流れ込む。元タブ側の undo は生きている。
- **抜粋タブ自身の差分通知の最中に抜粋タブを書き換えない。** 裏でタブを開いた結果の写し直し
  （`EditorDocumentEvents.Loaded`）や、写せなかった編集の作り直しは `Dispatcher.BeginInvoke` で後に回す。
- **モデルは元ファイルへ入ってから確定する**（`TranslateEdit` は写すだけ、`Commit` で確定）。元ファイルを
  開けない・入れられないときにモデルだけ進むと、抜粋タブと元ファイルが食い違ったまま以後の編集がずれた行へ入る。
  入れられなかったら抜粋タブをモデル（＝編集前）へ戻す。
- **元タブが閉じられたら、ディスクの内容で写し直す**。未保存の変更を捨てて閉じた場合、抜粋に残っているのは
  捨てられた本文なので、そのままだと次の打鍵でディスクから開き直した元ファイルへずれた位置で書き込む。
- **ワークスペースを分ける**。抜粋タブは作られたときのタブ集合（ワークスペース）を覚え、別のワークスペースで
  開いた同名ファイルには結び付かない。元ファイルを探す・裏で開くのは Diff の右側と同じ `DiffWorkingDocuments`
  （切替の途中は開かない・パスの正規化）に任せる。
- **元ファイルの全文を取らない**。元タブで抜粋の中を打つたびに `VimEditorControl.Text` を割ると打鍵ごとに
  文書まるごとの複製になるので、バッファから行を1つずつ引く（`BufferLines`）。ガターの行の種類の判定は
  見出し位置の二分探索。
- 抜粋を作るときは、開いているタブがあれば**その本文**（未保存の変更を含む）から作る。ディスクから作ると、
  未保存の変更の分だけ行がずれた抜粋に編集を入れてしまう。
- テスト: モデルは `ExcerptDocumentTests`（実際の `TextBuffer` を抜粋タブと元ファイルの両方に立て、400 手の
  ランダム編集で両者が一致し続ける）、Editor 側は `HostEditGuardTests`・`TextBufferChangeTests`。実機では
  参照→抜粋タブ→抜粋で編集→元タブに入る／元タブで編集→抜粋に写る／見出しの `x` は断られる／Ctrl+S で
  元ファイルが保存され両タブの印が消える／右クリックで元の行へ飛ぶ、を確認した。

### まだ無いもの

- **復元**: 抜粋タブは仮想文書なので、ワークスペースのスナップショットから外れる（`PeekIsVirtual`）。
  下の「部屋としての約束」の形（生成元＋アンカーを保存して引き直す）で入れる。
- **軌跡（§27）**: 抜粋タブ内の移動は記録されない（仮想文書は記録対象外）。元ファイルの位置として記録する。
- **LSP**: 抜粋タブには言語サーバーが付かない（補完・ホバー・定義へ移動は効かない）。元の行へは右クリックで飛ぶ。
- **シンボル単位の抜粋**（「`Foo.Bar` メソッド全体」）と、ホストの全文置換が行差分で報告されたときの
  境界の曖昧さ（元タブで整形した直後など、抜粋の端の1行がずれうる）。

### 部屋としての約束

- **抜粋はシンボルでも定義できる**ようにする（「`Foo.Bar` メソッド全体」）。編集で行がずれても
  documentSymbol／Roslyn で引き直せる——§35.2 の構文木がここで効く。
- **復元**: `WorkspaceSnapshot` には中身ではなく生成元（検索語・参照元シンボル・診断フィルタ）と
  抜粋ごとのアンカー・キャレットを保存し、再オープン時に引き直す。
- **軌跡（§27）**: 抜粋内の移動は仮想位置ではなく**元ファイルの位置**として記録する。
- **マルチルート**: 見出しは `workspace.ToDisplayPath`、所属判定は `workspace.Contains`。
