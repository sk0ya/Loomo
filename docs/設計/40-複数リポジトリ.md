## §40.1 目的と位置

ワークスペースはフォルダーの集合になった（マルチルート・§32.10）が、**Git は今も「対象リポジトリが1つ」**の
作りのままである。Loomo（アプリ）と AimAssist（別リポジトリ）を1つの部屋に入れると、Git パネル・Git セッション・
差分・裏の fetch・ガターの比較元は、そのうち**どれか1つ**しか見ない。どれを見ているかはコンボボックスで決まり、
ファイル起点の操作（ブレーム・履歴）で**黙って入れ替わる**。

部屋の物差し（§24「場所としての信頼」）で言えば、これは周辺視野の欠落である。

- **見えない**：もう一方のリポジトリが汚れていても、ahead していても、rebase の途中で止まっていても、
  そちらへ切り替えるまで分からない。
- **足元が動く**：ブレームを開いただけで Git パネルの中身が別のリポジトリに変わる。見ていた変更一覧が
  理由なく消えたように見える。
- **入らない**：`C:\work` を1つ入れてその下に `api/`・`web/` という2つのリポジトリがある構成では、
  `rev-parse --show-toplevel` が失敗し、**全体が Git 管理外**として扱われる。

この章の答えは、**リポジトリを部屋の中の「場所」の単位に加え、場所を見せるすべての面（ツリー・ファイル一覧・
Git パネル・Git セッション・差分・ステータスバー）で同じ部品で見せる**こと。AI のための機能ではなく、§23/§24 と
同じ「道具としての部屋」の作り込みである。

## §40.2 現状——何が「1つ」なのか

### §40.2.1 根：暗黙の対象（ambient state）

`GitService`（`Loomo.Services/Git/GitService.cs`）は DI のシングルトンで、`GitRootState.CurrentRoot`
（明示選択したワークスペースフォルダー、無ければプライマリ）を**ただ1つ**持つ。`GitCommandRunner` は git を
起こすたびにこの値を読むので、runner を受け取る**サブサービス 22 ファイル**（status・branch・commit・log・
diff・stash・worktree・rebase…）は全員、呼び出し側が意識しないまま同じ1か所に対して動く。

これは §32.10 で潰した欠陥と**同じ形**である。あちらは「プライマリと比べる」、こちらは「共有された1つの
対象で実行する」。直し方も同じで、**対象を暗黙の状態にせず、問い合わせて明示的に渡す**。

### §40.2.2 1か所しか見ていない面

| 面・機能 | 依存の仕方 |
|---|---|
| Git パネル（`GitPanelViewModel`） | `_git.RootPath` を 13 か所。切替は `GitRootSwitchViewModel`（コンボボックス） |
| Git セッション（`GitSessionViewModel`） | `_git.RootPath` を 10 か所。`SetActiveRootForPath` でファイル起点に**自動切替** |
| 差分ペイン（`DiffSessionQuery`） | 作業ツリー差分を `_git.RootPath` 基準で取る |
| 裏の fetch（`GitAutoFetchScheduler`・§24.92） | 対象リポジトリだけ。切替で予定を組み直す |
| ガターの比較元（`EditorGutterBaseTracker`） | 比較基準の解決を `_git.RootPath` で行う |
| 不在サマリー・GitHub／Azure の PR・削除済みファイル | `_git.RootPath` |
| 変更の監視（`GitRepositoryMonitor`） | 対象1つだけを 1.5 秒ごとにポーリング |
| 比較基準の復元（`WorkspaceSnapshot.GitCompare`） | ワークスペースに**1つ**。ブランチ名はリポジトリごとに違うのに |

### §40.2.3 すでにフォルダーごとに分かれているもの（ただし単位は「フォルダー」）

- **エクスプローラー**：マルチルートのときフォルダーごとに `FolderTreeRootState.GitState`（`GitTreeState`）を
  持ち、独立に読み込む。ただし1フォルダー＝1リポジトリの前提で、入れ子のリポジトリは区別できない。変更ありの
  集約（`AggregateNestedGitStatus`）もリポジトリの境目を越えて上へ伝わる。
- **エディタのガター**：`EditorGitService` は `RunInFolderAsync` でフォルダーを指定して git を起こす。
- **コミットの下書き**（`CommitDrafts`・§24.32）：鍵は「Git の対象フォルダー」。リポジトリ単位に近いが、
  フォルダーとリポジトリがずれる構成では食い違う。

### §40.2.4 見せ方の制約

- **エクスプローラーの見出し行がコンボボックスそのもの**（`FolderTreeView.xaml` の `RootSwitchCombo`）。
  ピン留めしたサブフォルダーへの切替のための部品で、ブランチや ahead/behind を置く余地が無い。出せるのは
  右端の「●」だけ。1フォルダー時はツリーの上に別のコンボボックスがあり、単一とマルチで形が違う。
- **ファイル一覧ペインは Git の状態をツリーから借りている**（`FilesColumnViewModel` → `_folderTree.GitStatusForPath`
  ／`GitStatusesForPaths`）。サイドバーが別パネルのときにこそ使う面（§26.10「サイドバーは排他」）なのに、
  Git の印はツリーに依存している。右クリックの Git 項目（ブレーム・履歴・.gitignore）もツリー経由。
- ファイル一覧の区切りもワークスペースフォルダー単位：パンくずの先頭、マルチルートの切替行、2/4 カラムを
  増やしたときの第1候補（`OpenUnshownPlace`・§26.10.1）、「場所」の `FilesPlaceKind.WorkspaceFolder`。

## §40.3 用語と規約

- **リポジトリ**：`git rev-parse --show-toplevel` が返す作業ツリーの根（正規化した絶対パス）。これが
  **識別子**（`GitRepositoryId`）。リンクされたワークツリーは別の作業ツリーなので**別のリポジトリ**として数え、
  共通の `--git-common-dir` で「同じ本体のワークツリー」と分かるようにする。サブモジュールは親の中の
  別リポジトリとして数え、種別を持つ。
- **所属**：あるパスが属するリポジトリは、そのパスを含むリポジトリのうち**いちばん深いもの**。
  （`WorktreeRoomSeed.PathMap` の「持ち主はいちばん深いワークツリー」と同じ規則。）
- **規約（§32.10 の Git 版）**：
  1. 「このパスはどのリポジトリか」は `GitRepositoryCatalog.RepositoryFor(path)` だけが答える。
     **`StartsWith` を手で書かない。`GitService.RootPath` に頼らない。**
  2. git を起こすときは `GitService.For(repo)`（または `ForPath(path)`）で**対象を明示**する。
  3. 状態（ブランチ・ahead/behind・変更・操作中）は `GitWorkspaceStatus` から引く。**面同士で借り合わない**
     （ファイル一覧がツリーから借りる形をやめる）。
  4. アクティブなファイルに合わせて変わるのは**表示だけ**。操作の対象を黙って入れ替えない。

## §40.4 基盤：`GitRepositoryCatalog`

`Loomo.Services/Git/`（新規）。ワークスペースの全リポジトリを知る唯一の場所。

- **見つけ方**（ワークスペースフォルダーごと）：
  1. フォルダー自身、またはその先祖がリポジトリ → そのリポジトリ（`rev-parse --show-toplevel`）。
  2. フォルダーの下 **2 段まで**の `.git`（ディレクトリまたはファイル＝ワークツリー／サブモジュール）。
     2 段は `C:\work\{api,web}` と `C:\src\org\{a,b}` を拾い、`node_modules` の奥までは潜らない深さ。
     `bin`／`obj`／`node_modules`／`.git` は潜らない（`DebouncedFolderWatcher` の除外と揃える）。
  3. 見つけたリポジトリの中では、さらに下へは探さない（サブモジュールは `git submodule status` から足す）。
- **API**：`Repositories`（ワークスペースフォルダーの順→その中の深さ優先の順）、`RepositoryFor(path)`、
  `RepositoriesIn(folder)`、`Changed` イベント。
- **git を起こさない**：`.git`（ディレクトリでもファイルでも）を持つディレクトリがそのまま作業ツリーの根なので、
  `rev-parse --show-toplevel` と同じ答えになる。フォルダーを開くたびに候補の数だけ git を起こさずに済む。
  `GIT_DIR`／`core.worktree` で根をよそへ向けた特殊な構成は扱わない。種類は `.git` の形で決める：ディレクトリ＝
  本体、ファイルで `gitdir:` が `…/worktrees/<名前>` ＝ワークツリー（共通ディレクトリはその2つ上）、それ以外＝
  サブモジュール。サブモジュールは `git submodule status` ではなく `.gitmodules` の `path` を読み、チェックアウト
  済み（`.git` がある）ものだけ数える。ジャンクション（再解析ポイント）には潜らない。
- **作り直す契機**：`FoldersChanged` と `Refresh()`。一覧は遅延で作る（最初の問い合わせで探索が走るので、
  UI スレッドからは呼ばない）。ワークスペースフォルダー直下 2 段での `.git` の出現・消滅（クローン・`git init`・
  削除）を拾って `Refresh()` を呼ぶのは P2（`GitWorkspaceStatus` の監視）の仕事。
- **重なり**：`WorkspaceService.AddFolder` が祖先／子孫のフォルダーを拒むので、ワークスペースフォルダー同士は
  重ならない。リポジトリは重なり得る（入れ子）ので、所属は常に「いちばん深い」で決める。
- `Folders` の外のリポジトリ（フォルダーの先祖にある根）は、根がフォルダーより上でも**ワークスペースの中にある
  部分だけ**を扱う（ツリーに出るのはフォルダー配下だけなので）。

## §40.5 `GitService` をリポジトリ単位に

- **中身は移さず、対象を固定した `GitService` をリポジトリごとに作る**（P1 で決定）。下位サービスはすべて
  `GitRootState.CurrentRoot` 経由で作業ディレクトリを決めているので、`GitRootState` に「固定」の形
  （`new GitRootState(root)`・`IsFixed`）を足し、それを持たせた `GitService` を作れば、サブサービス 22 ファイルと
  照会のキャッシュ・変更の監視はそのまま「そのリポジトリのもの」になる。別クラス `GitRepository` へ移す案は、
  857 行の移設と全呼び出し側の型の付け替えが要るわりに得るものが名前だけなので採らなかった。
- 窓口：`GitService.For(root)`／`For(GitRepositoryInfo)`／`ForPath(path)`（どのリポジトリにも属さなければ null）、
  一覧は `GitService.Repositories`（＝DI の `GitRepositoryCatalog`）。同じリポジトリには**同じインスタンス**を返す
  （照会のキャッシュと監視を共有するため）。固定の窓口から `For` を呼んでもワークスペースの窓口へ回るので、
  どこから引いても同じものになる。一覧に無い根でも作る（クローン直後など、一覧の作り直しより先に操作する場面）。
  作ったインスタンスはセッション中持ち続ける（数はリポジトリの数で頭打ち）。
- 固定の窓口では `SetActiveRoot`／`SetActiveRootForPath` は**何もしない**（`IsRepositoryScoped`）。リポジトリを
  明示して得た窓口の対象が、よその操作で入れ替わってはいけないため。
- **移行期の互換**：`RootPath`／`SetActiveRoot`／`SetActiveRootForPath`／`ActiveRootChanged` は P1〜P6 の間、
  「いま Git パネルで選んでいるリポジトリ」を返す互換の口として残し、P7 で消す。新しいコードはこれを使わない。
- 書き込み系（commit・checkout・rebase…）の排他は**リポジトリごと**。別リポジトリの fetch が commit を待たせない。

## §40.6 状態の集約：`GitWorkspaceStatus`

`Loomo.App/Services/Git/`（新規、シングルトン）。全リポジトリの「いまの様子」を1か所に持つ。

- **リポジトリごとに持つもの**：ブランチ（detached なら短いハッシュ）、upstream、ahead/behind、変更数
  （ステージ済み／未ステージ／未追跡）、競合数、操作中（rebase／merge／cherry-pick／revert／bisect）、最終 fetch
  時刻、ファイルごとの状態（今の `GitTreeState` の中身）。
- **取り方**：`git --no-optional-locks status --porcelain=v2 --branch`（ファイルごとの状態もここから）。操作中は
  `.git` の `rebase-merge` 等の有無で見る。
- **更新の契機**：
  - 監視は各リポジトリの `HEAD`・`index`・`refs/`・`packed-refs`・操作中の印ファイル**だけ**。`.git` 全体を
    監視すると、`git status` 自身の書き込みで監視が発火し続けるループ（メモリ ui-jank-git-watcher）が再発する。
  - 作業ツリーの変化は今どおりワークスペースフォルダーの `DebouncedFolderWatcher` から受け、所属リポジトリだけ
    読み直す。
  - ポーリングは安全網として残し、**いずれかの面に見えているリポジトリ**は短い間隔、それ以外は長い間隔にする。
    git はリポジトリ単位で直列、全体の同時起動数に上限を置く（子プロセスの待ちは `ChildProcessIo`・§31.16）。
- **受け手**：エクスプローラー（`GitTreeState` の読み込みはここに置き換える）、ファイル一覧、Git パネル、
  ステータスバー、袖。**面ごとの git 起動はなくなる**（今はツリーとパネルが別々に status を起こしている）。
- 裏の fetch（§24.92）は**全リポジトリ**を対象にし、間隔はリポジトリごとに数える。認証で止まったものは
  そのリポジトリだけ止める（§24.101 の askpass は裏の fetch では聞かない、を維持）。

### §40.6.1 P2 で作ったもの（2026-11-01）

- **`GitRepositoryFileState`**（リポジトリ1つの状態）：`git --no-optional-locks status --porcelain -z -b
  --untracked-files=all` の**1回**から、ファイルごとの種別・ブランチ行（`## main...origin/main [ahead 1, behind 2]`／
  `[gone]`／`No commits yet on`／`HEAD (no branch)`）・ステージ済み／未ステージ／未追跡／競合の数を取る。上の
  「v2」案ではなく **v1 の `-b`** にしたのは、ツリーが使っていた v1 の解析（XY の写し方・リネームの旧パスの読み飛ばし）を
  そのまま持ち込めて、ブランチ行も同じ出力に乗るから。止まっている操作は git ディレクトリの印
  （`rebase-merge`／`rebase-apply`／`MERGE_HEAD`／`CHERRY_PICK_HEAD`／`REVERT_HEAD`／`BISECT_LOG`）で見る。
  `check-ignore` の一括照会もここへ移した（リポジトリごとに1回）。
- **`GitTreeState`** は「表示ルートから見た束」になった（`Compose(visibleRoot, states)`）。ファイルの状態と無視対象は
  **いちばん深い**リポジトリに問い、「配下に変更あり」は表示ルートまで集約する（境目で止めるのは P4）。以前は
  ここで `rev-parse --show-toplevel` を起こしてリポジトリを1つに決めていたので、親フォルダーの下の複数リポジトリは
  丸ごと管理外だった——**P2 で唯一見た目が変わるのはここ**で、`C:\work\{api,web}` の変更がツリーに出るようになる。
- **`GitWorkspaceStatus`**（DI シングルトン）：
  - `Load(root, fresh)`：リポジトリごとに直列。`fresh` でも、**頼んだ時刻より後に読み終えた状態**があれば読まない
    ——同じリポジトリにかかる複数の表示ルート・ツリーとファイル一覧の同時の読み込みが git 1回にまとまる。
  - `TreeStateFor(visibleRoot, fresh)`：表示ルートにかかるリポジトリ（先祖が根・配下にある）を読んで束ねる。
    ツリー（`FolderTreeQuery.LoadGitState`）はここを通す。
  - `StatusForPath`（読み込み済みだけ・git を起こさない）／`StatusesForPaths`（未読込なら読んでから、リポジトリごとに
    `check-ignore` 1回）。ファイル一覧はツリーの `GitStatusForPath`／`GitStatusesForPaths` 経由でここに届く
    （ツリーがどの表示ルートで出しているかに左右されない。ツリーを経由しない形にするのは P5）。
  - **監視**：読み込んだリポジトリの git ディレクトリ（ワークツリーなら共通ディレクトリも）を見て、`HEAD`・`index`・
    `refs/`・`packed-refs`・止まっている操作の印だけを拾う。`*.lock`・`objects/`・`logs/`・`FETCH_HEAD`・
    共通ディレクトリの `worktrees/` は捨てる（判定は純関数 `IsRelevantGitPath`）。300ms でまとめて `RepositoryChanged`
    （背景スレッド）を鳴らし、その状態を古い（`Stale`）とする。自分の status は `--no-optional-locks` なので鳴らない
    ことをテストで固定した。ツリーはこれを受けて読み直す——**ターミナルでのコミット・チェックアウト・fetch が、
    作業ツリーのファイルが変わらなくてもツリーに届く**ようになった（以前は Git パネルの対象のリポジトリで、パネルが
    監視している間だけだった）。
  - 一覧から外れたリポジトリ（部屋の切替・フォルダーの削除）は監視を止めて捨てる。
- **裏の fetch** は全リポジトリ。状態（最後の取得・失敗の回数・remote の有無）はリポジトリごとで、1 回の刻み（30 秒）で
  取得するのは**1つだけ**（開いた瞬間に一斉に走らせない）。Git パネルの対象のリポジトリを先に見て、そこはパネルと
  同じ窓口で取得する（取得後の ahead/behind がパネルへ届くように）。それ以外は `GitService.For`。
- **まだやっていないこと**（上の計画から外したもの・後段で）：ポーリングの安全網（今は Git パネルの監視
  `GitRepositoryMonitor` が対象の1つについて残っているだけ）、全体の git 同時起動数の上限（リポジトリごとの直列だけ）、
  Git パネルとの status の共有（パネルは今も自分の `GitStatusService` で読む——パネルを `For(repo)` に載せる P6 で
  まとまる）。

**実測（2026-11-01・Ryzen 5 3500）**：起動から 60 秒置いた後の 30 秒で、Loomo の CPU は平均 0.37%。その間に Loomo が
起こした git は 4 本で、すべて Git パネルの監視（`GitRepositoryMonitor` の `status --porcelain=v2 --branch` のポーリング・
従来からあるもの）。ツリーの読み込み（`status --porcelain -z -b`）は 0 本で、`.git` の監視が自分の読み込みで鳴り続ける
ループは起きていない。

**踏んだもの**：Git 管理外の表示ルートは git を起こさなくなったので一瞬で読み終わり、`await` の時点で済んでいると
続きが**同期的に**走る。すると `LoadRoot` → `RestoreAdditionalFolders` の間に単一フォルダーのツリーが組み上がり、
復元する展開状態を先に食べてしまう（本番でも起き得る順序の崩れ）。以前は `rev-parse` の数十 ms がたまたま
防いでいた。ツリーの読み込みの頭で `Task.Yield()` して、反映を必ず次の順番に回す。dispatcher の無いテストでは
続きがプールで割り込むので、該当テストは dispatcher の上で走らせる／読み終えてから次の操作をする形に直した。

## §40.7 共通の見せ部品：`RepositoryChip` と `RepositoryActions`

- **`RepositoryChip`**（View＋VM、`Loomo.App/Views/Git/`）：`⎇ main  ↑2 ↓3  12  REBASING  ⚠3` の形で、
  ブランチ名は常に、**それ以外は 0 件・該当なしなら出さず幅も取らない**（UI 密度の原則）。操作中と競合は強い色。
  文字サイズは `Fs*` トークン。ツールチップに upstream・最終 fetch・作業ツリーの根。
- **`RepositoryActions`**：印の各部を押したときの動作を1か所に。
  - ブランチ → そのリポジトリを対象にブランチ切替（`BranchSwitcherView` にリポジトリを渡す）
  - ↑↓ → そのリポジトリで fetch／pull
  - 変更数・競合 → Git パネルの該当セクションへ
  - 右クリック → fetch・pull・ログを開く・差分を開く・ターミナルでここへ（`TerminalService.IsForegroundBusy` を守る）
    ・ファイル一覧で開く
- 面ごとに作らない理由：片方だけ押せる／片方だけ fetch の対象が違う、という食い違いが必ず出る（§26.10 で
  操作の実体をツリーと共有したのと同じ理由）。

### §40.7.1 P3 で作ったもの（2026-11-01）

- `RepositoryChipViewModel`（`Services/Git/RepositoryChips.cs`）と `RepositoryChip`（`Views/Git/`）。`GitRepositoryChips`
  （DI シングルトン）がリポジトリごとに**1つ**の印を持ち、`GitWorkspaceStatus.StatusLoaded` で更新し、未読込なら裏で読む。
  `ForRootPath(path)` は「そのパスがリポジトリの根なら印」——ツリー・ファイル一覧の行に添えるかをこれで決める。
- `RepositoryActions`：fetch／pull はここで実行（Git パネルの対象のリポジトリならパネルと同じ窓口、それ以外は
  `GitService.For`）、ブランチ切替・変更の一覧・ログ・ターミナル・ファイル一覧は `Requested` で ShellWindow
  （`ShellWindow.Repositories.cs`）へ。**印を押すのはそのリポジトリを指した明示の操作**なので、ブランチ切替・変更の一覧・
  ログは Git の対象をそのリポジトリへ切り替えてから開く（§40.3 規約4 が禁じるのは暗黙の切替）。
- Git の対象（`GitRootState`）は、ワークスペースフォルダーに加えて**一覧が見つけたリポジトリの根**（入れ子）も選べる
  ようになった。親フォルダーの下の `api/` を Git パネルで開くため。
- 実行中は「…」、失敗は「✕」（ツールチップに git のエラー）を印の後ろに出す。
- **踏んだもの**：印の各部（Button の文字列）の色が全部同じ灰色になった。アプリの暗黙の `TextBlock` スタイルが、
  ContentPresenter が文字列から作る TextBlock に当たって Button の Foreground を上書きするため。各部に
  `ContentTemplate`（TextBlock の Foreground を Button へ明示的に結ぶ）を持たせた。view-render-harness の PNG で発見。

## §40.8 面ごとの見せ方

### §40.8.1 エクスプローラー（`FolderTreeView`）

```
▾ Loomo            ⎇ main  ↑2           12   ← ワークスペースフォルダー＝リポジトリ
    docs
  ▸ src                                   ●
▾ work             (Git 管理外)               ← 管理外のフォルダーは見出しを薄く
  ▸ api            ⎇ feat/auth ↓3        4   ← 入れ子のリポジトリ：フォルダー行に印
  ▸ web            ⎇ main  REBASING      ⚠
  ▸ notes
▾ AimAssist        ⎇ main                     ← 変更なし：数字は出さない
```

- **見出し行**はコンボボックスをやめ、通常の行と同じ「アイコン＋名前」＋`RepositoryChip`。
- **ピン留めフォルダーへの切替**は、見出し行のホバーで出る「▾」と右クリックの「ピン留めフォルダーへ切替」
  （既存）へ移す。表示ルートを差し替える挙動そのものは変えない。1フォルダー時のツリー上部のコンボボックスも
  同じ「▾」に揃える。
- **見出し行を出す条件**：リポジトリが 2 つ以上（入れ子を数える）か、フォルダーが 2 つ以上。どちらでもない
  （1フォルダー・1リポジトリ）ときは今の見た目のままにし、ブランチは上部の行に出す。
- **入れ子のリポジトリ**は、その根のフォルダー行にリポジトリのアイコンと印。ツリーを平らに並べ直さない。
- **集約はリポジトリの境目で止める**：中のリポジトリの変更は、外側のフォルダーへ「●（配下に変更あり）」として
  だけ伝え、M／A などの種別は伝えない。外側のリポジトリにとって中のリポジトリは自分の変更ではないため。
- **「変更のみ」（`ShowChangedOnly`）**では、変更の無いリポジトリの見出しを1行に畳む。
- Git の状態の引き方：`GitStatusFor(path, isDirectory, rootKey)` を `rootKey` ではなく
  「パス → `RepositoryFor` → そのリポジトリの状態」にする。ファイル監視はワークスペースフォルダー単位のまま。
- 後回し：スクロールしても見出しが上に残る表示（sticky header）。TreeView の仮想化との兼ね合いで手間が大きい。

### §40.8.4 Git セッションペイン

- ログのグラフは**リポジトリごとのタブ**。ファイル起点の操作（ブレーム・履歴）は、該当リポジトリのタブを
  前に出して絞り込むだけ（他のタブの状態は動かさない）。
- 全リポジトリのコミットを時刻順に並べる統合タイムラインは**この章では作らない**（§40.10）。

### §40.8.5 差分ペイン・その他

- 差分ペインの作業ツリー差分は、リポジトリごとの見出しを付けて全リポジトリぶんをまとめて出す
  （`DiffSessionQuery` をリポジトリ×変更で組む）。
- ステータスバー・袖：アクティブなファイルの所属リポジトリの `RepositoryChip`。変わるのは表示だけ。
- 不在サマリー：全リポジトリをまたいで（「AimAssist に 3 件の取り込み待ち」）。
- GitHub／Azure の PR：所属リポジトリの remote から。リポジトリが複数あれば見出しで分ける。
- ガターの比較元（`EditorGutterBaseTracker`）：ファイルの所属リポジトリの比較基準で解決する。
- ワークツリーの部屋の写し（`WorktreeRoomSeed`・`CurrentWorktree`）：「Git の対象」ではなく、操作を始めた
  リポジトリを明示して渡す。

### §40.8.6 P6 で作ったもの（2026-11-01）と、計画から変えたこと

- **リポジトリの帯**（`GitRepositoryStripViewModel`／`RepositoryStripView`）が対象フォルダーの ComboBox
  （`GitRootSwitchViewModel`・削除）を置き換えた。ワークスペースフォルダーの順に「フォルダーを含むリポジトリ（無ければ
  `○○（Git 管理外）`＝init／clone の入口）→その下の入れ子のリポジトリ（字下げ）」を印付きで並べ、項目が2つ以上のときだけ出す。
  Git パネルでは縦の一覧（選んだものに左の線）、Git ペインでは横のタブ（下の線）、ブランチ切替のポップアップでは ComboBox。
  3 つとも同じインスタンスなので、どこで選んでも全部が動く。
- **計画から変えたこと：Git パネル／Git ペインは「選んでいるリポジトリ」を1つ持ったまま**にした。上の計画（§40.8.3・
  §40.8.4）は「リポジトリごとのセクション（それぞれにコミット欄）」「タブごとに独立した状態」だったが、Git パネル（1500 行）と
  Git ペイン（1000 行）とその下の操作・照会・比較基準・ガターが**全部**同じ `GitService` の窓口を共有しているため、
  リポジトリごとに独立させるにはこの一式をリポジトリの数だけ組む作り替えが要る。代わりに「選んでいるもの」を**常に見える**
  ようにした（帯の選択・タイトルバーの `リポジトリ名 ·` ・切り替わったときの一言）。選んでいないリポジトリの様子
  （ブランチ・↑↓・変更数・操作中）は帯の印で見えるので、§40.1 の「もう一方が見えない」は解ける。
- **ファイル起点の切替は残した（見える形で）**：履歴・コミットの中のファイル・コミットへのリンクは、そのファイルのリポジトリを
  対象にしないと正しく動かない（別リポジトリへ `git log -- path` が飛ぶ）。切り替わると帯の選択が動き、帯の下に
  「○○ に切り替えました」が4秒出る（帯で自分で選んだときは出さない）。§40.11 P6 の完了条件「ブレームを開いてもパネルの
  中身が変わらない」は、この理由で「変わるが、何が起きたかが見える」に改めた。
- **踏んだもの**：ファイル起点の切替（`GitRootState.SelectForPath`）は「パスを含む**ワークスペースフォルダー**」を選んでいたので、
  親フォルダーの下の入れ子のリポジトリのファイルの履歴を開くと、対象が Git 管理外の親フォルダーになって何も引けなかった。
  一覧（カタログ）で「パスを含む**リポジトリ**」を引くようにした（`GitRootState` の `repositoryFor`）。
- タイトルバーのブランチの前に、リポジトリが2つ以上の部屋では選んでいるリポジトリの名前を出す。
- 留守中の知らせ・その日のまとめは**全リポジトリ**の reflog と変更を合わせる（以前は Git パネルの対象だけ）。
- **まだやっていないこと**：差分ペインを全リポジトリの変更でまとめる（§40.8.5）。差分ペイン（6000 行）の項目の操作（ステージ・
  取り消し・差分の取得）がすべて選んでいるリポジトリの窓口を前提にしていて、項目ごとにリポジトリを持たせて経路を付け替える
  必要がある。今は帯で選んでいるリポジトリに従う。GitHub／Azure の PR・ガターの比較基準も選んでいるリポジトリのもの。

## §40.9 永続化

> **P7 の進み具合（2026-11-01）**：`GitRootSwitchViewModel` と `GitService.AvailableRoots` は削除済み。`RootPath`／
> `SetActiveRoot` は §40.8.6 の決定（パネル／ペインは選んでいるリポジトリを1つ持つ）により「選んでいるリポジトリ」として残す。
> 保存（2026-11-02）：比較基準は `WorkspaceSnapshot.GitCompareByRepository`（作業ツリーの根 → 基準）にリポジトリごとに持ち、
> 帯でリポジトリを切り替えると今の基準を預けて次のリポジトリの基準を出す（初めて見るリポジトリは作業ツリー基準・作業ツリー
> 基準は保存しない）。旧データの `GitCompare` は今のリポジトリの分が無いときに読む（書き出しも続ける）。対象が「無し」からの
> 切替（起動時の復元のあとでフォルダーを開く）は預けずに引き継ぐ——作業ツリー基準へ戻すと復元したばかりの枝が消える
> （既存テスト「復元した枝は候補がまだ読めていなくても失われない」で発見）。選んでいたリポジトリは
> `WorkspaceSnapshot.GitRepository` に持ち、比較基準と下書きの前に戻す。コミットの下書きは、対象がリポジトリの根に
> なったことで実質リポジトリ別に保存されている（鍵の形は変えていない）。Git パネルのセクションの開閉・Git ペインのタブは
> §40.8.6 の決定で作らなかったので、保存するものも無い。

|---|---|---|
| コミットの下書き `CommitDrafts`（§24.32） | Git の対象フォルダーの絶対パス | リポジトリ識別子（作業ツリーの根）。旧データはフォルダー→所属リポジトリへ読み替え |
| 比較基準 `GitCompare` | ワークスペースに1つ | リポジトリ識別子 → 比較基準の辞書。旧データは当時の対象リポジトリのものとして読む |
| Git パネルのセクションの折りたたみ | （無い） | リポジトリ識別子 → 開閉 |
| Git セッションのタブ | （無い） | 開いていたリポジトリ識別子の列と前面のタブ |
| ファイル一覧の現在地（`Files`） | パス | 変更なし（パスはリポジトリと無関係に有効） |

識別子は作業ツリーの根の絶対パスなので、フォルダーを移動したら別物になる。読み込み時にカタログに無い鍵は
**捨てずに残し**（一時的に外したフォルダーを戻したとき用）、ワークスペース削除で一緒に消える。

## §40.10 採らないもの

- **統合タイムライン**（全リポジトリのコミットを時刻順に1本で）：グラフの線がリポジトリをまたいで意味を
  持たず、作っても読めない。「どこで何が起きたか」は不在サマリーとリポジトリ一覧で足りる。
- **リポジトリ一覧を Git セッションにも置く**：同じ表を2つ持つと片方だけ古くなる。
- **ワークスペースフォルダーの下を無制限に探す**：`C:\` を入れた人の部屋が固まる。2 段で止める。
- **リポジトリを自動でワークスペースフォルダーに昇格させる**：ワークスペースの形は人間が決める
  （フォルダーの追加は今どおり明示操作）。

## §40.13 検証の方法

- 単体テスト：カタログ（探索と所属）、集約の境目、永続化の読み替え、`FilesListing` 相当の純関数。
- 見た目：view-render-harness で `RepositoryChip`・見出し行・場所パネル・リポジトリ一覧を PNG にして比べる。
- 実機：印のクリックは **SendInput**（合成イベントやヒットテストでは押せることの確認にならない）。場所パネルは
  素の ItemsControl で UIA から行が見えないので、座標クリック＋スクリーンショット。
- 負荷：リポジトリ 10 個のワークスペースでアイドル CPU と git 起動回数を計測（P2・P6）。
- 実構成：`C:\Projects\Loomo` ＋ `C:\Projects\AimAssist`（マルチルート）と、親フォルダー1つの下に複数リポジトリ
  （入れ子）の両方で通す。
