# §28 デバッグ実行（IDEペイン）

> 作成日: 2026-07-07
> 位置づけ: `PaneKind.Debug`（§26.1 表では一行のみの記載だった）の**正本**。DAP（Debug Adapter Protocol）を
> 使ったビルド・テスト・デバッグ実行機能。実装は `src/Loomo.Core/Debug/`（モデル・純ロジック）・
> `src/Loomo.Services/Debug/`（DAPクライアント）・`src/Loomo.App/ViewModels/Debugging/*.cs`・
> `src/Loomo.App/Views/Debugging/{DebugView,DebugConfigView,DebugVariablesView,DebugBreakpointsView,
> DebugImmediateView}.xaml(.cs)` ＋ `Views/Shell/Debugging/ShellWindow.Debug.cs`（エディタ⇔デバッグの橋渡し）。

---

## §28.1 目的

「ビルド・テスト・デバッグ」という IDE的な操作を、Loomo のペインの1つとして持ち込む。VS Code 的な
DAP（Debug Adapter Protocol）連携により、Editor（`sk0ya.Editor.Controls`）のブレークポイントガター・
実行行ハイライト・DataTip（ホバー評価）と噛み合わせる。対象は **C#/.NET（`netcoredbg` アダプタ）のみ**。

---

## §28.2 アーキテクチャ（ファサード＋機能別サブVM、複数セッション対応）

`DebugViewModel`（`IDebugSession` 実装・`IDisposable`）がペインのファサードで、`Views/Shell/ShellWindow.xaml` から
`DataContext="{Binding Debug}"` で束ねられる。**同時に複数のデバッグセッション（`DebugSessionViewModel`＝
1つが1 `IDebugService`＝1 netcoredbg プロセス）を保持できる**（Rider の「実行」ツールウィンドウのタブ切替と
同じ発想。2026-07 に単一セッション制約を撤廃）：`DebugViewModel.Sessions`（起動中/停止中/終了直後の全セッション）
と `ActiveSession`（今デバッグペインに表示中の1つ）を持ち、`Inspection`/`Output`/`StatusMessage`/`IsBusy`/
`IsStopped` はどれも `ActiveSession` への **転送プロパティ**（`ActiveSession` 切替のたびに
`PropertyChanged` を再送出し、購読も張り替える）。`IDebugSessionFactory`（`Loomo.Services.Debug`、DI 登録）が
新しい未起動の `IDebugService` を作る——`NetcoredbgDebugService` はコンストラクタ引数が無い薄い実装なので、
工場はただの `new`。

「開始」「アタッチ」は必ず `DebugViewModel.CreateSession(...)` で**新しいセッション**を作る（既存セッションは
止めない）——ヘッダーの「開始」ボタンを2回押すと2本のセッションが同時に走る。「停止」「続行」「ステップ」
「一時停止」「再起動」は `ActiveSession` に対してのみ行う（複数走っていても、今見ているセッションだけを操作する）。
セッション切替 UI はヘッダーの構成コンボの隣（`Debug.Sessions`/`Debug.ActiveSession` を束ねるコンボボックスで、
2 個以上あるときだけ表示——1 個の間は今までと見た目が変わらない）。

**共有（全セッションで1個だけ、`DebugViewModel` が直接保持）とセッション固有（`DebugSessionViewModel` が保持）の
線引き**：

| サブVM/状態 | スコープ | 理由 |
|--------|------|------|
| `Launch`（`DebugLaunchViewModel`） | 共有 | 起動構成（対象・引数・例外フィルタ等）はプロファイル単位の設定であってセッション単位ではない。「開始」はここが新セッションを作る入口 |
| `Profiles`（`DebugProfilesViewModel`） | 共有 | 起動構成（プロファイル）一覧・プロジェクト選択・永続化（§28.4） |
| `Attach`（`DebugAttachViewModel`） | 共有 | プロセス列挙・フィルタは全セッション共通の入口。「アタッチ」はここが新セッションを作る |
| `Breakpoints`（`DebugBreakpointsViewModel`） | 共有 | ブレークポイントはファイル単位でグローバル（Rider 同様）。新セッション作成時に `PrimeSession` で現在値を流し込み、編集時は全実行中セッションへ fan-out する |
| `Tests`（`DebugTestsViewModel`） | 共有 | テスト実行はどのセッションにも属さない（`dotnet test` を独立プロセスで実行） |
| `Inspection`（`DebugInspectionViewModel`） | **セッション固有** | コールスタック・変数・Autos・Watch・スレッド・イミディエイト・モジュールは、その netcoredbg プロセスだけのもの |
| `Output`／`StatusMessage`／`IsBusy`／`IsStopped` | **セッション固有** | 実行中/停止中や状態文言はセッションごとに別。ヘッダーは `ActiveSession` の値を表示する |

各サブVMは狭い腰の **`IDebugSession`** インターフェース（`IsBusy`/`IsStopped`/`IsTaskRunning`/
`IsAdapterMissing`/`StatusMessage`・`BeginSession()`/`CancelSession()`・`Append`/`WriteConsole`・
`RequestOutput()`・`FindBuildTarget()`・`RaiseExecutionLine`/`RaiseFramePreview`/`RaiseFrameActivated`/
`RaiseBreakpointsRefreshed`・`SessionStateChanged` イベント）に依存する。共有サブVM（`Breakpoints`/`Tests`）は
`DebugViewModel` 自身を（マネージャ視点で——`IsBusy`/`IsStopped` は「いずれかのセッションが」の集約、
`IsTaskRunning`/`IsAdapterMissing` は本当に全セッション共有）、セッション固有の `Inspection` はその
`DebugSessionViewModel` 自身を実装として受け取る。`IsTaskRunning`（ビルド/テスト実行中の排他）は
`DebugSessionViewModel` 側でもマネージャへ委譲し、常に app 全体で1本の排他になる。

**実行行ハイライトは Phase 1 の割り切りとして「アクティブセッションの分だけ」**：エディタの実行行 API
（`VimEditorControl.SetExecutionLine`）はセッションごとの色分け等を持たないため、非アクティブで停止中の
セッションはセッション切替コンボの選択でのみ確認できる（切り替えるとそのセッションの停止位置へエディタの
ハイライトが移る）。セッションごとに別の色で同時ハイライトする拡張は `Editor.Controls` 側の変更が要る
クロスリポジトリ作業のため、別途取り組む。

`Views/Shell/Debugging/ShellWindow.Debug.cs` はエディタ⇔デバッグの橋渡し（View層、ViewModelではない）：ブレークポイントガターの
トグル・実行行ハイライト・フレームプレビュー/ジャンプ・DataTip の有効/無効・ガターグリフのマッピング
（`BreakpointGlyphInfo` → `EditorBreakpoint`）を配線する。`DebugViewModel` の5イベント（購読は起動時1回）が
今どのセッションを指すかは `ActiveSession` 切替に応じて内部で張り替わるので、View 層の配線自体は
単一セッション時代から変更していない。

DI: `DebugLaunchProfileStore` と `DebugViewModel` を `App.xaml.cs` で Singleton 登録。`IDebugService` は
DI から直接解決しない——`IDebugSessionFactory`（Singleton）だけを登録し、`DebugViewModel` がセッション開始の
たびに `Create()` で個別インスタンスを作る。

## §28.3 DAP 連携

- **アダプタ**：.NET（Core）は **`netcoredbg`**、.NET Framework は Loomo 同梱の **NetFx アダプタ**
  （§28.12）。どちらにするかは対象で決まる（`DebugAdapterResolver`）。以下は netcoredbg の説明——
  `DebugAdapterCatalog`（`Services/Debug/`）に登録された .NET（Core）用アダプタは **`netcoredbg`**
  （Samsung 製 OSS。実行ファイル `netcoredbg`、引数 `--interpreter=vscode` で stdio DAP モードへ）。
  拡張子 `.cs`。導入コマンドは `scoop install netcoredbg`。**MS 公式 `vsdbg` は VS/VS Code 外の利用がライセンスで
  禁止されているため意図的に不採用**（コードコメントに明記）。解決は LSP サーバカタログと同じ流儀で
  **PATH 検出のみ**（`ExecutableResolver.IsOnPath`）。バージョン固定・同梱バイナリは無い。
- **トランスポート**：`DapProtocolClient`（`internal sealed class`）が低レベル層。子プロセスとして起動
  （stdin/stdout/stderr リダイレクト・UTF-8 no-BOM・シェル/ウィンドウ無し）、フレーミングは **LSP と同じ
  `Content-Length: N\r\n\r\n<json>`**（DAP の JSON 本体形＝`seq`/`type: request|response|event`）を使う旨
  コードコメントに明記。`SendRequestAsync` は `seq` を採番し `TaskCompletionSource<JsonElement?>` を
  `_pending` 辞書に積み、`ReadLoop`（専用バックグラウンド `Thread`）が `response` を `request_seq` で
  マッチさせて完了させる。`event` は `EventReceived` で通知。アダプタからの**逆方向リクエスト**
  （例：`runInTerminal`）は即座に `success:true`／空ボディで応答してブロックを防ぐ。診断用に全送受信を
  `%TEMP%/loomo-dap-debug.log`（1行300文字に切詰め）へ記録する。`Dispose()` はプロセスツリーごと kill。
- **セッション状態機械**：`NetcoredbgDebugService`（`IDebugService` 実装）が実体。起動シーケンス：
  `initialize` → 応答 → `launch`/`attach` を送信（まだ待たない）→ アダプタが `initialized` イベントを
  発火 → `ConfigureAsync()`（記憶済みブレークポイントをソース単位で送信＋例外フィルタ＋`configurationDone`）
  → `configurationDone` 完了後にようやく `launch`/`attach` の応答が返る → `SetState(Running)`。
  `_requestSent` という `TaskCompletionSource` で「`launch`/`attach` を stdin へ書き終えてから
  `configurationDone` を送る」順序を保証する（netcoredbg は `configurationDone` が先に届くと15秒でタイムアウト
  する。`initialize` の await と `initialized` イベントが競合し得るための対策）。
  - `launch` 本体：`{name, type:"coreclr", request:"launch", program, args, cwd, env, stopAtEntry, justMyCode,
    console:"internalConsole"}`。**`console` は常に `internalConsole`**（外部コンソール窓は無い）。
  - `attach` 本体：`{name, type:"coreclr", request:"attach", processId, justMyCode:false}`——**アタッチ時は
    `justMyCode` が常に false に固定**（起動時のチェックボックスは launch にのみ効く）。
  - Capability ネゴシエーション：`initialize` 応答の `supportsSetVariable`/`supportsGotoTargetsRequest`/
    `supportsStepInTargetsRequest`/`exceptionBreakpointFilters` を読み、`IDebugService.SupportsSetVariable`/
    `SupportsSetNextStatement`/`SupportsStepInTargets`/`ExceptionFilters` として公開（機能の出し分けに使う）。
  - `setBreakpoints`/`setExceptionBreakpoints`/`continue`/`next`/`stepIn`/`stepOut`/`pause`/`stackTrace`/
    `scopes`/`variables`/`evaluate`（`context: watch` と `repl` を使い分け）/`threads`/`setVariable`/
    `gotoTargets`/`goto`/`modules`/`stepInTargets` は型付き DAP SDK を使わず、生の `JsonElement` で手組み。
  - 停止：`disconnect` を送信（`terminateDebuggee = !_attached`＝launch は対象を道連れに終了、attach は
    対象プロセスを生かしたまま切り離す）、2秒タイムアウト、常にクライアントを破棄する。

## §28.4 起動構成（プロファイル）

`3a56aa8`（2026-07-07）で追加。

- **モデル** `DebugLaunchProfile`（`Core/Debug/`）：不変 `record`——`Id, Name, ProjectPath（相対・null=自動検出）,
  TargetProgram, BuildFirst, LaunchArgs, LaunchEnv, JustMyCode, BreakOnAllExceptions, BreakOnUncaughtExceptions`。
- **永続化** `DebugLaunchProfileStore`：`%APPDATA%/Loomo/launchProfiles.json` に **全ワークスペース分を1ファイル**
  （`WorkspaceEntry(RootPath, Profiles, SelectedProfileId)` の配列）で保存。ワークスペースごとに独立した
  プロファイル集合を持つ。壊れたファイルは黙って空扱い。
- **プロジェクト発見** `DebugProjectDiscovery`（静的・UI非依存）：`.sln` があれば正規表現で `Project(...)` 行を
  パースしパス実在チェック、無ければ深さ制限（4）付き再帰スキャン（`bin/obj/.git/node_modules/.vs` 等を除外）。
  `.csproj` は軽量パース（`XDocument`）でテストプロジェクト（`<IsTestProject>true</IsTestProject>` または
  `Microsoft.NET.Test.Sdk` 参照）を判別し起動候補から除外する。先頭には常に **番人エントリ `(自動検出)`**
  （空パス）を置く——WPF `ComboBox.SelectedItem` は `null` を「未選択」（空欄表示）として扱うため、`null` の
  代わりに実体オブジェクトの番人が必要という理由がコメントに明記されている。
- **仲介** `DebugProfilesViewModel`：`IWorkspaceService.RootChanged` で `ReloadForWorkspace()`
  （再発見＋ストア読込。無ければ `"既定"` を1件 seed）。`AttachLaunch(launch)`（`DebugViewModel` 構築直後に
  1回呼ぶ）が `Launch.PropertyChanged` を購読し、選択中プロファイルの値を `Launch` の各バインド可能プロパティへ
  即時反映する。プロファイル切替は `_applying` フラグで書き戻しループを防止。監視対象プロパティ
  （`WatchedLaunchProperties`）の編集や `SelectedProject` 変更は **400ms デバウンス**（`DispatcherTimer`）の後、
  現在値を選択中プロファイルへ `with { ... }` で書き戻して永続化する。
  `SelectedProjectPath` は `(自動検出)` 選択時は `null`、それ以外は選択 `.csproj` の絶対パスとなり、
  `DebugTargetResolver.ResolveProgramAsync` の `explicitProjectPath` へ流れる（`StartAsync` の対象解決にのみ影響。
  ヘッダーの「🔨 ビルド」ボタン＝`BuildTarget` は `FindBuildTarget` を使い続けるため、プロファイルの
  プロジェクト選択には影響されない）。
- **UI**：**ヘッダーの ComboBox**（`Views/Shell/ShellWindow.xaml`、幅150・`DisplayMemberPath=Name`）は**切替専用**。
  追加/名前変更/削除・プロジェクト選択は「構成」タブ（`DebugConfigView`）側に限定する
  （XAML コメント「編集…は『構成』タブ側」）。削除は最後の1件では不可（`CanDeleteSelectedProfile`）。

## §28.5 UI 構成（2026-07 再編後）

`DebugView.xaml` 自身のコメントが要約：*「ヘッダ（IDEラベル・状態・デバッグツールバー）はホスト
（ペインヘッダ）側が出す。日常の起動は『実行』タブ、停止中の変数・スレッド等は『デバッグ』タブ、
詳細設定は『構成』タブにまとめる。」*

**ペインヘッダー**（`Views/Shell/ShellWindow.xaml` の `DebugPane`、左→右）：
1. `IDE` ラベル
2. **起動構成 ComboBox**（§28.4）
3. ステータステキスト（`Debug.StatusMessage`、省略記号つき、残り幅を占有）
4. **デバッグツールバー**（`IsBusy`/`IsStopped` で排他表示の3系統）
   - 非実行時：`▶ 開始` / `🔨 ビルド` / `🧪 テスト` / 「先にビルド」チェックボックス
   - 停止中：`▶` 続行(F5) / `⤼` ステップオーバー / `⤷` ステップイン / `⤴` ステップアウト
   - 実行中：`⏸` 一時停止 / `⟳` 再起動 / `■` 停止
5. ペイン非表示ボタン（`—`）

**ペイン本体**＝`DebugView`（横スクロール対応タブ、フラット下線スタイル）。外側のタブは
**実行／問題／デバッグ／テスト／構成**。実行タブはプロジェクト一覧（クリック／Enter／ダブルクリック／▶）と
直近の出力を左右に表示する。プロジェクト一覧は見出し右端のトグルで折りたため、閉じた状態では
「プロジェクト」の縦書きレールだけを残し、再展開時は直前の幅へ戻す（`DebugView` 内で保持、設定には保存しない）。
変数／自動／コールスタック／スレッド／ブレークポイント／イミディエイト／
モジュールは「デバッグ」タブ内の検査タブへまとめる（`DebugView.xaml.cs` の `InspectionTabs`）。
自動タブ切替は `IsStopped` になったら **デバッグ＞変数**、再開・終了したら **実行**。`OutputRequested`
（開始/ビルド/テスト/アタッチを押した瞬間に発火。`IsBusy` の反映より早い）でも即座に実行タブへ移る。
テストタブ選択で `Tests.EnsureTestsDiscovered()`。

**「構成」タブ**（`DebugConfigView`）：アダプタ未導入時の導入バー／起動構成セクション（プロファイル
＋/名前変更/削除ボタン・起動プロジェクト ComboBox・対象 `.dll`/`.exe` テキストボックス・起動引数・
環境変数の複数行テキストボックス、**`IsBusy` 中は非表示**）／例外・オプションセクション（「すべての例外」
「未処理の例外」「マイ コードのみ」チェックボックス、常時表示）／アタッチセクション（トグルボタン＋
フィルタ可能なプロセス一覧、**`IsBusy` 中は非表示**）。

**タイトルバートグル**：`DebugPaneToggle`（バーアイコン、ツールチップ「IDE（ビルド・テスト・デバッグ）」）。
`Visibility` はプログラムから制御される（§28.6）。

## §28.6 ワークスペース適用性（C#プロジェクトの無いワークスペースでは非表示）

`59454f9`（2026-07-01）。`DebugTargetResolver.HasCSharpProject(root)` がトップレベル `.sln` 優先、無ければ
深さ制限（3）付き再帰 `.csproj` スキャン（`bin/obj/.git/node_modules/.vs` 等を除外）で判定する
——**無制限 `AllDirectories` を使わない**のは、この判定が初回フレーム描画前に同期実行され、`node_modules` 等
巨大な非C#ワークスペースで起動をブロックしてはならないため。

`ShellWindow._idePaneApplicable`（既定 `true`）＋`ApplyIdePaneApplicability(root)` が `HasCSharpProject` の
結果で `DebugPaneToggle.Visibility` を切替える。**適用外なら以下4箇所すべてから `PaneKind.Debug` を除外**する
（どの経路からも IDE ペインが出てこないように）：
1. タイトルバートグル（上記）。
2. `LoadEnabledSessions` が `_enabledSessions` から `Debug` を除去（保存済みセッション状態からの復活も防ぐ）。
3. `PrepareStageSnapshot`（Stage.cs）が `PaneKind.Debug` を指すソロ/ズーム舞台の復元を拒否し `Editor` へ
   フォールバック。
4. `PaneLayout.cs` の保存済みレイアウト復元が、残存する `Debug` タイルを強制的に `Hidden=true` にする
   （古い保存レイアウトが参照していても）。

判定はワークスペースロード時（`Views/Shell/Workspace/ShellWindow.Workspaces.cs`、`LoadEnabledSessions`/`PrepareStageSnapshot`/
レイアウト復元より**前**）と、ワークスペース無し（`root: null`）分岐の両方で行う。

## §28.7 セッション再利用の安全策（間欠的起動失敗の修正、`9663f79` 2026-07-07）

**バグ1：前セッションのアダプタがファイルハンドルを保持したまま**——デバッグ対象が自然終了すると
`NetcoredbgDebugService.Finish()` が `Exited` を発火するが、**アダプタ本体（netcoredbg）は生き続け**、対象
`.dll`/`.pdb` を開いたままになる。従来テアダウン（`TearDownAdapterAsync`）は fire-and-forget だったため、
直後に「開始」を押すと古いアダプタがDLLをロックしたままリビルドが始まり "ファイル使用中" で失敗し得た。
→ テアダウンタスクを `_teardownTask` に保持し、新設の `IDebugService.WaitForIdleAsync()` がそれを待つ
（既に完了/null なら no-op）。`DebugLaunchViewModel.StartAsync`/`BuildTarget` は対象解決・ビルドの**前**に
これを await するようになった。

**バグ2：明示ターゲット時に「先にビルド」が無視される**——`DebugTargetResolver.ResolveProgramAsync` は
`TargetProgram`（`.dll`/`.exe` パス）が明示されていると、`BuildFirst` が真でもビルドせず `File.Exists` だけ
見ていた。→ `FindProjectNear(programPath)`（対象パスから最大6階層親を遡り `.csproj` を探索）を追加し、
`BuildFirst` が真ならそのプロジェクト（またはプロファイルの明示プロジェクト `explicitProjectPath`）を
`File.Exists` 判定の**前**にビルドするようにした。プロジェクトを推測できない場合はビルドを黙ってスキップ
（従来の存在確認のみへフォールバック）。

## §28.8 実装済み機能（要点）

条件付きブレークポイント／ログポイント（`BreakpointViewModel.Condition`/`HitCondition`/`LogMessage`、

（停止中のみ有効化）・Watch（停止/フレーム変更ごとに再評価）・ビルド統合（`dotnet build "<target>" -c Debug
--nologo`、対象は `.sln` 優先／なければ最初の `.csproj`）・テスト統合（`dotnet test`＋TRXパース、DAPセッション
とは独立、ファイル監視による再発見）・**エディタのガターのテスト実行▶／結果グリフ**（§28.10）。

## §28.9 既知の制約（意図的に対応していないもの）

- **アダプタは netcoredbg（`coreclr`）と同梱の NetFx アダプタ（`clr`、§28.12）の2本**。他言語/ランタイムは
  配線されていない（TypeScript は §29 の js-debug）。
- **`vsdbg` 非対応**（ライセンス上の理由）。同梱バイナリも無く、PATH 検出のみ・バージョン確認も無い。
- **`console` は常に `internalConsole`**——対象の外部コンソール窓／統合ターミナル起動モードは無い。
- **アタッチ時は `justMyCode` が常に false**（チェックボックスは launch のみに効く）。
- **Autos はヒューリスティック**（netcoredbg ネイティブのスコープではない）。
- **プロセスアタッチの `.NET` 判定はベストエフォート**（権限/ビット不一致で調べられないプロセスは
  非マネージド扱いになる）。
- **ブレークポイントの条件式/ヒット条件/ログメッセージはクライアント側で検証しない**（そのまま netcoredbg へ
  送るだけ）。
- **テスト実行/ビルドは常に別CLIプロセス**（`dotnet test`/`dotnet build`）——DAPセッションを介した
  「テストをデバッグする」（実行中テストへのアタッチ）統合は無い。
- **起動構成が持つのは `DebugLaunchViewModel` が既に公開しているフィールドのみ**（対象・先にビルド・引数・
  環境変数・マイコードのみ・例外2種・プロジェクトパス）。作業ディレクトリの上書き・複合起動（compound
  launch＝複数の起動構成を1操作でまとめて始める機能）・pre/post タスク（VS Code の `tasks.json` 相当）は無い。
- **プロジェクト発見ロジックが3箇所に重複**（`HasCSharpProject` 深さ3・`FindProject` の無制限
  `AllDirectories` フォールバック・`DebugProjectDiscovery.CollectCsproj` 深さ4）——機能上のバグではないが
  保守上の注意点。

## §28.10 エディタのガターのテスト実行 ▶ ／結果（2026-08）

テストソースを開くと、**テストメソッドの行のガターに ▶ が出て、押すとそのテストだけが走り、結果
（成功／失敗／スキップ）がグリフとして同じ場所に残る**。ツールチップに所要時間と失敗メッセージを出す。
TypeScript 側（vitest / jest）も同じ動線で動く（§29）。

### 責務の分け方

エディタ側（`sk0ya.Editor.Controls` 1.0.79）が持つのは**列の描画とクリックの通知**だけ：
`SetTestGlyphsEnabled(bool)` / `SetTestGlyphs(IReadOnlyList<EditorTestGlyph>)` / `TestGlyphClicked(int line0)`。
**テストの正本はテストエクスプローラの VM**（dotnet=`DebugTestsViewModel` / TS=`TsDebugTestsViewModel`）で、
エディタは表示するだけ——ブレークポイント列（§28 のガター）とまったく同じ流儀。既存のテスト探索・
実行器（`TestDiscoveryService` / `DotnetTestRunner` / `TsTestRunner`）を再利用し、**新しい探索も実行器も作っていない**。

- `ITestExplorer`（`TestItems` / `TestsChanged` / `RunTestAsync`）が両 VM の共通の窓口。ファイルの管轄は
  デバッグの `ManagerForPath` と同じ拡張子表（`.ts/.js` 系→TS IDE、それ以外→dotnet）。
- `Services/Editor/Support/EditorTestGlyphMap.cs` が「テスト項目 → グリフ一覧」の純ロジック（WPF 非依存・単体テスト済み）。
  **行の基準が変わるのはここ 1 箇所だけ**（テスト側は 1 始まり、エディタのバッファ行は 0 始まり）。
- `Views/Shell/Debugging/ShellWindow.TestGlyphs.cs` が配線。

### 宣言位置は「失敗位置」と別枠

▶ を置くのは**メソッドの宣言行**。`TestItemViewModel.SourcePath`/`Line` は実行結果（TRX のスタックトレース）
由来の**失敗位置**で、ヘルパの行を指すことがあり成功時は空なので、置き場所には使えない。そこで
`DiscoveredTest(SourcePath, Line1)` と `TestItemViewModel.DeclarationPath`/`DeclarationLine` を**別に**持ち、
探索のたびに前者だけを更新する（後者＝ジャンプ先の意味は変えていない）。

### 再送の契機（ここが壊れやすい）

エディタ側のグリフは**全置換**で、`LoadFile` で捨てられ、行の挿入・削除には追従しない。しかも
`VimEditorControl.LoadFile` は **`BufferChanged` を発火しない**。したがって送り直す契機は 3 つ：

1. `TestsChanged`（走査の再収集・実行の開始と完了）。実行の後始末は `finally` に置く——例外・中断で
   飛ばすと「実行中」の塗りのまま固まる。
2. `BufferChanged`（編集）。Dispatcher の Background 優先度で 1 フレームぶんにまとめる。
3. **`ShellWindow.LoadEditorFile`**（Loomo 側の `LoadFile` の唯一の漏斗）とセッション復元。これを落とすと
   外部変更の読み直し（ブランチ切替・一括置換・既存タブの開き直し）と**切り離しウィンドウの初回表示**で
   ガターが空のまま残る。`control.LoadFile` を直に呼ぶ経路を増やさないこと。

### 列の出し入れ

テストソースでないファイルでは列を無効化する（列幅 0＝本文左端を動かさない）。ただし**いったんテストが
見つかったファイルでは 0 件になっても畳まない**（`EditorTestGlyphColumns`）——保存契機の再走査で編集途中の
ソースが一時的に 0 件になるたび列が開閉し、本文が左右に動くため。

### キーボード導線

▶ は**マウス専用**なので、`editor.test.runAtCaret`「カーソル行のテストを実行」をコマンドカタログへ登録
（既定キーは未割当・設定画面から割り当て可）。キャレット行に宣言が無ければ上方向へ
`EditorTestGlyphMap.MaxCaretLookback` 行まで遡って「今いるテスト」を選ぶ。対象が無いとき・実行を始められない
とき（ビルド中／デバッグ中）はトーストで理由を返す——押せるのに何も起きない状態を作らない。

### 既知の制約

- テスト探索は行ベースのベストエフォート（`TestSourceParser`）。入れ子クラスの完全名は崩れ、同名
  オーバーロードと別ファイルの同一完全名は重複排除で最初の 1 つにしかグリフが出ない。
- 行の追従は再走査（`TestSourceWatcher` は保存契機）まで。編集直後はグリフの行がずれて見える。
- TS 側の位置は探索由来のみ（結果 JSON からは位置を取らない）。

## §28.11 タイトルバーのデバッグメニュー（実行ターゲット・2026-09-21）

**目的**: C# の部屋では「何をどう実行するか」を、IDE ペインを出していなくてもタイトルバーから決めて
始められるようにする。ブランチ切替（§21.6）と同じ「現在値をボタンに出し、押すとポップアップ」の作り。

- **ボタン**（`Views/Shell/ShellWindow.xaml` の `DebugButton` / AutomationId `TitleBarDebugButton`）はブランチ切替の
  右隣。出し入れは IDE ペインの適用性と同じ判定で、`ApplyIdePaneApplicability` が
  `UpdateDebugButtonVisibility()` を呼ぶ（§28.6 と同じ `HasCSharpProject`。C# の無い部屋には出ない）。
  ラベルは**構成名ではなく解決後の対象**（`DebugProfilesViewModel.SelectedTargetLabel`＝
  `プロジェクト` または `プロジェクト: launchSettings名`、対象が自動検出なら構成名）——「既定」のような
  構成名だけでは押す前に何が動くか分からないため。デバッグ中は右に ● （Accent）を出す（状態の文字は
  ポップアップの中。袖のバッジ＝§24.1 と同じく、目の端で気づくためだけの印）。
- **中身**は `DebugSwitcherView`（DataContext は `DebugViewModel`＝IDE ペインと同じインスタンス。
  どちらで変えても同じ状態）。開閉は `Views/Shell/Debugging/ShellWindow.DebugSwitcher.cs`、再オープンガードは
  `Views/Shell/Layout/ShellWindow.Popups.cs`（ブランチ／ワークスペース切替と共用）。
  - 上の**固定帯**＝いま選んでいる対象に効く操作：`▶ 実行`（デバッグなし）/ `🐞 デバッグ` / `🔨 ビルド` /
    `🧪 テスト` / 「先にビルド」、停止中はステップ、実行中は中断・再起動・停止、最後に状態テキスト。
    netcoredbg 未導入のときは理由と「インストール」を帯の上に出す。
  - 下の**実行ターゲット一覧**（`DebugRunTargetItem`）＝**1 行＝そのまま実行できる 1 つの対象**。
    行の右の ▶／🐞 でその行を実行・デバッグできる（選んでから別の場所の「開始」を押す往復が要らない）。
  - フッターは「構成を編集…（IDE ペインの『構成』タブ）」＝`ShowIdePane()`。**開始しただけでは部屋を
    組み替えない**（勝手なレイアウト変更をしない。実行中であることは袖のバッジで分かる）。

### 3つの並列な一覧をやめた理由（Rider の実行構成ウィジェットに寄せた）

最初の実装は「構成」「起動プロジェクト」「launchSettings」を**そのまま3つの一覧**として並べていた。
どれを選べば何が動くのかが行だけからは読めず（答えは3つの掛け合わせ）、選んだ後に帯の「開始」へ戻る
必要もあった。`DebugRunTargetItem` はこれを 1 本に畳む：

| 行 | 印 | クリック | 右の ▶／🐞 |
|----|----|----------|------------|
| 保存した構成 | ⚙ | その構成に切替 | 構成の対象を実行／デバッグ |
| プロジェクト | ▸ | 現在の構成の対象を差し替え | そのプロジェクトを実行／デバッグ |
| launchSettings プロファイル | ⚑（字下げ） | 対象＋プロファイルを差し替え | それで実行／デバッグ |

`RefreshRunTargets()` はメニューを開く直前に一覧を作り直し、**候補すべての** `launchSettings.json` を
その場で読む（`ReloadLaunchSettingsProfiles` は選択中プロジェクトのぶんしか読まない）。見出しは
グループ先頭行にだけ出す（`GroupLabel`）ので、一覧は 1 本・スクロールも 1 本のまま。

**デバッグなしの実行**（▶）は可視ターミナルで `dotnet run` を走らせるホスト側の仕事なので、ビューは
`RunRequested` でウィンドウへ投げ、`ShellWindow.ExecuteCSharpTargetAsync` を通す——Solution Explorer の
「実行」と**同じ経路**（launchSettings／IIS Express／TFM／構成の扱いが片方だけ直るのを避ける）。

## §28.12 .NET Framework／旧形式（非SDK）プロジェクトのビルドとデバッグ（2026-09-27）

`<Project ToolsVersion=…>` で始まる旧形式の csproj（.NET Framework 4.x）は、`dotnet build` では通らないものが
多い——`packages.config` は `dotnet restore` が復元しない、`COMReference` を解決できない、`$(VSToolsPath)` 経由で
Visual Studio にしか無い targets（旧 ASP.NET の WebApplication.targets 等）を import している。そして
**netcoredbg／vsdbg はどちらも CoreCLR 専用**で、ビルドが通っても .NET Framework のプロセスはデバッグできない。

### ビルド・実行・評価は Visual Studio の MSBuild.exe へ

- 判定は `MsBuildToolchain`（`Loomo.CSharp/Build/`）の**一箇所**：ルートの `Sdk` 属性・`<Sdk>`・`Sdk` 付き
  `<Import>` のどれも無く、素の `<Import>` がある csproj が旧形式。.sln／.slnx は中身のプロジェクトを見て、
  1つでも旧形式があれば全体を MSBuild.exe で回す（SDK 形式も MSBuild.exe で通る）。
- MSBuild.exe は Visual Studio インストーラーの `_Instances\*\state.json`（vswhere と同じ情報源。子プロセス不要）
  から探し、無ければ vswhere。`LOOMO_MSBUILD` で上書きできる。Loomo が使う `-getProperty`／`-getItem` は
  MSBuild 17.8 からなので、それより古い MSBuild.exe は使わない。**見つからなければ従来どおり dotnet へ落とす**
  （単純な旧形式なら通るので、何もしないより悪くならない。落ちたとき理由が分かるよう一言出す）。
- ビルド（`CSharpBuildService`）：`-restore -p:RestorePackagesConfig=true` で packages.config も同じ1回で復元する
  （NuGet.exe を別に要らない）。**プロジェクト単体のビルドには `SolutionDir` を渡す**——packages.config の
  復元先と `..\packages\…` の HintPath はソリューションのフォルダーが前提で、渡さないと NuGet が
  「ソリューションが見つかりません」で落ちる（Visual Studio もプロジェクト単体のビルドで渡している）。
  末尾は `/`：`\` で終えると Windows PowerShell 5.1 のネイティブ引数の引用で `\"` になり閉じ引用符が消える。
- `TargetPath` の問い合わせ（実行・デバッグ対象の解決・評価）にも**ビルドと同じ `SolutionDir` を渡す**——
  `OutputPath` が `$(SolutionDir)bin\…` のプロジェクトで、ビルドした場所と問い合わせの答えが食い違わないように。
- 実行（`CSharpRunService`）：`dotnet run` が使えないので、ビルド後に `-getProperty:TargetPath` で出力先を
  MSBuild 自身に聞いて起動する（AssemblyName・OutputPath・プラットフォーム別出力を推測しない）。
- プロジェクト評価（`MsBuildProjectEvaluator`／テスト対象解決）も同じ `MsBuildToolchain.For` で選ぶ。
  旧形式に TFM の切り替えは無いので、モデル上の TFM 名（`(既定)`）はコマンドへ渡さない。

### デバッグは同梱の NetFx アダプタ（`src/Loomo.NetFxDebug`）

- **ICorDebug を直接使う自前の DAP アダプタ**（ClrDebug ラッパー、MIT）。netcoredbg と同じ DAP を stdio で話すので、
  Loomo 側は `NetcoredbgDebugService` のまま**相手の実行ファイルが違うだけ**。net48 なのは、ICorDebug を
  「デバッガ自身が載っている CLR」から取るのが素直で、.NET Framework 4.x は Windows に必ずあるから。
- **ICorDebug はデバッガと対象のビット数が一致しないと繋がらない**。旧形式の exe は既定で `Prefer32Bit=true`
  （AnyCPU でも 32bit で動く）なので、同じソースを 32bit でもビルドし（`Build32/Loomo.NetFxDebug.Build32.csproj`。フォルダー名を `x86` にすると `.gitignore` の `x86/` に吸われる）、
  App の出力 `netfxdbg\` に2本並べる。選び分けは `ManagedProgramInspector`（PE と CLI フラグ＝corflags と同じ規則、
  `*.runtimeconfig.json` が隣にある exe は .NET（Core）の apphost）。アタッチは対象プロセスのモジュール
  （`clr.dll`／`coreclr.dll`、WOW64 側も見る）で決める。
- シンボルは**ポータブル PDB（System.Reflection.Metadata）と Windows PDB（.NET Framework 同梱の
  diasymreader）の両方**を読む。旧形式の既定 `DebugType=full` は Windows PDB で、ビルド時に portable へ
  上書きしても CoreCompile が最新扱いで走らず PDB が変わらないため、読む側で両方に対応した。
- 対応：ブレークポイント（条件・ヒット回数・ログポイント、ラムダと同居する行は行の左端の文へ）、ステップ
  （JMC＝シンボルのあるモジュールだけがマイコード、隠し区間は自動で読み飛ばす）、例外ブレーク（all／
  user-unhandled）、一時停止、スレッド、スタック（async／ラムダ名は書いたコードの名前へ寄せる）、ローカル
  （クロージャ・async/iterator の状態機械に持ち上げた変数は元の名前で平らに並べる）、式評価（C# のサブセット、
  プロパティ・メソッド呼び出しは関数評価）、値の書き換え、次のステートメントの設定、モジュール、アタッチ／デタッチ。
- **値の寿命**：対象を 1 度でも走らせると（関数評価も含む）フレームと値のオブジェクトは無効になる。値は
  「どこから辿ったか」（`ValueSource`）で持ち、世代が変わったら辿り直す。ヒープのオブジェクトは強いハンドルで
  押さえて辿り直しを省く。
- **スレッドの約束**：ICorDebug を触るのはロックを握ったときだけ。条件付きブレークポイントの条件は関数評価を
  伴いうるので、コールバックスレッドでは評価しない（評価の完了もそのスレッドに届くので自分を待つことになる）。
  止めたままワーカーへ渡し、偽なら黙って続行する。
- Loomo が `disconnect` を送らずに閉じた（落ちた）ときは、launch した対象は終わらせ、**アタッチした対象は切り離すだけ**。
  IIS Express のように起動直後にアタッチする対象は、ランタイムが読み込まれるまで少し待ってからアダプタを選ぶ。
- **アダプタ自身の標準入出力を子へ継承させない**：継承させると、デバッグ対象が Loomo とのパイプを握り、
  アダプタが終わってもパイプが閉じない（js-debug の node 残留と同じ罠）。対象の出力は専用パイプで受け、
  **1 行ずつ** output イベントにする（Loomo はイベント 1 つを 1 行として表示する）。

### まだ無いもの

- 旧形式のテストプロジェクト（MSTest v1／`packages.config` の NUnit 等）の実行・探索は `dotnet test` のまま
  （vstest.console.exe 経路は無い）。
- 旧 ASP.NET（System.Web）を IIS Express で動かす起動構成は無い（アタッチなら NetFx アダプタが選ばれる）。
- エディットコンティニュー、DebuggerTypeProxy（List／Dictionary は専用の展開で代替）、混在モード（ネイティブ）
  デバッグ、.NET Framework 2.0/3.5（CLR v2）での実機確認。

## §28.13 停止中の行末の値（Inline Values・2026-10-03）

デバッグで止まっている間、**関数の先頭〜停止行**の各行の末尾に、その行に出てくる変数の値を薄く出す
（`var x = Foo(a);   x = 3, a = "abc"`。VS Code の Debug Inline Values）。設定はエディタ設定の
「デバッグ中に変数の値を行末に表示する」（`EditorSettings.ShowDebugInlineValues`、既定 ON）。

- **値の出どころは変数ツリーと同じ** scopes→variables（`DebugInspectionViewModel.LoadInlineValuesAsync`）。
  式評価（`evaluate`）はしない——副作用が無く、netcoredbg／同梱 NetFx／js-debug のどれでも同じ経路で動くため
  （C# と TS で共通）。重いスコープ（`expensive`）と JS の Global/Script は読まない。内側のスコープの名前が
  外側の同名を隠す（先に来たものを採る）。LSP の `textDocument/inlineValue` は使っていない。
- **範囲と突き合わせは純ロジック**（`Core/Debug/DebugInlineValues.cs`、単体テスト済み）：停止行から上へ波括弧の
  対応を数えて囲む `{` を探し、見出しが if/for/try/初期化子なら外側へ、メソッド・ローカル関数・ラムダ・
  `function` ならそこを先頭とする（コメント・文字列の中の括弧は数えない、遡りは 300 行まで）。ステップインで
  開き `{` の行に止まったときはその関数。各行の識別子（メンバアクセス `obj.x` の `x` は除く）を変数名と突き合わせ、
  行内の出現順・重複なしで `名前 = 値` を並べる（値は 1 行化して 60 字、行は 150 字で切る）。停止行より下には出さない。
- **無効化**：続行・ステップ・終了で `Inspection.Clear()` が空の一揃いを送る（世代が変わった取得結果は捨てる）。
  フレームを切り替えるとそのフレームで作り直す（§31.6 の「表示と評価のフレームを揃える」）。停止中にソースを
  編集したエディタは、行がずれて別の行の値に見えるので、次の停止までそのエディタだけ消す。
- **経路**：`IDebugSession.RaiseInlineValues` → `DebugSessionViewModel.InlineValuesChanged` →（アクティブ
  セッションだけ）`DebugManagerViewModelBase.InlineValuesChanged` → `DebugEditorController`。コントローラは
  マネージャごとの最新の一揃いを持ち、`WireEditor` と `AfterEditorFileLoaded`（停止と同時に開いたタブ・
  `LoadFile` は値を捨てる）で出し直す。セッション切替では切替先の値（無ければ空）を出す。
- **描画**は `VimEditorControl.SetInlineValues`（`sk0ya.Editor.Controls` 1.0.95〜）。それより古いピンでは収集・
  無効化までで描画しない（`Loomo.App.csproj` の `EditorHasInlineValues` → `LOOMO_EDITOR_INLINE_VALUES`）。
  ピンを上げれば自動で描画が入る。

既知の制約：見出しの判定は行ベースの推定（複数行にまたがるシグネチャは `{` の直前の行を見出しとする）。
切り離しウィンドウのエディタには出ない。値の行は編集に追従しない（消すだけ）。
