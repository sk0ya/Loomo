## §37.1 目的と、部屋の中での位置

人間は Loomo の**可視ターミナル**で Claude Code などの既存エージェントを走らせて開発している。その開発は
`CLAUDE.md`・Skills・Hooks・サブエージェント定義といった**ハーネス**の上で回っているのに、ハーネスのどこが
非効率で、直したら良くなったのかを確かめる場所が部屋に無かった。§20 のトレースは Loomo 内蔵エージェントの
記録で、外のエージェントは見えない。

ハーネスペインは**ハーネスの記録を見て、改善箇所探しをエージェントに渡し、変更前後を比べるための道具**である（構想§1）。
タスクボードでも監視ダッシュボードでもない（構想§7.1）。主役はあくまで人間で、このペインはエージェントを
動かさない——**人間がハーネスを直すための作業台**として部屋に置く（§24「道具としての進化」）。

| 物差し（§24） | このペインでの意味 |
|---|---|
| 周辺視野 | 下の帯（ステータスバー）に Run 数・受け入れ1件あたりトークン・ツール失敗率が常に出ている |
| 素材の流れ | ツール呼び出しから**記録（transcript）の該当行**を、構成タブから**ハーネスの定義ファイル**（ユーザー全体の `~/.claude` も）をエディタで開ける。分析プロンプトをコピーして可視ターミナルの Claude Code へ渡す |
| 復元 | 選んでいたタブ・期間・絞り込みはワークスペースごとに戻る（§37.7） |

## §37.2 データの出どころ（観測事実と推測を分ける）

構想§2-4「観測事実と推測を分ける」をデータの出どころで担保する。画面に出す値は必ずどれかに属し、
**推定値には必ず「推定」と書く**。

| 出どころ | 何が分かるか | 種別 |
|---|---|---|
| `.harness/`（ワークスペース各フォルダー直下） | ハーネスの宣言（ID・版・タスク・ワークフロー・ルール・評価） | 定義（正本） |
| `CLAUDE.md` / `AGENTS.md` / `.mcp.json` / `.claude/{CLAUDE.md,settings*.json,skills,agents,commands}/`、同じ形のユーザー全体の `~/.claude/` | Claude Code が読む構成要素 | 定義（**設定されている**こと） |
| `~/.claude/projects/<slug>/<session>.jsonl`（＋ `<session>/subagents/*.jsonl`） | 実際のツール呼び出し・結果の大きさ・失敗・トークン使用量 | 観測（**実際に起きた**こと） |
| `git log -- .harness CLAUDE.md AGENTS.md .claude` | Run 開始時点のハーネスの版 | 観測 |
| `.harness/runs/verdicts.json` | 人間が下した受け入れ／差し戻し | 判定 |

「設定されている」と「実際に使われた」は別に出す（構想§7.2）。構成タブの各要素は、Skill／サブエージェントなら
観測期間内に何回呼ばれたか（`Skill` ツールの `skill`、`Agent`/`Task` ツールの `subagent_type`）を併記し、
呼ばれていなければ「観測なし」と書く。CLAUDE.md は毎回読まれる前提なので回数は出さない。

### §37.2.1 Claude Code の記録の読み方（実測で確かめた形）

- 1行1 JSON。`type` が `user` / `assistant` / `system` / `attachment` / `ai-title` / `cost-state` などに分かれる。
- **assistant は content ブロックごとに別の行になり、同じ `message.id` の行が `usage` を重複して持つ。**
  そのまま足すとトークンが数倍に化ける（手元の1セッションで最大6重）。`message.id` ごとに最後の `usage` だけを採る。
- `tool_use`（assistant 側）と `tool_result`（user 側）は `tool_use_id` で対応づける。結果の `is_error` が失敗。
  ただし `The user doesn't want to proceed…` は**人間が拒否した**のであって失敗ではない（失敗率に入れない）。
- 大きすぎる結果は本文の代わりに `<persisted-output>Output too large (40.4KB). Full output saved to: …` が入る。
  この場合の大きさは括弧内の値を使う（本文の長さはプレビュー分しか無い）。
- 料金は `cost-state.totalCostUSD`（CLI が自分で計算した値）があるときだけ出す。無ければ「不明」で、
  トークンから単価を掛けて**作らない**（構想§8「プロバイダーが提供する範囲」）。
- slug は作業フォルダーの英数字以外を `-` にしたもの（`C:\Projects\Loomo` → `C--Projects-Loomo`）。
  同じ slug に別フォルダーが潰れ得るので、候補のフォルダーは**記録内の `cwd` が `workspace.Contains` で
  ワークスペース内か**で確かめてから採る。サブフォルダーで起動したセッション（`<slug>-sub`）も同じ確かめ方で拾う。

## §37.3 ハーネスの最小構造（`.harness/`）

構想§4 の構造をそのまま採る。**中身の書式は固定しない**——Loomo が機械的に読むのは ID と参照だけ。

```text
.harness/
├── harness.yaml       # id: / version: の2行だけを読む（他のキーは無視）
├── tasks/             # 1ファイル1タスク。ID＝拡張子を除いたファイル名、題＝最初の見出し（無ければID）
├── agents/  workflows/  rules/  evaluations/   # 1ファイル1要素。ID＝ファイル名
└── runs/
    └── verdicts.json  # { "<runId>": { "verdict": "accepted|rejected", "at": "...", "note": "..." } }
```

`.harness/` が無いワークスペースでも動く（Claude Code の構成要素と記録だけで指標・分析プロンプトは出る）。`.harness/` は
**人間が判定を付けたときに初めて作る**——ペインを開いただけでリポジトリにフォルダーを生やさない。ペインがほかに
ファイルを書くことはない（雛形やタスクを書き出す機能は外した）。

`.harness/tasks/` のほかに、`tickets/<群>/<ID>/<ID>-detail.md` でチケット駆動の仕事を回しているワークスペースは
そのチケットをタスクとして読む（§37.11）。そのために `harness.yaml` に設定を足すことはしない。

### §37.3.1 Task と Run の対応

構想§6 の Task（仕事の定義）・Run（試行）・Session（エージェントの実行単位）のうち、第1段では
**Run ＝ Claude Code の1セッション（本体＋サブエージェント）**とする。Run が Task に属するのは、
人間の入力が次のどちらかを含むときに限る（推測で結び付けない）：

- `.harness/tasks/<id>` へのパス（例「`.harness/tasks/fix-login.md` をやって」）
- `task:<id>` という印

### §37.3.2 チケットをタスクとして扱う

仕事の単位が `.harness/tasks/` のファイルではなく**チケット**（Azure DevOps の Work Item・GitHub の Issue）である
ことも多い。チケットの受け入れ条件はチケット側にあるので、同じ内容をタスクファイルに写させない。§37.3.1 と同じく
**書かれているものだけ**で結ぶ（`Loomo.Core/Harness/HarnessTickets.cs`）：

| 指示に書かれたもの | 鍵 |
|---|---|
| `AB#1234`（Azure Boards の言及の書き方。直前が英数字なら別の語） | `AB#1234` |
| `…/_workitems/edit/1234`（dev.azure.com・*.visualstudio.com・Azure DevOps Server） | `AB#1234`（URL も持つ） |
| `https://github.com/<owner>/<repo>/issues/12` | `<owner>/<repo>#12` |

- 素の `#1234` は PR・見出し・Issue のどれか決まらないので拾わない。ブランチ名の番号も命名の約束ごとでしかないので拾わない。
- タスクファイルが先頭近くに `ticket: AB#1234`（URL・`owner/repo#12`・番号だけでも可。番号だけは Work Item とみなす。
  `<!-- -->` の中は読まない）を書いていれば、そのチケットを書いた Run は**そのタスク**に結び付く（同じチケットを
  宣言したファイルが複数あればすべてに）。ハーネス側で受け入れ条件を足したいチケットだけファイルを作る。
- 番号は数として揃える（`AB#0012` と `AB#12` は同じチケット）。
  対応するファイルが無ければ**チケットそのものがタスク**になる（`HarnessTask.IsTicketOnly`）。
- 題はハーネスからは問い合わせない（記録だけから決まる）。Work Items の一覧が読み込み済みならそこから添える。
  実行タブの「チケットを開く」は指示の URL、無ければ Work Items の設定（未設定なら TaskAzure の設定）の組織と
  プロジェクトから URL を組んでブラウザペインで開く。
- Work Items 一覧の右クリック「指示用にコピー」は `AB#1234 題` を写す——これを指示に貼れば Run が結び付く。

## §37.4 指標（構想§10）

| 指標 | 定義 | 注意 |
|---|---|---|
| Run | 期間内のセッション数 | |
| 総トークン | input + output + cache_read + cache_creation（`message.id` で重複除去） | |
| 受け入れ1件あたりトークン | **失敗・差し戻し・未判定を含む**総トークン ÷ 受け入れ件数 | 受け入れ0件なら値を出さず「受け入れなし」と書く（構想§10） |
| キャッシュ読込率 | cache_read ÷（input + cache_read + cache_creation） | |
| ツール失敗率 | is_error の結果 ÷ ツール呼び出し（人間の拒否は除く） | |
| 開始時の入力 | 本体の**最初の応答**の input + cache_read + cache_creation の**中央値**（usage が 0 の API エラーの合成応答は飛ばす） | システムプロンプト・ツール定義・CLAUDE.md・自動メモリなど、何もしないうちから毎回払う量。ハーネスを削った／足した効き目が一番素直に出る。再開したセッションは前の会話を持ち込んで桁違いに跳ねるので平均にしない（2026-11-11） |
| 費用 | `cost-state` のある Run の合計＋「記録のある Run 数 / 全 Run 数」 | 無い Run を推計で埋めない |

成功タスクだけの平均にしない（構想§10）。進捗率のような根拠の無い数字は出さない（構想§7.2）。

## §37.5 改善箇所の分析は Claude Code に渡す（規則では当てない）

**直し所を見つけるのはエージェント、直すかどうかを決めるのは人間**。ペインは材料を揃えて渡すだけにする。
「分析」タブ（既定のタブ）は、期間内の記録をもとに組んだプロンプトを**そのまま見せ**、「分析プロンプトをコピー」で
クリップボードへ写す（`HarnessAnalysisPrompt.Build`）。人間がそれを可視ターミナルの Claude Code に貼る。

プロンプトに入れるもの：

- 進め方：記録は JSONL で大きいので全文を読まず `rg`／`jq` で必要な行だけ引く、サブエージェントの記録の場所、
  差し戻し・失敗・トークンの多い Run から見る、観点の例（大きすぎる出力・読み直し・失敗の反復・編集の空振り・
  検証なしの変更・指示や Skill が守られていない箇所。例に無い観点でもよい）、1回きりの偶然は直し所にしない。
- 直す先はハーネスだけ（プロダクトのコードは変えない。ユーザー全体の `~/.claude` は他のワークスペースにも効くので断ってから）。
- 直し方の優先順位：毎回必ず守らせたいこと（してはいけない操作・編集後の検証）は指示文ではなく `permissions.deny`／hooks、
  決まった手順は Skill、`CLAUDE.md` はどちらにもできない説明だけ（文章の指示は読み飛ばされ得る）。毎回読み込まれる指示を
  削ることも直し所にしてよい。ハーネスエンジニアリングの通説（2026）のうち、ペインの方針と矛盾しない部分を渡し方に取り込んだもの（2026-11-11）。
- 返し方：直し所・観測（何 Run・根拠の記録:行）・原因の見立て・直す先と直し方の表を**先に**出し、直すのは人間が了承したものだけ。
- 期間の指標（§37.4。開始時の入力の中央値を含む）、いまの構成要素（パス・ユーザー全体かどうか・指示は行数と毎回読まれるかどうか）、Run の一覧（新しい順・最大 60 件。開始・題・版・
  トークン・ツール／失敗・判定・**記録の絶対パス**）。

### §37.5.1 規則による検出をやめた理由（2026-11-09）

第1段は「LLM は必要なところだけ」（構想§2-5）に従い、改善候補を**決定的な規則**（同じファイルの繰り返し読込・
過大なツール出力・同じコマンドの失敗反復・編集の空振り・検証なしの変更）で検出し、候補に扱い（対処中・対処済み・
見送り）を付け、ハーネスを変えた時刻より前の Run だけで起きた候補を外す仕組みまで積んだ。これを外した。

- 規則が見られるのは**表面の症状**だけで、「なぜそうなったか」「どこを直すか」は規則の当たり（推測）だった。
  直し所を探すことこそ LLM が要るところで、しかも出口は結局「改善プロンプトをコピーして Claude Code に貼る」だった。
- 規則の手入れが手間の大半になっていた：ファイルごとに割れて 30 日で 86 件中 72 件が「1 Run だけ」、
  `<persisted-output>` の印を本文の途中で拾う誤検出、扱いのボタンが押されないので「前の版だけ」の自動外しを足す、と続いた。
  扱いのファイル（`candidates.json`）は実際ほとんど書かれなかった。
- 決定的な数字（指標・版の比較・ツール失敗）はそのまま残す。観測はペイン、推測はエージェント、と分けたのは §37.2 と同じ考え方。

同じ理由で、点検（`.harness/` の最小構造との突き合わせと雛形作成、旧§37.10）と、改善候補を `.harness/tasks/` へ
書き出す「タスクにする」も外した——どちらも規則の判定と、頼まれないファイル作成だった。

## §37.6 ハーネスの版と比較

版の単位は **git のコミット**（構想§12 の未決をこう決めた）。Run の版＝その Run の開始時刻以前で
ハーネスのパス（`.harness`・`CLAUDE.md`・`AGENTS.md`・`.claude`）を最後に変えたコミット。
**未コミットの変更は区別できない**（画面にもそう書く）。`harness.yaml` の `version:` は表示用のラベルとして併記する。

版の比較タブは版ごとに Run・受け入れ／差し戻し・受け入れ1件あたりトークン・1 Run あたりトークン・ツール失敗率を並べる。**単発の良い結果で改善と判断しない**（構想§10）ので、Run が3未満の版には
「試行が少ない」と添える。同じ評価タスク群を新旧に与える実験（構想§10）は第1段では人間が行い、
`task:<id>` で結び付けた Run を版ごとに見比べる。

## §37.7 画面

```text
┌ HARNESS ─────────────────────────────────────────── [期間 30日 ▾] [更新] ┐
│ Run 42 ・ 受け入れ 5／差し戻し 1 ・ 受け入れ1件あたり 24.1M ・ キャッシュ 93% ・ 失敗 4.1% │
├ 分析 │ 実行 │ 構成 │ 版の比較 ───────────────────────────────────────────┤
│ 期間内の記録の場所・指標・構成要素をまとめたプロンプト。   [分析プロンプトをコピー] │
│ # ハーネスの直し所を探す                                                      │
│ このワークスペースで動いた Claude Code の作業記録（…の 42 Run）を読み、…       │
└───────────────────────────────────────────────────────────────────────────┘
```

- **下の帯**：タブより上に置くと最初に数字が目に入り、分析タブの主役（コピー）を押し下げるので、ステータスバーとして下に置く（2026-11-09）。判定が1件も無い間は「受け入れ／差し戻し」「受け入れ1件あたり」を出さない（0／0 と「受け入れなし」が並ぶだけになる）。
  版の比較の同じ列も同様。`.harness` の ID・版は宣言があるときだけ出す。トークンは 3.08B／17.0M／54.5k と縮める。
- **分析**（既定のタブ）：§37.5。見出し・何を渡すかの一行（期間・Run 数・失敗のある Run・差し戻し・構成要素数）・
  主操作「分析プロンプトをコピー」と使い方（① コピー → ② 貼る → ③ 表から選ぶ）を上に置き、渡す中身は折り返して下に出す
  （何が渡るかを人間が確かめられる）。プロンプトではユーザー全体の Skill・エージェント・コマンドを種類ごとに1行へ畳み、
  Hook は設定ファイルの行に `hooks: …` と添える。
- **実行**：Run の一覧（新しい順・題・版・トークン・失敗・判定）と、選んだ Run のツール呼び出しの系列。
  Run に「受け入れ」「差し戻し」「判定を外す」を付けられる（構想§6「自己申告だけで完了としない」——判定は人間）。
- **構成**：定義された構成要素と、観測された使用回数。**Claude Code の設定ファイルを開く入口**でもある：
  `settings.json`／`settings.local.json`／`.mcp.json` は hooks の有無によらず「設定」として並べ、ユーザー全体の
  `~/.claude`（`CLAUDE.md`・`settings.json`・skills・agents・commands。`CLAUDE_CONFIG_DIR` があればそこ）も「ユーザー」の印を付けて並べる。
  「このワークスペース」「ユーザー全体（~/.claude）」の見出しで分け、各々 指示→設定→その他の順。Hook は行を分けず、
  その設定ファイルの行の使用欄に `hooks: Notification, SessionStart` と出す。指示の行は使用欄に**行数**を出し、
  Claude Code がセッション開始で必ず読むもの（`CLAUDE.md`・自動メモリ `~/.claude/projects/<slug>/memory/MEMORY.md`）には
  「毎回読まれる」を添える（`AGENTS.md` は、そのフォルダーか上の階層に CLAUDE.md・`.claude/CLAUDE.md`・CLAUDE.local.md があると Claude Code が読まない——v2.1.277 から CLAUDE.md が無いときだけ直接読む——ので、そのときは行数だけ。CLAUDE.md が `@AGENTS.md` で取り込んでいれば読まれる。2026-11-11）。自動メモリは置き場所こそ `~/.claude` だが効くのは
  そのワークスペースだけなので「このワークスペース」に並べる。長すぎるかどうかの判定はしない（数えた事実だけ）。ダブルクリック・Enter・「開く」でエディタに開く。
  パスはワークスペースの外なら `~` で縮め、区切りは `/` に揃える（日本語フォントでは `\` が `¥` に見える）。
- **版の比較**：§37.6。列に「開始時の入力」（中央値）を足した——CLAUDE.md を削った版で下がったかを見るため。見出しは GridView の既定ヘッダー（テーマに乗らず白く出る）を使わず、行と同じ並びで描く。
- **素材の流れ**：「記録を開く」は transcript をエディタで開いて該当行へ飛ぶ。構成タブの行は定義ファイルを開く。
- **復元**：選んでいたタブ・期間は `WorkspaceSnapshot.Harness` に保存する。タブの番号は永続化されるので、旧「改善候補」の 0 を
  「分析」が引き継ぎ、旧「点検」の 4 は 0 に戻す。

## §37.8 実装の配置

一方向依存（App → Services → Core）に従う。

- `Loomo.Core/Harness/` —— UI 非依存。`ClaudeTranscriptParser`（1セッション→`HarnessRun`）、
  `HarnessDefinitionReader`（構成要素の列挙）、`HarnessAnalysisPrompt`（§37.5）、`HarnessMetrics`（§37.4）、
  `HarnessVersionTimeline`（§37.6）、`HarnessVerdictStore`（verdicts.json）。
- `Loomo.Services/Harness/` —— `ClaudeTranscriptLocator`（slug と `cwd` 確認）、`HarnessGitHistory`
  （`git log` を `ChildProcessIo` 経由で）、`HarnessAnalyzer`（全体を組み、**ファイルの長さ＋更新時刻で
  解析結果をメモリに持つ**——数百 MB の記録を毎回読み直さない）。
- `Loomo.App` —— `PaneKind.Harness`（**enum の末尾に追加**、数値で永続化されるため）、`HarnessPaneViewModel`、
  `HarnessPaneView`。ペインの登録はファイル一覧（§26.10）と同じ箇所（`_paneElements`・`DeferPaneContent`・
  `StageOrder`・`DockOrder`（下）・ラベル・アイコン・コマンド `pane.harness`）。

重い処理（記録の解析）は UI スレッドに載せない（§31.15）。解析は `Task.Run`（CPU 仕事なのでプールで良い）、
git は子プロセスなので `ChildProcessIo`（§31.16）。記録フォルダーの監視はしない——Claude Code は1ターンごとに
追記するので、監視すると作業中ずっと再解析が走る。更新はペインを開いたとき・期間を変えたとき・更新ボタン。

## §37.11 チケット型タスク（`.harness/` を持たないチケット駆動のワークスペース）

`.harness/` を持たず、独自のチケット駆動のワークフローで回しているワークスペース（例：CurrentTask）がある。
**相手のフォルダー構成は変えさせない**——Loomo の側がその形を読む。実装は `Loomo.Core/Harness/HarnessLocalTickets.cs`。

```text
<ワークスペース>/
  AGENTS.md / CLAUDE.md
  doc/tickets-format/contents/ワークフロー仕様*.md   ← 工程の定義（workflows/ と同じ役割）
  tickets/<群>/tickets.tsv                           ← 一覧の正本（ID Status Type Title Priority Summary DependIDs LastUpdated）
  tickets/<群>/<ID>/<ID>-detail.md                   ← 目的・要件・受け入れ条件（- [ ] のチェックリスト）
  meta/<群>/…                                        ← ワークスペース自体の改修。構成は tickets/ と同じ
  archive/<テーマ>/<群>/…                             ← 完了済み。構成は同じ
```

### §37.11.1 読み方を切り替える方法：設定ではなく形で検出する

`harness.yaml` に `taskSources:`（glob のリスト）を足す案と、形で自動検出する案を比べ、**自動検出**にした。

- `taskSources:` は §37.3 の「`harness.yaml` は `id:`・`version:` の2行だけを読む（中身の書式を固定しない）」を破り、
  Loomo が YAML のリストを解釈することになる。
- そもそも CurrentTask 型は `.harness/` を持たない。設定で切り替えるなら相手のフォルダーにファイルを足させることになり、
  「構成は変えない」に反する。
- 検出の条件は `tickets/*/*/*-detail.md`・`meta/*/*/*-detail.md` という十分に特殊な形なので、ふつうのリポジトリが
  誤って当たる余地は小さい。当たっても ID が指示に書かれない限り Run は結ばれない（§37.11.3）。

### §37.11.2 列挙と、定義として出す値

| 値 | 出どころ | 種別 |
|---|---|---|
| ID | `<ID>-detail.md` のファイル名 | 定義 |
| 題 | `tickets.tsv` の Title。行が無ければ detail の最初の見出し | 定義 |
| 状態・種類・依存 | `tickets.tsv` の Status（`not-started`/`working`/`done`）・Type・DependIDs の**今の値** | 定義（Run 当時の状態ではない） |
| 受け入れ条件の数 | detail の「要件・受け入れ条件」節の `- [ ]`／`- [x]`（他の節の項目は数えない。コードフェンスの中は読まない） | 定義 |

- **archive は一覧にしない**（約 90 件ある）。期間内の Run の指示が言及した ID のうち、`tickets/`・`meta/` に無いものだけ
  `archive/<テーマ>/<群>/<ID>/` を探し、見つかったチケットの detail と**その群の** `tickets.tsv` だけを読む。
  言及が無ければ `archive/` には触れない。
- 読まないもの：`tickets.tsv` 以外の表（`decisions.tsv` 等）、`<ID>-discussion.md`、`reviews/`。
- 「状態」も「受け入れ条件 2/5」も**定義側の値**で、観測（記録）から作った推定とは混ぜない。画面では「tickets.tsv の現在値」と書く。

### §37.11.3 Run とチケットを結ぶ規則

§37.3.1・§37.3.2 と同じく**書かれているもの**か、**エージェントが実際にした書き換え（観測）**だけで結ぶ——題が似ている等の
推測では結ばない。読むのは人間の指示と、打たれたスラッシュコマンドの引数
（記録の `<command-name>`／`<command-args>`。指示や題にはしないが `HarnessRun.Commands` に持つ）。

| 書かれたもの | 結ぶ先 |
|---|---|
| 素の ID `[A-Z]{2,4}-\d{3}`（前後が ASCII の英数字なら別の語。日本語が続いてもよい） | **列挙済みの ID と一致したとき**だけ、その ID のチケット（同じ ID が複数の群にあればすべて） |
| `tickets/<群>/<ID>/…`・`meta/<群>/<ID>/…`・`archive/<テーマ>/<群>/<ID>/…` | その群のその ID のチケットだけ（パスの中の `<ID>-detail.md` を素の ID として数え直さない） |
| `/ticket-run <ID>` 等のスラッシュコマンドの引数 | 指示と同じ規則 |

**作業の跡（指示に ID が無いとき）**：「続きをお願い」のように指示に ID が無くても、エージェントが**そのチケットを
実際に書き換えた**記録があれば結ぶ（`HarnessLocalTickets.FindTraces`）。指示による結び付きとは根拠を分けて持ち
（`HarnessTaskLink.Basis` が `Declared`／`Observed`）、画面では `VCI-001（working・跡）`、詳細に「作業の跡・指示には無い」と
根拠（「VCI-001-detail.md ほか1件を編集 2回」「状態 working→done」）を出す。

| 跡に数えるもの | 数えないもの |
|---|---|
| `<root>/<群>/<ID>/` の中のファイルへの Edit／MultiEdit／Write／NotebookEdit（本体・サブエージェントとも） | Read・Grep など読んだだけ（依存先や前例を読むのは別のチケットの仕事でも起きる） |
| `tickets.tsv` への Edit で、置換前後で同じ ID の行の Status が変わったもの | 行の追加（起票は、そのチケットの仕事ではない）・Write による表の丸ごと書き換え（前後を比べられない） |
| | 失敗・拒否された呼び出し、AI の返答文に出た ID（依存先や別チケットへの言及が混ざる） |

- 跡も定義にある ID と一致したときだけ結ぶ。指示にも書かれていれば指示の側に入れる（跡で上書きしない）。
- `tickets.tsv` の行を読むため、Edit／MultiEdit の置換前後の文字列を `RunToolCall.EditOld`／`EditNew` に持つ（4,000 字で切る）。
- archive のチケットも、跡（書き換え）があれば言及と同じく読み込む。

- ID の形をしていても定義に無い語（`ABC-123`）は拾わない。大文字・小文字は区別する（`vci-001` は拾わない）。
- 1つの Run に複数の ID があれば、すべてに結ぶ。
- `AB#…`（Azure DevOps の Work Item）は §37.3.2 のまま別に結ぶ。チケット型タスクに `ticket:` は付けない。

### §37.11.5 実行タブ

Run の一覧のタスク欄に `VCI-001（working）` と状態を併記する（作業の跡だけで結んだものは `VCI-001（working・跡）`）。詳細には群・状態・種類・受け入れ条件の数・依存を出す。
版の比較と指標（§37.4・§37.6）は変えない。

## §37.9 まだやらないこと（構想§11 の残り）

- **Runner**：ハーネスから Claude Code / Codex を起動し、Task・Run・worktree を結び付ける口（構想§6）。
  起動するなら可視ターミナルで（人間の目の前で走らせる、§34 の常駐セッションに乗る）。
- **自動の検証ゲート**：Run の完了をビルド/テストの成否で機械判定する（構想§6 Verification Gate）。今は人間の判定だけ。
- **分析プロンプトを可視ターミナルの Claude Code へ直接送る口**。今はコピーして人間が貼る（前面が busy のタブへ打ち込まない約束、§38）。
- **Codex 等の別エージェントの記録**。`HarnessRun` は Claude Code に依存しない形にしてあるので、パーサを足せば載る。
