# §32 リファクタリング（右クリック「リファクタリング」）

> 作成日: 2026-08-05 / 状態: **実装済み**（実機確認は §32.8 が未消化）
> 対象リポジトリ: `C:\Projects\Loomo` ＋ `C:\Projects\Editor`
> 関連する正本: LSP の所有境界は §30、体感品質の順序は §31、VS Code との差の台帳は §19.9。
> Editor パッケージ: **1.0.77**（公開済み最新は 1.0.76。1.0.77 は nuget.org へ未反映＝ローカル注入で検証中）。

## §32.1 目的と、着手前の実態

エディタの右クリックから、Rider の「Refactor This」に相当する操作——**名前の変更／メソッドの抽出／
クラス（インターフェース・基底クラス）の抽出／インライン化／移動／シグネチャの変更**——へ入れるようにする。

着手前に実測した結果、**「Code Action は実装済み」は表向きの話で、リファクタリングは1つも動かなかった**。
理由は4つあり、いずれもプロトコル層にあった（`ga` のポップアップ UI 自体は存在していた）。

| # | 実態 | 何が起きるか |
|---|------|--------------|
| 1 | `initialize` の client capabilities に `textDocument.codeAction` の宣言が**無い** | サーバーは旧仕様の `Command[]` しか返さない（kind が無く quick fix と区別できない）。Roslyn は候補自体を絞る |
| 2 | 要求が**キャレット1点**のみ（`LspRange(pos, pos)`）で `only` フィルタも無い | 「メソッドの抽出」のように**範囲そのものが対象**のものは候補に出ない |
| 3 | `codeAction/resolve` **非対応** | Roslyn は一覧で `data` だけを返し edit は解決時に作る → 「適用しても何も起きない」 |
| 4 | `workspace/applyEdit` が常に `applied: false` | tsserver 系のコマンド型リファクタリングは編集を返す経路が無く、無言で失敗 |

さらに `documentChanges` の**ファイル操作（create/rename/delete）を捨てていた**ため、
「クラスに抽出」「型をファイルへ移動」は新しいファイルが生まれず、そこへの編集だけが宙に浮いていた。

## §32.2 分担（どこに何を置いたか）

§30 の分割線（プロセスとプロトコルはワークスペース単位、UI 状態はビュー単位）をそのまま踏襲する。

```
Editor（プロトコルとビュー）
 ├ LspClient          codeAction(range, only) / codeAction/resolve / workspace/executeCommand
 │                    client capabilities の宣言、workspace/applyEdit のホストへの委譲
 ├ LspModels          LspCodeAction(Command/RawJson/IsPreferred/DisabledReason)
 │                    LspWorkspaceEdit.FileOperations、LspCodeActionKinds（ドット階層の前方一致）
 └ VimEditorControl   SelectionAsLspRange()、`ga` ポップアップの resolve/command 対応

Loomo（ワークスペースと導線）
 ├ LspClientPool / LspWorkspaceService  ApplyEditRequested をホストへ中継
 ├ LspDocumentHandle                    範囲指定 codeAction / resolve / executeCommand を素通し
 ├ Services/Refactoring/RefactoringMenu 候補の分類と日本語化（純粋関数・テスト対象）
 ├ Services/Refactoring/CSharpSignature* シグネチャ変更（§32.5）
 └ ShellWindow.Refactoring.cs            右クリックメニューと適用経路
```

**Loomo が主導する**のは §30 と同じ理由による。ワークスペースのルート・開いているタブ・
ファイルの実体を知っているのはホストで、複数ファイルに及ぶ編集を安全に当てられるのもホストだけだから。

## §32.3 適用の3経路

選んだ項目をどう適用するかはサーバーによって違う。3つとも通す。

1. **edit を持つ** — そのまま適用する。
2. **未解決（`data` だけ）** — `codeAction/resolve` で edit を確定してから適用する。**Roslyn はこれ**。
3. **command を持つ** — `workspace/executeCommand` で実行し、編集はサーバー起点の
   `workspace/applyEdit` で返ってくる。**typescript-language-server はこれ**。

3 の経路は**読み取りスレッドで発火し、ハンドラが戻るまでサーバーは応答を待って止まっている**。
Loomo は `Dispatcher.Invoke` で UI スレッドへ同期的に入って適用し、結果を `applied` として返す。
これが詰まらないのは、**この編集の原因となった `executeCommand` を UI スレッドが `await` している**
（＝ブロックしていない）ためで、ここを同期待ちに変えるとデッドロックする。

**ワークスペースは1フォルダーではない。** 書き込んでよい範囲の判定
（`LspWorkspaceEditPaths`）は `IWorkspaceService.Folders` の**全件**を見る。プライマリ
（`Folders[0]`）だけで判定していると、**あとから追加したフォルダーのファイルが「ワークスペース外」**
になり、そこを含む rename やリファクタリングが丸ごと失敗する。言語サーバー自身は `initialize` で
全フォルダーを受け取っていて参照も返すので、判定側だけが取り残される形になる
（これは §32 以前から rename にあった不具合で、ここで直した）。
シグネチャ変更も同じ一覧を受け取り、どのフォルダーにも属さない参照は
**黙って飛ばさず件数を数えて結果に出す**（一部だけ変わったコードに気付けないのが一番危ない）。

適用そのものは `ShellWindow.ApplyLspWorkspaceEdit` に一本化した。順序は
**ファイル操作（作成→改名→削除）→ 本文の編集**。作成を先にしないと、新規ファイルへの編集が
実体の無いパスに当たる。本文の編集は**全ファイルぶんの検証を先に済ませてから**書き込む
（途中まで適用された壊れた状態を作らない）。書き込み先はいずれも
`LspWorkspaceEditPaths.ResolveInWorkspace` を通し、ワークスペース外には触れない。

## §32.4 メニューの作り

- 右クリック時点では**LSP を叩かない**。サブメニューを開いた瞬間に中身を作る
  （`MenuItem.SubmenuOpened`）。右クリックしただけで言語サーバーへ問い合わせが飛ばない。
- **使えない項目は出さない。**「シグネチャの変更」はキャレットがメソッド／コンストラクター宣言の中に
  あるときだけ出す（構文解析はバックグラウンドで、LSP 要求と同時に走らせる）。押しても
  「できません」としか返らない項目を並べない、という方針を全項目に通す。
- **「名前の変更」はこのサブメニューの中に1つだけ置く。** コントロール側のネイティブ
  "Rename Symbol" は `VimEditorControlOptions.HostProvidesRenameMenuItem` で消す
  （残すと同じ操作が2つ並ぶ）。したがってサブメニューを出す条件は、
  ネイティブ項目が出ていた条件と**同じ「接続済み」**に揃える必要がある——
  `IsReady`（didOpen 済み）まで絞ると、接続直後にどちらのメニューにも名前の変更が無い瞬間ができる。
- 言語サーバーの題名は `MenuHeaderText.Escape` を通してから載せる。WPF は `_` を
  アクセスキー指定と解釈して1文字消すので、`Introduce local for 'foo_bar'` が化ける。
- 要求範囲は**選択があれば選択、無ければキャレット**。行選択・矩形選択は外接する連続範囲として渡す
  （LSP に矩形を表す手段が無く、抽出の対象としては外接矩形が最も近いため）。
- `context.only` に `refactor` を渡し、さらに受信側でも quick fix / source を落とす
  （`only` を無視するサーバーがあるため二重に守る）。
- 並びは Rider に合わせて **抽出 → インライン化 → 移動 → 書き換え → その他**。
  kind を申告しないサーバーのために、原文の前置き（`Extract` / `Inline` / `Move`…）でも分類する。
- `disabled` の項目は落とす（押せない項目でメニューが埋まる）。
- 表示名は**定番のリファクタリングだけ日本語へ寄せ、未知の題は原文のまま**出す。
  当てずっぽうの訳より原文のほうが誤解が少ない。原題は必ずツールチップに残す。

### §32.4.1 実 Roslyn での実測（2026-08-05）

`roslyn-language-server` を実プロセスで起動し、`textDocument/codeAction` に何が返るかを直接測った。
推測で組んだ部分が実物と合っているかの確認と、**「出ない」ときの原因の切り分け**が目的。

| 観測 | 値 |
|------|-----|
| `codeActionProvider.codeActionKinds` | `[quickfix, refactor]` |
| `resolveProvider` | `true` |
| `executeCommandProvider.commands` | **空**（Roslyn はコマンド型を使わない） |
| 2行を覆う範囲での `only:["refactor"]` | 2件（`refactor.extract`） |
| 各アクションの `edit` | **null**、`data` のみ ＝ 必ず `codeAction/resolve` が要る |
| resolve 後 | 1ファイル・2編集（`y = NewMethod(a, b)` ＋ メソッド追加） |
| 題名 | **サーバー側で日本語化されて返る**（「メソッドを抽出する」「ローカル関数の抽出」） |

つまり §32.3 の経路2（resolve）がそのまま本番経路で、これが無ければ Roslyn では
**1件も適用できない**。題名が既に日本語なので、§32.4 の対訳表は Roslyn では出番が無い
（英語ロケールのサーバーや他言語サーバー向けの保険として残す）。

**この時点で判っていた「候補が出ない」条件**（真因は §32.4.3）:

1. **ファイルがプロジェクトに属していない。** どのプロジェクトにも属さない `.cs` は
   `roslyn-canonical-misc` の「その他ファイル」プロジェクトへ入り、hover や documentSymbol は
   通るのに **code action は永久に 0 件**（2分待っても 0 だった）。実プロジェクト内の
   ファイルへ変えた途端に 2 件返った。
2. **プロジェクト読込が終わっていない。** 読込中も**エラーではなく空配列**を即答するので、
   「無い」と区別がつかない。→ サーバー状態が `Ready` でなければ
   「言語サーバーの準備中です」と出し分ける（`DescribeNoRefactorings`）。

もう1つ、実測とは別に**選択が消える経路**があった。§32.4 の「選択があれば範囲で問う」は、
右クリック時点で選択が残っていることが前提だが、コントロールの右クリック処理は
Vim 無効時に `Escape` を通すため `ClearPlainSelection` で選択を捨てていた。
結果、範囲ではなくキャレット1点で問い合わせることになり、**範囲を対象とするリファクタリング
（メソッドの抽出はこれ）が原理的に1つも出ない**。選択の内側での右クリックは選択もキャレットも
保つよう直した（`Selection.Contains`。VS / VS Code / Rider と同じ挙動）。

### §32.4.2 選択→range 変換のズレ（実機で見つけた本命）

上の2つを直しても「メソッドの抽出」は出なかった。実機を UI Automation で操作し、
診断ログ（`LOOMO_REFACTOR_DEBUG=1` → `%APPDATA%/Loomo/refactor-debug.log`）で
実際に送っている範囲を見て原因が確定した。

```
menu: … hasSelection=True range=30,27-31,0      ← 行選択したのに開始桁が 27
```

**エディタの `Selection` と LSP の range は規約が2つ食い違う。**

1. `Selection` の終端は**含むセル**（`GetSelectionText` が `End.Column + 1` で切り出す）。
   LSP の range は**含まない**。
2. 行選択（VisualLine）は「行まるごと」の意味なのに、`Selection.Start` には
   **キャレットの桁が残る**。

変換でこの2点を無視していたため、行選択すると**文の途中から始まり次行の行頭で終わる範囲**を
送っていた。Roslyn は完全な文の並びを要求するので、これでは 0 件になる。
`V`＋`j` は抽出したいときに最も自然な選択操作なので、事実上ほぼ全ての場合で出ないことになる。

さらに `V` を押しただけ（1行だけの行選択）は `Start == End` で `Selection.IsEmpty` が真になり、
**「選択なし」に化けてキャレット1点で問い合わせて**いた。

変換を純粋関数 `Editor.Core/Lsp/EditorSelectionRange.cs` へ切り出し、
行選択は行頭〜行末、文字/矩形選択は終端 +1（行末で丸める）、行選択は `IsEmpty` で弾かない、
と定めてテストで固定した。実機で `range=30,27-31,0` → `range=28,0-30,67` に変わり、
候補がメニューへ出るようになった。

### §32.4.3 マルチルートが Roslyn の「メソッドの抽出」を殺していた（真因）

§32.4.2 を直しても「メソッドの抽出」だけは出なかった。他のリファクタリング
（インライン化・`for` に変換する・式本体・ローカルの導入）は出るのに、**抽出系だけが全く出ない**。
同じファイル・同じ範囲を生の `LspClient` で叩いてもアプリと結果が一致したので、
こちら側の変換や分類ではないことは早くに分かったが、そこから先が見えなかった。

条件を1つずつ潰した結果、効いていたのは **`initialize` の `workspaceFolders` の件数**だった。
同じサーバー・同じファイル・同じ範囲で:

| `workspaceFolders` | 結果 |
|--------------------|------|
| `[Loomo]` | **5秒で2件**（メソッドを抽出する／ローカル関数の抽出） |
| `[Loomo, AimAssist]` | **120秒待っても0件** |

Roslyn は複数ルートを渡されると、構文だけで済むリファクタリングは返すのに、
**データフロー解析を要するもの（抽出系）を返さなくなる**。エラー診断は出ないし
hover も補完も効くので、「LSP は動いている」ように見えてしまう——一番たちの悪い壊れ方だった。

そこで §30.0-5 の「ルートは常にプライマリ、フォルダー一覧は全件渡す」をやめ、
**ワークスペースフォルダーごとにサーバーを1本**立てる（`ResolveRoot` はそのファイルを含む
フォルダーを返し、`initialize` にはそのルート1件だけを載せる）。フォルダー同士が
祖先/子孫にならないことは `IWorkspaceService.AddFolder` が保証しているので、
§30.0-6 が禁じた「含んでいるフォルダーをルートに選ぶ」には当たらない。
同じフォルダー内なら何枚開いてもサーバーは1本のまま——§30 本来の目的は保たれる。

代償はフォルダー数ぶんプロセスが増えること。ワークスペースに足したフォルダーは
「ついでに見えるフォルダー」ではなく**同格の作業対象**なので、そのぶんの解析コストは払う、という判断。

### §32.4.4 それでも出ないとき

**アプリは Roslyn の返答に忠実**であることを確認済み——同じファイル・同じ範囲を
生の `LspClient` で問い合わせた結果と、アプリのログの候補一覧が**完全に一致**する
（ワークスペースルートを変えても同じ）。したがって「出ない」の残りは Roslyn の判断であり、
次の2つが典型:

- **プロジェクトに属さないファイル**（`roslyn-canonical-misc` 行き）。インライン化や
  「ローカルを導入します」のような局所的な refactoring は出るのに、**データフロー解析を要する
  メソッドの抽出だけが出ない**という紛らわしい状態になる。
- **その領域では抽出できない**とサーバーが判断した場合（出力が複数になる選択など）。

切り分けは `LOOMO_REFACTOR_DEBUG=1` のログを見るのが早い。`range` が期待どおりで
`actions` に `refactor.*` が1つも無ければ、原因はこちら側ではなく言語サーバー側にある。

## §32.5 シグネチャの変更（C#・LSP には無い）

**「シグネチャの変更」は LSP 仕様に存在せず、Roslyn / tsserver / rust-analyzer のいずれも
code action として公開していない**（Rider と VS は IDE 内蔵の Roslyn API で実現している）。
そこで C# に限り Loomo 側で組む。ただし丸ごと自前にはせず、次の分担にした。

- **どこから呼ばれているか** — 言語サーバーの `textDocument/references`。
  すでにソリューションを読み込み済みのプロセスに聞く。**MSBuildWorkspace を別に立てない**
  （同じ解析を二重に走らせるのは、CPU と起動時間の両方で割に合わない）。
- **宣言と実引数の書き換え** — Roslyn の**構文 API のみ**（`Microsoft.CodeAnalysis.CSharp`）。
  意味解決はしないので、コンパイル可能なプロジェクト構成を用意する必要が無い。

扱う操作は、並べ替え／改名／型の変更／既定値／追加／削除／戻り値型の変更。

**安全側の作り**（ここが本体と言ってよい）:

- 書き換えられない参照が**1つでもあれば、何も適用せずに理由を返す**。半分だけ書き換わった状態を作らない。
  対象は、デリゲートへ渡されるメソッドグループ、`nameof`、属性の中。
- 名前付き引数は**名前ごと運ぶ**。パラメーターを改名したら引数側の名前も追随させる（さもなくば壊れる）。
  並べ替えの結果、名前付きの後ろに位置指定が来る形になるときは、以降を名前付きへ倒す。
- 省略されていた既定値つき引数は**省略のまま**運ぶ。並べ替えで途中に来てしまった場合だけ既定値を書き出す。
  既定値が無ければ中止する。
- 追加したパラメーターは、**呼び出し側に書く値か既定値のどちらか**が必須。どちらも無ければ中止する。
- メニューを開いてからダイアログを確定するまでに本文が編集されていることがある。計画を作る前に
  **宣言が読み取った時と同じ形か照合**し、変わっていれば適用せずやり直しを促す
  （古い位置のまま書き換えると、別の場所を壊すか黙って何もしない）。
- override / インターフェース実装の宣言が参照一覧に含まれていれば、**宣言として同じ変換を当てる**
  （呼び出しか宣言かは構文で判定する）。
- XML ドキュメントの `<param name="…">` を追随させる。放置すると CS1572/CS1573 の警告が新たに生える。
- 型と戻り値だけの変更なら、呼び出し元は**見に行かない**（言語サーバーが未準備でも通る）。

**限界（意図的に埋めていない）**: オーバーロードの解決は見ていない。参照一覧に出てこない動的呼び出し
（リフレクション・`dynamic`・文字列によるバインド）は当然たどれない。C# 以外の言語には出さない。

## §32.6 抽出は「名前を先に決める」

言語サーバーが返す抽出の編集は、名前が **`NewMethod`** で固定されている（Roslyn の実測）。
これをそのまま当てて終わりにすると、**抽出という操作の半分しかやっていない**——
切り出しはできても名前が付いていない。Rider も VS も名前を先に訊く。

そこで抽出系（`refactor.extract`）を選んだときは、**適用前に**名前を訊いて差し替える
（`ExtractedSymbolName`）。キャンセルすれば何も起きない。

- 名前の取り出しは **C# の構文解析**。編集テキストを `ParseMemberDeclaration` /
  `ParseStatement` / クラス本体としての再解釈の順で読み、`MethodDeclaration` か
  `LocalFunctionStatement` の識別子を取る。呼び出し側と宣言がひと続きの1編集で来る形も実測にあるので、
  そこも読めるようにしてある。
- 差し替えは**これから挿入する文字列の中だけ**を単語単位で置換する。サーバーへ rename を投げ直すより速く、
  既存コードに同名の識別子があっても巻き込まない。
- 名前が取り出せない言語では**訊かずにそのまま適用**する（誤爆するくらいなら訊かない）。

### ローカル変数を含む選択

「選択した中でローカル変数を宣言していて、それを後ろで使っている」場合も抽出できる。
Roslyn は `out` 引数にして返す:

```
int a, b;
NewMethod(seed, out a, out b);

private static void NewMethod(int seed, out int a, out int b) { a = seed + 1; b = a * 2; }
```

一時期これが出ないように見えたのは §32.4.3 のマルチルート不具合の症状で、抽出の制限ではない。

## §32.6.1 なぜ Editor 側にも手を入れたか

「Loomo だけで完結させ、Editor は触らない」という選択肢はあった。採らなかったのは、
§32.1 の 1〜4 が**すべてプロトコル層の欠落**で、そこは `LspClient` にしか無いから。
Loomo 側に第2の LSP クライアントを立てるのは §30 が潰したはずの構造（N 本のセッション）へ戻ることになる。

同じ理由で、Editor 自身の `ga` ポップアップも同時に直した。
プロトコル層を直しておきながら `ga` だけ古い挙動（範囲を見ない・解決しない）で残すと、
**「右クリックからは動くのに `ga` からは動かない」**という説明のつかない差になる。

## §32.10 マルチルートの規約（構造の見直し）

§32 の作業で踏んだ不具合3件（編集先の判定・シグネチャ変更の参照収集・LSP のルート解決）は、
どれも同じ形をしていた。個別の実装ミスではなく、**同じ間違いを繰り返させる構造**だったので、
そこを直した。

実測した現状（2026-08-05）:

| 指標 | 値 |
|------|-----|
| `RootPath`（プライマリ）参照 | 67 箇所 |
| `Folders`（全フォルダー）参照 | 47 箇所 |
| 「ワークスペース内か」の**自前実装** | 8 箇所以上 |
| ソースに「マルチルート」と注釈があるファイル | **19**（＋テスト4） |

19 ファイルに注釈が付いている＝**同じ学習を19回している**、というのが症状そのもの。原因は
`IWorkspaceService` が `Folders`（生のリスト）と `RootPath`（プライマリ）しか公開しておらず、
**問いを提供していなかった**こと。消費者は毎回「どちらを使うか」と「包含判定の書き方」を自分で決め、
常習の間違いが2つ出る:

1. **プライマリだけを見る** — 追加フォルダーのファイルが「ワークスペース外」になる。
2. **区切り文字なしの前方一致** — `C:\work\app2` を `C:\work\app` 配下と誤認する（`ProblemsViewModel` に実在した）。

**直した形**: 問いをインターフェースへ載せ、実装を `Loomo.Core/Files/WorkspacePaths.cs` の1つに集約する。
既定インターフェース実装にしてあるので、テスト用の実装を含め振る舞いは常に一致する。

- `workspace.Contains(path)` — 触ってよいか／対象に含めるか
- `workspace.FolderFor(path)` — 担当フォルダー（LSP ルート・フォルダー単位の状態・表示基準）
- `workspace.ToDisplayPath(path)` — 一覧表記（フォルダーが2つ以上のときだけフォルダー名を前置）

`RootPath` は残すが、XML ドキュメントで**「プライマリでなければならない用途」専用**と明記した
（相対パス基準・ターミナル既定 cwd・スナップショットの同一性・Git 既定対象）。名前が短く無害に見えることが
選ばれてきた理由なので、そこに注意書きを置くのが一番効く。

寄せた箇所: `WorkspaceService.ResolvePath` / `AddFolder`、`LspWorkspaceEditPaths`、
`CSharpSignatureRefactoring`、`LspWorkspaceService.ResolveRoot`、`ProblemsViewModel.ToRelativeDir`、
`SearchPanelViewModel.FindOwningFolder`、`WorkspaceSearchService`、`GitRootState`。

`AddFolder` が祖先/子孫のフォルダーを弾く不変条件は、§32.4.3 の「フォルダーごとに言語サーバー1本」が
成立する前提でもある（担当範囲が重ならない）。コメントで結び付けてある。

**残り（未着手）**: `RootPath` 67 箇所の棚卸し（「本当にプライマリでよいか」の分類）は範囲が広いので分けた。
