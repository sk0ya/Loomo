採用: **カスタムタイトルバー + ActivityBar/Sidebar + 自由配置のペイン群（AI もペインの1つ）**

### レイアウト実装方針
- メイン領域は **レイアウトツリー**（`PaneNode` = リーフ `PaneLeaf`／スプリット `PaneSplit`）で保持し、`PaneHost`（Grid）を
  `RebuildPaneLayout` がツリーから動的に組み立てる。スプリットごとに行/列 Grid を生成し、ペイン本体を再ペアレントする
  （同一ウィンドウ内なので WebView2 等は生存）。詳細は §21。
- 各ペインは **ドラッグで 2D 並べ替え**（ドロップ先の辺を半透明プレビューで表示。WebView2 の airspace を越えるため
  最前面 `Popup` で描画）、**GridSplitter でリサイズ**、**タイトルの「—」で非表示**（タイトルバーのトグルで再表示）。
- 既定レイアウトは `[Editor | (EditorSupport:隠) | Browser]`（上段）/ `[Terminal]` / `[(AI:隠)]`（縦積み）。
- **2つの表示モード**：通常の **タイル（レイアウトツリー）** と、1ペインを全面に立てる **ソロ（舞台＋袖＋俯瞰）**
  をタイトルバーで切替（§26）。ソロはツリー（`_root`）に触れず表示だけ差し替えるので、レイアウトへ戻すと元配置に復帰。
- 名前付きレイアウトの**保存・巡回**（Ctrl+T）に対応（`ShellWindow.Layouts.cs`）。
- サイドバー切替は `ShellViewModel.ActivePanel`、開閉は `IsSidebarVisible`（列幅と GridSplitter を code-behind で切替）。
- 配色は `Themes/Palette.<Theme>.xaml`（ブラシのみ）に分離し、角丸・余白・スタイル類は `Themes/Controls.xaml` に
  集約する。テーマの一覧は `Core.Models.AppTheme`（暗色系＋明色系。列挙子とファイル名が一対一）を参照。
  スタイルは色を `DynamicResource` で参照するため、`ThemeManager` がマージ辞書のパレットを差し替えるだけで
  全 UI に即時反映される。
  - **新テーマの追加手順**：`AppTheme` に値を足す → 同名の `Palette.<名前>.xaml` を作る（キーは `Palette.Dark.xaml`
    と一対一。過不足は `PaletteResourceTests` が検出する）→ `AppearanceViewModel.Themes` に代表色つきで1行足す。
    明色テーマなら `AppThemeExtensions.IsLight()` にも追加する（テーマ切替に追随しない外部コントロール
    ＝TSV グリッド等へ明暗どちらの配色を渡すかの判定に使う。こちらも同テストが背景色の明度と突き合わせる）。
    明色テーマの `AccentHover` は暗色テーマと逆に **暗く**する（明るくすると `AccentFg` の白文字が読めなくなる）。
- アクセントカラーは `ThemeManager` が `Application.Resources` 直下に `Accent` / `AccentHover` / `AccentFg` を置いて
  パレット定義を上書きする（マージ辞書より直下キーが優先。`AccentHover` は自動で明色化、`AccentFg` は輝度から白/黒を選択）。
  空ならテーマ既定へ戻る。
- テーマ／アクセントの選択は **外観（Appearance）パネル**（ActivityBar の 🎨）で行い、AIプロバイダ設定（⚙）とは分離。
  どちらも `settings.json` に永続化される。

### FolderTree の右クリックメニュー（2026-08-10 整理）

項目が増えて一続きの平坦な並びになっていたので、**グループ＋区切り線**へ整理した。並びは
「作る → 移す → 直す → 開く/送る → フォルダーを見る → 写す → Git → ワークスペース → AI」
（`FolderTreeView.xaml` の `DockPanel.ContextMenu`）。

- **入口をまとめる基準**は「その道具立てがどれか」。トップレベルは**頻度が高く対象を選ばない**操作、
  サブメニューは**ドメインのかたまり**（Diff／Git／パス／AI／ピン留め切替）。深い入れ子は増やさない
  ——エクスプローラーやターミナルへの「送る」は §24.3 の主動線なので、1階層に置いたままにする。
- **`.gitignore に追加` は Git のサブメニューへ移した**。Git リポジトリでしか意味を持たない操作なのに
  トップレベルにあり、非 Git のワークスペースでは**黙って何も起きなかった**（`CanAddToGitignore` で
  出し分けるようになった）。ワークスペースフォルダー自身も対象外——自分自身への相対パスは `.` なので
  `./` という無意味な行が入る。
- **区切り線は静的に置き、出し分けは `FolderTreeView.NormalizeSeparators` が行う**。この menu は項目の
  大半が条件付き表示（ファイル/フォルダ・Git 配下・ピン留め済み・AI 暖機済み…）で、WPF は `Separator` の
  表示可否を自動調整しないため、そのままだと「先頭・末尾に線」「線が2本続く」が普通に起きる。
  `ContextMenu.Opened` ですべての出し分けを終えた**最後**に、前後に可視項目がある線だけを残す。
- **`ContextNode` は `ContextMenu` まで遡る**。子メニュー項目の `Parent` は親 `MenuItem` なので、
  遡らないと「選択中ノード」頼みのフォールバックに落ち、親メニューと対象がずれ得る。
- 追加した操作: **複製**（Ctrl+D。同フォルダーへ貼り付けと同じ「 - コピー」規則で一意化）、
  **既定のアプリで開く**（拡張子の関連付け先。エディタペインで開けない PDF・画像・Office の逃げ道）、
  **パスをコピー ▸ フルパス / 相対パス / 名前**（貼り付け先で欲しい形が違う。相対パスの基準は
  **所属するワークスペースフォルダー**で、表示中ルートではない——ピン留めの状態でコピー結果が変わると
  貼り付け先での意味が変わるため。マルチルートでプライマリ固定にすると `..\..\` だらけになる）、
  **配下をすべて展開／折りたたむ**（ツールバーのボタンはツリー全体が対象なので、枝1つ版）。
  パス3種と複製・削除・コピー/切り取りは**複数選択をまとめて**扱う（パスは1行1件で載せる）。
- 空き領域のメニューは対象が「ツリー全体／表示ルート直下」に限られるので、すべて展開・すべて折りたたむ・
  更新を足した（項目に効く操作は置かない）。
- **元に戻す／やり直す**（Ctrl+Z／Ctrl+Y）は項目・空き領域の両方に置く（§24.12）。対象は選択ではなく
  「直近のファイル操作」なので、次の一手が無いときは項目ごと隠す。

### ファイル種別アイコン（FolderTree / 検索結果）

行頭のアイコンは **Catppuccin の VS Code アイコン（MIT）の SVG を機械変換したベクター**。拡張子・ファイル名
ごとに形と色が変わる（`.cs`＝C#、`.ts`＝TypeScript、`package.json`＝Node、`Dockerfile`＝Docker …）。
パステルの**線画**で、1 個が色ちがいの線 数本でできている。以前の「コード／設定／マークアップ／画像／文書」の
5 カテゴリ分類は廃止した。

- `tools/icons/gen_file_icons.py` が唯一の生成元。実行するとリポジトリの tar.gz を 1 回取得して
  `src/Loomo.App/ViewModels/FileIconData.cs` を書き出す。**生成物は手で編集しない**。tar.gz は
  `tools/icons/cache/`（gitignore 済み）に置かれる。
- 拡張子・ファイル名の対応表は Catppuccin 側の `src/defaults/fileIcons.ts` をそのまま使う（自前で
  持たない）。多段拡張子（`d.ts` 等）は `Path.GetExtension` で引けないので入れていない。
- **配色はテーマの明暗に連動**する。色は 16 個の意味名（blue / peach / text …）でしか持たず、実際の値は
  暗色用（Mocha）・明色用（Latte）の 2 本のパレットにある。`icons/css-variables/` 版だけが色を
  `var(--vscode-ctp-*)` という意味名で持っているので、そこから形と色名を、`icons/mocha` と `icons/latte`
  から実際の値を取る。切替は `ThemeManager.ApplyPalette` → `FileIcons.UseLightPalette`。
  アイコンは描画済みの `DrawingImage` で `DynamicResource` を経由しないため自動では追随せず、
  `FileIcons.PaletteChanged` を受けた `FolderTreeViewModel.RefreshIcons` が引き直させる。
- 座標は元の `viewBox` から **16×16 へ正規化**する。ほとんどが元から 16×16 なので行列は単位行列になり、
  変換は丸ごと省かれる（行列は重複が多いため別表に一意化し、レイヤーは添字だけ持つ）。
- 描画は `Image` 1 要素（`DrawingImage`）。色ちがいの線が複数あるので `Path` 1 本では描けない。
  `DrawingImage` の大きさは中身の境界で決まってしまうため、**透明な 16×16 の下敷きを 1 枚敷いて**
  境界を固定する（敷かないとアイコンごとに余白のぶん拡大率が変わる）。
- `FileIcons` は **遅延生成＋共有キャッシュ**。`Geometry.Parse` は画面に出たアイコンの線ぶんだけ初回に
  一度走り、`Geometry`/`Pen`/`Brush`/`DrawingImage` はいずれも Freeze して全ノードで使い回す
  （ノードごとには作らない）。形は配色に依らないので暗色・明色で共有し、色が絡むものだけ 2 系統持つ。
- 引き当ての優先順位は **ファイル名まるごと → 拡張子 → 既定のファイルアイコン**。フォルダーは
  **開閉で絵が変わる**（`_folder` / `_folder_open`）。
- ライセンス本文は `src/Loomo.App/Assets/Icons/LICENSE-catppuccin-vscode-icons.txt`（ビルド出力にコピーされる）。

## 21. ペインレイアウト刷新・ブラウザ・複数ワークスペース（2026-06-01 実装完了）

> §4 を全面刷新した実装の記録。「全幅下部 AIバー＋固定 Grid」を廃し、**メイン領域をレイアウトツリーで保持して
> 動的に組み立てる**方式へ移行。あわせて Browser ペイン・各ペインのタブ・複数ワークスペースを導入した。
> 中核ロジックは `ShellWindow.xaml.cs`（code-behind）に集約している。

### 21.1 レイアウトツリーと動的構築
- ツリーは `PaneNode`（基底）＝ `PaneLeaf`（1ペイン）／ `PaneSplit`（行=上下 or 列=左右の入れ子）で表す。
  ルートを `_root` に保持し、`RebuildPaneLayout` が **スプリットごとに Grid を生成**して `PaneHost` を組み直す。
  ペイン本体（`TerminalPane`/`EditorPane`/`BrowserPane`/`AiPane`）は XAML に1つだけ定義し、再構築のたびに生成した
  Grid へ **再ペアレント**する（同一ウィンドウ内なので WebView2/Terminal の HWND は生存）。
- **正規化** `Normalize`：空スプリット除去・子1個のスプリット畳み込み・同方向スプリットのフラット化。
- **既定レイアウト** `ApplyDefaultLayout`：`[Editor | Browser]`（列）/ `[Terminal]`（行）。EditorSupport と AI は
  **リーフを置いたまま `Hidden`**（消すのではなく隠すので、出したときに元の位置・比率へ戻る＝§21.3）。
- 列/行トラックには可視な子だけを割り当て、間に `GridSplitter` を差す。`GridSplitter` 操作後の star 比率は
  `CaptureLayoutSizes`→`CaptureNode` で各ノードの `Weight` に取り込み、保存・再構築で維持する。

### 21.2 ドラッグ並べ替え（スナップ風プレビュー）
- ペインタイトルを掴んでしきい値以上ドラッグすると `BeginPaneDrag`。**WebView2 の airspace を越えて最前面に描く
  ため、透明 `Popup`＋`Canvas`** を被せ、その上でマウス追跡＆プレビュー（ドロップ先ペインの枠＋落とす辺の半分を
  半透明で塗る）を行う。
- `HitTestCell` でカーソル下のペイン矩形を求め、`NearestZone` で最も近い辺（Left/Right/Above/Below）を判定。
  ドロップで `MovePane`→`RemoveNode`＋`InsertRelative`：望む方向が対象の親スプリットと一致すれば兄弟挿入、
  異なれば対象を新スプリットで包む（＝列の片方だけを上下分割できる）。

### 21.3 ペインの表示切替
- タイトルの「—」(`OnHidePane`) でそのペインを隠す。ActivityBar のトグル（▦/✎/🌐/🤖, `OnTogglePaneVisibility`）で
  再表示。非表示はツリーから消さず `PaneLeaf.Hidden` を立てるだけなので、**再表示で元の位置・比率に戻る**。
  可視ペインが1枚のときは最後の1枚を隠さない。
- **ペイン間フォーカス移動（Ctrl+W → h/j/k/l, vim 風）**: `Ctrl+W` でプレフィックス待ち状態に入り、続く
  `h`/`j`/`k`/`l` でフォーカス中ペインの左/下/上/右の隣接ペインへフォーカスを移す（`FocusPaneInDirection`）。
  方向は `HitTestCell`/`NearestZone` と同じ矩形判定でフォーカス中ペインに最も近い隣接ペインを選ぶ。
- **前面表示の配置（`PlacePaneByBehavior`、2026-07-06）**: 「AIへ送る」「ブラウザへ送る」「差分を開く」等の
  結果表示・ファイルを開く・袖ミニチュアのクリックは、対象ペインを前面へ出す操作を **共通関数
  `PlacePaneByBehavior` に集約**し、設定 `LoomoSettings.PaneOpenBehavior`（外観カテゴリのコンボボックス、
  既定 `Main`）で配置を切替えられる：
  - `Main`（従来挙動）：左上のペインと入れ替える。
  - `Sub`：右上のペインと入れ替える（上段が横1枚しか無ければ右へ追加）。右上（サブ）の判定は矩形の実測値
    ではなく**構造ベース**（`PaneLayoutTree.TopRow`/`RightmostVisibleLeaf`/`LeftmostVisibleLeaf`）——矩形が
    未確定なタイミングで下段を誤って選んでしまう不具合を避けるため。
  - `Loop`：常にサブ側に表示する。操作の起点がサブペイン自身なら、現在のサブをメインへ繰り上げてから表示する。
  - **対象ペインが既に画面に可視なら、いずれのモードでもレイアウトの入れ替え自体は行わない**
    （フォーカス移動・内容表示＝AI結果/差分/ファイル内容は従来どおり行う）。非表示のときだけ設定どおりに配置する。
  - `settings.json` は `null` を `Main` として後方互換で読む。

### 21.4 タブ（Terminal / Editor / Browser）
- 各ペインは複数タブを持つ。本体（`TerminalTabView`/`VimEditorControl`/`WebView2`）は専用の ContentHost に重ね、
  アクティブなものだけ `Visible` にする。タブ見出しは各ペイン上部のタブストリップ（横スクロール対応）に表示。
- **ドラッグ並べ替え＋一覧ドロップダウン**（2026-07）：タブをほぼ水平にドラッグすると（縦方向のブレが
  `PaneTabReorderVerticalTolerance`=6px 以内）その場で並べ替え、縦方向にも動かした場合は既存の
  切り離し（別ウィンドウ化）を優先する（`ShellWindow.Detach.cs` の `OnPaneTabPreviewMouseMove` が最初の
  しきい値超えの移動方向で振り分け。一度決まったら同じジェスチャー中は変わらない）。並べ替えは
  コードビハインドの実体リスト（`_editorTabs`/`_terminalTabs`/`_browserTabs`。タブ切替・ワークスペース復元が
  位置参照する）と ViewModel 側の `TabsViewModel` 表示用コレクションの両方を同じ並びに保つ。
  各タブストリップの「▾」ボタンは全タブを一覧表示するドロップダウン（あふれて見えなくなった分も含む）で、
  クリックで直接アクティブ化できる。
- サイドバーの **Tabs パネル**（`TabsViewModel`）が3種のタブを横断一覧化。クリックで該当タブをアクティブ化、×で閉じる
  （`TabActivated`/`TabCloseRequested` を code-behind が購読）。タブのアイコンは `TabIconService` が供給：
  ファイルは Shell アイコン（`SHGetFileInfo`）、ターミナルは pwsh/powershell の実行ファイルアイコン、
  ブラウザは WebView2 の favicon（`GetFaviconAsync`、取得失敗時は Edge アイコン→ベクターのフォールバック）。

### 21.5 Browser ペイン（WebView2）
- `Microsoft.Web.WebView2` を新規ペインとして追加。アドレスバー（URL/検索クエリを `NormalizeBrowserAddress` で解釈、
  localhost は http、ホスト名に見えないもの（空白入り・ドット無しの一語）は Google 検索）・戻る/進む/更新・
  favicon・複数タブに対応。既定 URL は Google。
  - **スキームの判定は「絶対 URI として解釈できるか」ではなく既知スキームの一覧で行う**。URI のスキームは
    ドットも数字も許すので、`localhost:5173` はスキーム `localhost` の絶対 URI として通ってしまい、
    そのままではどこへも遷移しない文字列が返っていた（2026-08 修正）。
  - その裏返しで、**ローカルパスは明示的に `file:` へ畳む**（`C:\notes\a.html` / UNC）。ドライブレターは
    未知スキーム `C` に見えるので、放っておくと `https://C:\notes\a.html` という Uri に載らない文字列になり、
    遷移で例外→`async void` の先なのでアプリごと落ちる。遷移の口も `TryNavigateBrowserCore` 一箇所に絞って
    必ず受け止める（アドレス欄には何でも打てる）。
- `NavigationCompleted`/`FaviconChanged` でタブのタイトル・アイコン・アドレス表示を更新。

#### 21.5.1 道具としてのブラウザ（2026-08）
「他のペインに比べて何もない」状態の解消。実装は `ShellWindow.Browser.cs`（タブとナビゲーション）と
`ShellWindow.BrowserChrome.cs`（ツールバー状態・候補・検索・DL・右クリック）に分け、状態は
`ViewModels/BrowserViewModel.cs`、覚えておく資産は `Services/BrowserLibraryStore.cs` が持つ。

- **`target="_blank"` を同じペインの新しいタブで受ける**（`NewWindowRequested`）。生成した `CoreWebView2` を
  `e.NewWindow` へ渡すので遷移は WebView2 側が行い、opener との結びつきも保たれる。**誰も扱わないと素の
  WebView2 の既定＝ツールバーの無い素っ気ない別窓**になる（`EditorSupportContextLink` に同じ罠の記録がある）。
  切り離しウィンドウ側は、もう1枚の切り離しウィンドウで受ける。`window.close()` は `WindowCloseRequested`
  でそのタブを閉じる。
- **状態が見える**：戻る/進むは `HistoryChanged` で活性が変わり、更新ボタンは読み込み中に停止（×）へ変わる。
  細い不定形プログレスバーと、`SourceChanged`（History API の同一ページ内遷移）まで追うアドレス表示。
  読み込み中フラグは**タブごと**に持つ（裏のタブの読み込みで手前のボタンが変わってはいけない）。
  タブストリップには favicon を出す（`TabIconService` が取得済みで、サイドバーにしか出ていなかった）。
- **ブックマークと履歴**は `%APPDATA%/Loomo/browser.json`（**アプリ単位**。ワークスペースを切り替えたら
  消える資産では道具にならない。ワークスペース固有のタブ構成は従来どおり `WorkspaceStateStore`）。
  ☆／Ctrl+D で付け外し、☰ で一覧、アドレス欄に打つと候補が降りる（`BrowserLibrary.Suggest`：ブックマーク優先、
  スキームと `www.` を飛ばした先頭一致が最上位）。URL の同一判定はフラグメントと末尾スラッシュを無視し、
  クエリは残す。読み込みは遅延（起動時には読まない）。軌跡（§27）と役割が重なるようで別物——あちらは
  「いつどこへ行ったか」の時系列、こちらは「よく行く場所」の頻度つき索引で、用途はアドレス欄の候補。
- **ブックマークバー**（アドレス欄の下の帯）は**根の直下だけ**を1行に並べる（`BookmarkBarItems`）。
  フォルダーは押すと中身を一枚落とす——そこは入れ子ぶんも**平らに**する。帯は「1クリックで届く」ための
  場所で、木を辿るのはブックマーク一覧（🔖）の仕事だから、同じ資産でも深さの扱いを変えてある。
  入り切らないぶんは横スクロールさせず « » で一覧へ回す。
  **表示・非表示**は帯の右クリック・一覧の「バーを表示／隠す」・**Ctrl+Shift+B**・ページの右クリック
  （Loomo）の4箇所からで、`LoomoSettings.BrowserBookmarkBarVisible`（settings.json）へ書き戻すので
  次回起動でも同じ見え方になる。帯は資産の量に関係なく1行ぶんの高さを取るので、**畳めることまで含めて機能**。
  読み込みは遅延のまま——起動時ではなく**ブラウザのタブを実体化した時点**で `PrepareBookmarkBar()` が
  browser.json を読む。
- **ページ内検索**（Ctrl+F）は `CoreWebView2.Find`。件数は `MatchCountChanged`/`ActiveMatchIndexChanged` から。
  古いランタイムには API が無いので、掴んだら二度と試さずバーに理由を出す（黙って何も起きないのを避ける）。
- **ズーム** Ctrl + `+`/`-`/`0`。等倍でないときだけツールバーに倍率が出て、押すと 100% に戻る。
- **ダウンロード**は既定の WebView2 の小窓を止めてペイン内の一覧で見せる（`DownloadStarting` で `Handled`）。
  進捗・中止・完了後の「開く／エディタで／場所」——**次の一手へ繋げる**のが自前 UI の理由。
- **キー**：F5・Ctrl+R（更新）、Alt+←→（履歴）、Ctrl+L（アドレス）、Ctrl+F・Ctrl+G（検索）、Ctrl+D（★）、
  Ctrl+`+`/`-`/`0`（ズーム）。**Ctrl+T と Ctrl+W は取らない**——前者は舞台／レイアウトの巡回、後者はペイン操作の
  プレフィックス（vim 風）で、部屋そのものの動線だから。新しいタブは ＋ ボタンと `tab.newBrowser`
  （設定でキー割当可）、閉じるはタブの × と中クリック。**Shift 付きも取らない**（`Ctrl+Shift+F` は
  アプリ全体の「検索を開く」。Shift を見ないとブラウザにフォーカスがある間だけ検索ペインが開かなくなる）。
  例外は **Ctrl+Shift+B**（ブックマークバーの表示切替）とズームだけ——どちらも他に割り当てが無く、
  ブラウザの慣習どおりで迷いようがない。
- **右クリックからの素材の流れ**（`ContextMenuRequested`。§23.3 の共通語彙「〜へ送る」）：
  選択テキスト→「AIへ送る」「ペグボードへ送る」、リンク→「新しいタブで開く」「別ウィンドウで開く」
  「ペグボードへピン」、ページ→「Loomo」サブメニューに「エディタへ送る（Markdown）」「ペグボードへピン」
  「ブックマーク」「ブックマークバーの表示切替」「ページ内を検索…」「URL をコピー」「外部ブラウザで開く」。
  Chromium 既定の項目は残す。
  - ページの Markdown 化（`Services/BrowserPageMarkdown.cs`）は**ページの中の JavaScript で DOM を歩く**。
    `HtmlToMarkdownConverter` は Mammoth の整形済み XHTML 専用（`XElement.Parse`）で実世界の HTML には通らない。
    ファイル名を `<ホスト名>.md` にしてあるので、そのまま EditorSupport のプレビューにも載る。

#### 21.5.2 拡張機能とパスワード（2026-08）
ブラウザを「素の WebView2」から**普段使いのブラウザ**へ寄せる2点。実装は
`ShellWindow.BrowserExtensions.cs`（プロファイルに触る側）と `Services/CrxArchive.cs` /
`Services/BrowserExtensionStore.cs` / `Services/SavedPasswordStore.cs`（ファイルとネットワーク側）。
どちらも**プロファイル単位の話**（＝アプリ共有の `%APPDATA%/Loomo/WebView2`）で、タブ1枚の都合ではない。

- **拡張機能を有効にする**のは `CreateWebViewCreationProperties()` の
  `AreBrowserExtensionsEnabled`（`ShellWindow.xaml.cs`、UserDataFolder と同じ一箇所）。既定は false で、
  false のままだと `AddBrowserExtensionAsync` は `ERROR_NOT_SUPPORTED` で失敗する。
- **入口はストアを見て「追加」**。ブラウザペインでストアの拡張機能ページを開くと、上端に促しバーが出る
  （LSP の促しバー §30 と同じ流儀）。ページ側の**「Chrome に追加」を押しても同じ導入へ回る**——
  注入スクリプトが**ボタンの文言**で拾って横取りする。ストアのページはカスタム要素で安定した id も class も
  持たないので構造では掴めず、外れたときは促しバーの「このブラウザに追加」が残る、という二段にしてある。
  そもそも**ストアの実物のボタンは WebView2 では何も起こせない**（Chromium の導入 API が無い）ので、
  横取りしなければ押しても黙って終わる。🧩 の一覧にも「拡張機能ストアを開く」を置いた。
  - 促しバーを出す判断は `TryParseStoreDetail`（**ストアのホストに限る**。貼り付けを受ける
    `TryParseStoreId` より狭い——32文字の英字が入っているだけの無関係なページで出さないため）。
    ストアは SPA なので `SourceChanged` でも評価する。見出しの元になる題は遷移完了より後に確定するので
    `DocumentTitleChanged` でも評価し、× で閉じられた拡張機能はそのページにいる間だけ出し直さない。
  - ページ側から届く合図は「入れてくれ」だけで、**入れる対象の ID は URL から取り直す**
    （ページが渡した値で導入先を決めない）。合図の**出どころ（`WebMessageReceived.Source`）も見る**——
    タブの中のどのフレームからも送れるので、見ないとストアのページに載った第三者の iframe が
    **クリック無しに導入を起こせる**。横取りしているのは「使う側が追加ボタンを押した」という出来事であって、
    ページからの依頼ではない。
  - **公開停止・非対応の拡張機能ではストアのボタン自体が無効化される**（uBlock Origin で確認）。
    促しバーがあるので、その場合でも入れられる。
- **導入は crx を自分で剥がす**。`AddBrowserExtensionAsync` は**展開済みフォルダーしか受け付けない**ので、
  ストアの URL/ID → crx を取得（Chrome は `clients2.google.com/service/update2/crx`、Edge は
  `edge.microsoft.com/extensionwebstorebase`。Chrome で見つからなければ Edge も試す）→ `CrxArchive` で
  ZIP に戻して `%APPDATA%/Loomo/BrowserExtensions/<ID>/` へ展開 → 登録、という順に自前で通す。
  URL/ID の貼り付けと、展開済みフォルダーを直接選ぶ経路も残してある（後者は**複製しない**——
  使う側の持ち物で、更新もその場で行われる）。
  - 削除した実体フォルダーは**その場では消せないことがある**（WebView2 が掴んだまま）。記録に無い
    フォルダーを一覧を開くたびに掃除して回収する（放っておくと数十MB が残る）。
  - **「記録が読めないときは何もしない」は読む側だけでは守れない**（2026-08-16 のレビューで発覚）。
    掃除は壊れた記録で止まるようにしてあったが、`Remember`/`Forget` が「読めない＝空」を土台に書き直して
    いたため、**壊れた記録の状態で1件入れる/消すと、その1件だけの readable な嘘**ができ、次の掃除が
    他の展開済み拡張機能をまとめて消す。書く側も `TryLoadRecords` で判断し、読めないなら書かない
    （記録できなかったことは一覧の状態文で言う——黙ると、動くがボタンも設定画面も出ない拡張機能になる）。
  - 掃除は**導入の最中は走らせない**。一覧の取り直しだけでなく**削除経路も**（`Forget(id, cleanFolders:)`）
    ——記録が書かれるのは登録の後なので、展開中のフォルダーが取り残しに見える。一覧の「削除」も
    導入中は押せないようにしてある。
  - 展開は**隣の `<ID>.tmp` へ出し切ってから置き換える**。先に消すと、ダウンロードが途中で切れた crx
    （ZIP が壊れていて `ZipArchive` が投げる）で**入れ直しのつもりが実体だけ失う**——WebView2 には
    登録が残るので、いちばん困る壊れ方をする。掃除はこの `.tmp` を取り残しと見なさない。
  - crx は「小さなヘッダ＋ZIP」。**署名の公開鍵を manifest の `key` へ書き戻す**のが要点で、これが無いと
    ID が展開先のパスから作られ、置き場所を変えるたびに別人になる（設定も権限も失う）。
  - **crx には署名が複数入る**（ストアの crx は発行元の鍵も載る）。先頭の鍵を採ると**ストアと違う ID**に
    なるので、ヘッダの `signed_header_data.crx_id`（＝公開鍵の SHA256 の先頭16バイト）と突き合わせて選ぶ。
    実機で踏んだ（uBlock Origin が `lfoeajg…` で入った）——直したうえで
    `cjpalhdlnbpafiamejdnhcphjbkeiagm` に一致することを確認済み。**ID が合っているとストア側も
    「追加済み」と認識する**（ボタンが「Chrome から削除」に変わる）ので、実機での確認はそこを見ればよい。
  - ストアが署名検証用に入れる `_metadata/` は捨てる（展開済み読み込みでは検証に失敗して読み込めなくなる）。
    ZIP の中の名前は信用せず、`../` や絶対パスは弾く。
- **拡張機能のボタン（ポップアップ UI）はホストが描く**。WebView2 は拡張機能のツールバーを一切描かないので、
  manifest の `action.default_popup`（MV2 は `browser_action`）を読み、`chrome-extension://<ID>/…` を
  こちらのポップアップに載せた WebView2 で開く。**これが無いと Bitwarden や 1Password は「入っているが
  触れない」まま**になる。閉じたら `about:blank` へ戻して裏で動かさない。
  - **大きさは manifest に書かれていない**ので読み込み後に測るが、`documentElement.scrollWidth` は
    **ビューポートより小さくならない**——器の既定値がそのまま返り、いつまでも縮まない。見た目は
    「本文の周りに WebView2 の地の色が広がる」形になる。**本文の矩形**を基準にし、はみ出しているとき
    （ビューポートを超える `scroll*`）だけそちらを採る。
  - `Popup` の窓は**開いた時点の大きさのまま**で、中身を縮めても付いてこない（位置を動かして作り直させる
    手も効かない）。閉じて**次のディスパッチで**開き直すと追従する（同じ呼び出しの中で開き直すと、
    閉じる処理が走り切る前に戻るだけで何も起きない）。中身の WebView2 は使い回すので読み込み直しは無い。
  - 閉じたときの `about:blank` でも**遷移完了は来る**。白紙を測ると器が下限（240×120）まで縮み、
    次に開いたポップアップがその小ささで出るので、**閉じているとき・`about:blank` のときは測らない**。
- **設定画面もホストが開く**（2026-08-16）。WebView2 には `chrome://extensions` が無く拡張機能のツールバーも
  描かれないので、**manifest の `options_ui.page`（古い形は `options_page`）が設定画面への唯一の道**。
  一覧の行に「設定」を置き、`chrome-extension://<ID>/…` を**新しいタブ**で開く（ポップアップの器 400×560 には
  収まらない作りが多く、設定は腰を据えて触るもの）。**アドレスの正規化（`NormalizeBrowserAddress`）の既知
  スキームに `chrome-extension` を足すのが要点**——無いと、開こうとした設定画面がまるごと検索語として
  Google へ流れる。
  - **ポップアップの中の歯車も塞がっていた**。拡張機能はそこで `chrome.runtime.openOptionsPage()` や
    `chrome.tabs.create()` を呼ぶが、WebView2 にはタブもツールバーも**行き先が存在しない**ので押しても
    何も起きない（拡張機能側からはどうにもならない）。`ExtensionPageBridge` を
    `AddScriptToExecuteOnDocumentCreated` で**拡張機能のページにだけ**流し込み、これらを
    `chrome.webview.postMessage` 経由でホストのタブへ回す（ポップアップの `NewWindowRequested` も同じ宛先）。
    差し替えは**無条件**——素の実装が生きているかは中からは判別できず（何も起こさずに返るだけ）、
    両方呼べば二重に開く。実機で確認済み（`openOptionsPage()`・`tabs.create()` ともホストのタブで開く）。
  - 合図を受けるのは**拡張機能のページからのものだけ**（`WebMessageReceived` の `Source` を見る）。
    普通のページから `chrome-extension://…` を開かせる口にしない。行き先も `http(s)` と `chrome-extension`
    に限る。
  - 仕込みは**最初の遷移より先に**済ませる（ドキュメント生成時の仕込みなので、待たずに navigate すると
    その1枚だけ効かない）。タブ側は `EnsureBrowserRealizedAsync` の `PendingUrl` 遷移の前、ポップアップは
    `EnsureCoreWebView2Async` の直後で、どちらも `await` してから遷移する。
  - 実機検証で踏んだ落とし穴：**拡張機能のページでは MV3 の CSP がインラインスクリプトを止める**ので、
    確認用の拡張機能を書くときは `<script src="…">` にする（インラインだと `onclick` が結線されず、
    「ブリッジが効いていない」ように見える）。ブリッジ自体が入っているかは CDP
    （`--remote-debugging-port`、§29）で `String(chrome.runtime.openOptionsPage)` を見れば分かる。
- **パスワードは「保存はされるのに二度と見られない」を塞ぐ**。`IsPasswordAutosaveEnabled` は前から立てて
  あるので保存と自動入力は Edge がやるが、WebView2 では `edge://settings/passwords` が開けない。
  `SavedPasswordStore` が Chromium と同じ手順で読む——`Local State` の `os_crypt.encrypted_key`
  （先頭 `DPAPI` を除いて DPAPI/CurrentUser で解錠）が AES-256-GCM の鍵、`Default/Login Data` の
  `password_value` が `v10`/`v11` ＋ノンス12 ＋本体 ＋タグ16（古い項目は DPAPI 直）。
  - **書き込まない**。Login Data は稼働中の WebView2 が掴んでいて、書き換えはプロファイルを壊す道。
    読むときも実体には触らず一時コピー（`-wal`/`-shm`/`-journal` も一緒に）を開く。個別削除は持たず、
    一括削除だけ `ClearBrowsingDataAsync(PasswordAutosave)`＝**ブラウザ自身にやらせる**。
  - 一覧は開くまで復号せず、閉じたら平文を手放す。**「空」と「読めなかった」は必ず区別する**
    （保存したはずなのに一覧が空、が一番困る）。

#### 21.5.3 Loomo を2つ起動したとき（プロファイル共有の作法・2026-08-18／2026-08-20 改訂）
プロファイル（`%APPDATA%/Loomo/WebView2`）はアプリ共有と書いたが、**共有はプロセスもまたぐ**。WebView2 の
決まりは「同じ UserDataFolder に入る全員が**同一のブラウザ引数**」で、これは同一プロセス内だけの話ではない
——2つ目の Loomo が違う引数で入ろうとすると環境生成が `ERROR_INVALID_STATE (0x8007139F)` で失敗し、
ブラウザペインも EditorSupport も**丸ごと無反応**になる（どちらも失敗を握り潰して静かに諦める作りなので、
症状は「動かない」だけで何も出ない）。引数が揃っていれば複数プロセスで共有して問題ない（実測確認済み）。

- **CDP ポートは生きているインスタンスに必ず合わせる**（`Services/WebViewDebugPort.cs`）。素朴に空きポートを
  選ぶと、2つ目は先行インスタンスのブラウザプロセスが 9333 を listen しているせいで 9334 を選び、上の失敗を踏む。
  控え `%APPDATA%/Loomo/WebView2/debug-port` は**生きている申告（claim）の一覧**（`"<pid> <port>"` の行）で、
  読み書きは排他ロック（同時起動で両方が「誰も居ない」を見ないため）。**生きている claim があれば、空いていなくても
  必ずその番号**を使い、自分の claim を書き足す。空きポート探索（dev サーバーとの衝突回避、§29）が働くのは
  誰も居ないときだけ。
  - 生存判定は「その pid が動いている」**または**「その番号を誰かが listen している」（主が終了しても共有ブラウザ
    プロセスが残っていることがある。WebView2 の CDP は環境によって `::1` にだけ bind するので IPv4／IPv6 は区別しない）。
  - **引き継いだときも自分の claim を書き足す**のが要点。控えを「持ち主1人」にしていた頃は、引き継いだ側が
    持ち主にならず、元の持ち主が終了した瞬間に次のインスタンスからは「誰も居ない」ように見えた——ペインは遅延
    実体化なので、生きているインスタンスがまだ listen していない窓が数分あり、そこに当たると別の番号を選んで
    上の失敗を踏む（2026-08-19 に実機で再現：先行が 9334・後発が 9333 を選び、負けた側の EditorSupport が
    ヘッダーだけ更新されて中身は永久に空、が症状）。
  - 主が死んでも番号を握っている「居残り」の claim は**番号につき1つだけ**残す（無条件に残すと死んだ pid が溜まる）。
- **生成条件（プロファイル・ブラウザ引数・拡張機能）の正本は `Services/WebViewEnvironment.cs`**。ここが立て直しも持つ：
  環境生成に失敗したら**いま listen している番号へ引き当て直して**（`TryAdoptRunningPort`）作り直し、それでも駄目なら
  トーストで知らせる。**黙って諦めない**のが肝——握り潰していたせいで、症状が「ブラウザとエディタ支援だけ何も
  起きない」になり原因に辿り着けなかった。一度でも生成できた後は引数を変えない（同一プロセス内でも縛りは効く）。
- **EditorSupport は WebView2 を作り直せる**（`Views/EditorSupportWebViewController.cs`）。失敗したコントロールは
  捨てて作り直し、1／3／8 秒でやり直す（共有ブラウザプロセスの落ち際や、別インスタンスの立ち上げ最中に当たった
  失敗はその場限りのことがある）。使い切ったらトースト。
- **ブラウザプロセスが落ちたら作り直す**。プロファイルを共有している以上ブラウザプロセスは全インスタンスで1つ
  なので、**他の Loomo の巻き添えでも落ちる**。`CoreWebView2.ProcessFailed` の `BrowserProcessExited` で
  コントロールを捨てて作り直す——EditorSupport（ページごと組み直し）、ブラウザペインのタブ
  （`RebuildBrowserViewAsync`：落ちる前の行き先を `PendingUrl` に預けて張り替え、見ているタブだけ即実体化）、
  切り離しウィンドウ（ブラウザは器の Grid の中身を差し替え、EditorSupport の複製は `RebuildWebView`＋再描画）。
  描画プロセスだけの死は読み直しで戻す。
  - 落ちた後の WebView2 は `CoreWebView2` を**読むだけで** `InvalidOperationException` を投げる
    （null にはならない）。だから `view?.CoreWebView2 is not { } core` は素通りできず、参照した側が丸ごと落ちて
    ペインが空のまま残る——参照は必ず `Services/WebViewSafe.cs` の `TryCore()` に均す（アプリ内の
    `CoreWebView2` 参照はすべてこれ経由）。
- **EditorSupport の一時ページはプロセスごとに別ファイル**（`preview-<pid>.html`、
  `Services/EditorSupportNavigationService.cs`）。置き場所はプロファイルの下＝共有なので、固定名だと
  2つの Loomo が互いの本文を上書きし合う。落ちたインスタンスの置き土産は起動時に裏で掃除する（1日より古いもの）。
- プロファイル配下のパスの正本は `Services/WebViewProfile.cs`（UserDataFolder／プレビュー置き場／ポートの控え）。

#### 21.5.4 他のブラウザからの取り込み（2026-08-25）
ブラウザペインを「素の WebView2」から普段使いへ寄せる最後の一段は、**いま使っているブラウザの中身を持ってくる**
こと。Chrome も Vivaldi も Edge も Brave も Chromium なので、プロファイルの形は WebView2 と同じ——
`Local State`（`os_crypt` 鍵）＋ `Default/` の `Bookmarks`(JSON) / `History`(SQLite) / `Login Data`(SQLite) /
`Network/Cookies`(SQLite)。だから読む手は既にあった（§21.5.2 の `SavedPasswordStore` が
WebView2 自身のプロファイルに対してやっていたこと）。実装は `Services/Chromium*.cs` ＋
`Services/BrowserImportService.cs` ＋ `Views/ShellWindow.BrowserImport.cs`。

**種類ごとに条件が違う**のがこの機能の全てで、一括の「インポート」ボタンにはできない。実測（2026-08-25、
実機の Chrome / Vivaldi / Edge）で確かめた表がそのまま設計になっている。

| 対象 | 読めるか | 相手が起動中でも読めるか | 書き先 |
| --- | --- | --- | --- |
| ブックマーク・履歴 | **常に**（暗号化されていない） | 読める | `browser.json`（VM 経由） |
| パスワード | 従来の `os_crypt` なら読める | 読める | 次回起動時に `Login Data` |
| Cookie | 従来の `os_crypt` なら読める | **読めない**（共有違反） | `CoreWebView2CookieManager` |
| キャッシュ | — | — | **扱わない** |

- **`v20`＝アプリ束縛暗号（App-Bound Encryption）は解けない**。Chrome 127 以降が使う形式で、鍵は Chrome 自身の
  COM サービスが**呼び出し元の実行ファイルを検証してから**しか渡さない。同じユーザー権限でも外から取れないのが
  仕様であり、迂回は他アプリの保護を破ることなので**やらない**。実機では Chrome（passwords 4件・cookies 1700件）と
  Edge（cookies 19件）が全て `v20`、Vivaldi は全て `v10` で **passwords 98件・cookies 3052件が読めた**。
  見分けは `Local State` の `app_bound_encrypted_key` の有無（`ChromiumCrypto.IsAppBound`）と値ごとの先頭3バイト。
  解けなかった件数は**数えて画面に出す**——黙って落とすと「全部移った」と誤解させる。
  - Chrome から**パスワードだけ**は移せる。ブラウザ自身に正規の手続き（`chrome://password-manager/settings` →
    エクスポート、Windows のログイン認証つき）で CSV を書き出させ、それを読む（`ChromePasswordCsv`）。
    列は**見出し行で決める**——位置決め打ちは、ずれた版でパスワード欄に URL が入るという最悪の壊れ方をする。
- **Cookie だけは相手の完全終了が要る**。稼働中の `Network/Cookies` は共有違反で開けない（Chrome・Vivaldi・
  そして自分の WebView2 も同じ。`Login Data` のほうは稼働中でもコピーできる、という非対称が実測で確かめてある）。
  判定は**プロセス名ではなく実際にファイルを開いて**行う（`IsCookieDatabaseLocked`）——常駐設定でバックグラウンドに
  残っている場合を見抜けるのはこちらだけ。できないことは**押す前に**、選択中の相手の但し書きとして出す。
- **Cookie の平文には host_key の SHA-256 が 32 バイト前置されている**（Chromium M118 以降）。剥がさないと
  全ての値の頭にゴミが乗る。**長さで決め打ちせず**、ハッシュと一致したときだけ剥がす——付いていない古い項目の
  頭 32 バイトを削ると値が静かに壊れる。実機の Vivaldi 3052 件が 100% 印字可能文字列で復号できることを確認済み。
- **相手の実体には触らない**。SQLite は必ず一時コピー（`ChromiumDatabaseCopy`、`-wal`/`-shm`/`-journal` ごと）を
  読み、書き戻しは一切しない。取り込みの失敗で**移行元が壊れる**のが最悪の結果なので、そこは形で保証する。
- **パスワードの書き込みは「次の起動」でしかできない**（`LoginDataWriter` ＋ `PendingPasswordImportStore`）。
  `Login Data` は稼働中の WebView2 が掴んでいて書けず、取り込みを操作している瞬間はブラウザペインが動いている
  ＝**必ず**掴まれている。だから「その場で書く」は原理的に成立しない。DPAPI で包んで
  `%APPDATA%/Loomo/pending-password-import.bin` に積み、WebView2 がまだ1つも作られていない
  `App.OnStartup` で流し込む。画面では「入った」ではなく**「次回起動時に取り込みます」**と言う。
  - 結果のトーストは **`shell.Show()` の後**で鳴らす。`ToastService` は購読者がいなければ黙って捨てる作りで、
    購読者（`ToastHostViewModel`）が生まれるのは `ShellWindow` を解決した後——適用した場所で鳴らすと
    成功も失敗も誰にも届かない。
  - `Login Data` が無い（ブラウザペインを一度も開いていない）ときは**DB を自作しない**。スキーマの版まで
    正しく作らないと Chromium 側が作り直しに走り、入れた行ごと消える。素直に断って一度開いてもらう。
  - 重複除けは `UNIQUE (origin_url, username_element, username_value, password_element, signon_realm)` に
    載せる（`INSERT OR IGNORE`）。要素名を Chromium の取り込みと同じく空で揃えることが、そのまま
    「同じサイトの同じユーザーは1件」になる。
- **Cookie は DB へ直接書かず `CookieManager`（正規の入口）に入れさせる**ので、稼働中でも入れられる。
  `Login Data` に入口が無いこととの差がそのまま実装の差になっている。実機で Vivaldi の 3052 行を通し、
  **2648 行が (host, name, path) 一致でそのまま入った**ことを確認済み（2026-08-25）。残りの内訳も
  全て説明が付く——**期限切れ 368**（渡しても Chromium が捨てる）と**セッション Cookie 36**
  （メモリにだけ存在し、そもそも DB に書かれない＝入っていないのではなく見えないだけ）。
  - **区画付き Cookie（CHIPS、`top_frame_site_key`）は持ち込まない**。あれは「どのサイトに埋め込まれている
    ときの Cookie か」まで含めて1件だが、`CookieManager` には区画を指定する入口が無い。区画を落として
    入れると**本来通用しない場所で通る** Cookie ができる（第三者の Cookie が第一者の顔をする）ので、
    数えて伝えるだけにする。実機の Vivaldi では 3052 行のうち 512 行がこれだった。
  - **期限切れも渡す前に外す**。渡しても相手が黙って捨てるので、外さないと「N 件取り込みました」の N が
    実際に入った数と食い違う。
- **`roots` の直下はフォルダーではない**（`ChromiumImportReader.ReadBookmarks`）。`bookmark_bar`／`other`／
  `synced`／`trash` は名前も役割も**ブラウザが決めた決め打ちの入れ物**で、その人が作った整理ではない。
  ここを普通のフォルダーとして1段数えると、相手のブックマークバーに並んでいた整理が丸ごと1枚の中へ潜る——
  Vivaldi の `bookmark_bar` の名前はそのものずばり**「ブックマーク」**なので、帯（§21.5.1）には
  「ブックマーク」という folder が1つ出るだけになり、**フォルダー情報が来ていないように見える**（実測）。
  だから `bookmark_bar` の**子**をこちらの一番上（＝帯に並ぶ段）とし、`trash`（Vivaldi のごみ箱＝
  **その人が消したぶん**）は持ち込まず、`other`／`synced` だけ名前どおりのフォルダーとして受ける。
  - **同じ URL が複数のフォルダーに入っているぶんは、いまは1つに畳まれる**（併合の鍵が URL 単位のため）。
    実測の Vivaldi 838 件のうち 225 件が重複で、畳んだ結果 30 フォルダーが一覧から消えた。置き場所を
    identity に含めると直るが、削除（`RemoveLink`／複数選択削除／☆の解除）が URL 単位である以上
    「1箇所だけ消す」まで揃える必要があるので、**そこまでやるときに一緒に**変える。
- **併合であって置き換えではない**（`BrowserImportMerge`）。取り込みは引っ越しではなく持ち込みで、Loomo で
  溜めたものが消えるのは受け入れられない。ぶつかったときは**多いほう・新しいほう**を採る——訪問回数を
  持ち込みの 1 で上書きすると、アドレス欄の候補順（訪問回数で並ぶ）が静かに劣化する。既存のタイトルも守る
  （自分で付け直した名前が消えるため）。履歴は 500 件まで（`browser.json` は全件を毎回書き直す作り）。
  - **`browser.json` の持ち主は `BrowserViewModel` だけ**なので、取り込み側はファイルへ直接書かない
    （`MergeImported` を通す）。直接書くと、VM が抱えている古い実体が次の保存で取り込みぶんを消し飛ばす。
- **キャッシュは扱わない**。HTTP キャッシュは持ち込んでも当たらないことが多く（検証情報もバージョンも相手のもの）、
  プロファイルを壊す危険だけが残る。「ログインしたままにしたい」という要求の実体は **Cookie** なので、そちらで満たす。
- **Opera は候補に入れない**。あれだけプロファイルの形が違い（`User Data` を挟まず `Opera Stable` 直下）、
  当てずっぽうで拾うと「あるのに読めない」項目が一覧に並ぶ。確かめられる形のものだけを並べる。

### 21.5b トースト通知（非モーダル）
- `Services/ToastService.cs`（静的、`Info`/`Success`/`Warning`/`Error`）が発行口。`ViewModels/ToastHostViewModel.cs`
  がイベントを購読し `Items`（`ObservableCollection<ToastEntryViewModel>`）へ追加、5秒後に自動で消す（手動×でも消せる）。
  `ShellViewModel.Toasts` として公開し、`ShellWindow.xaml` の右下オーバーレイ（`Grid.RowSpan="3"` で全面に重ね、
  内容は右下寄せ）が表示する。
- **使い分け**：ユーザーの決定（Yes/No・OK/Cancel）が要る確認は従来どおり `MessageBox.Show`（トーストは自動で
  消えるため応答を待てない）。単純な結果通知（成功・失敗、ブロックされた操作の説明など）はトーストへ
  順次移行中（2026-07、まずエラー系から。FolderTree の名前衝突・ワークフローのファイル読込失敗・
  エクスポート失敗・コンポーザ準備失敗・ターミナル実行前保存失敗・インタラクティブリベースの候補取得失敗・
  検索パネルの一括置換の完了・ワークスペース削除不可の通知が対象）。

### 21.6 複数ワークスペースと永続化
- タイトルバーの**ワークスペース切替ポップアップ**（`WorkspaceSwitcherView` ＋ `WorkspaceListViewModel`、
  2026-07-31 に ComboBox から作り替え）。作りは**ブランチ切替（`BranchSwitcherView`）に合わせてある**——
  上から「絞り込み＋一覧の表示切替」「一覧」「フッター（ここに無いものを足す）」。
  ただしブランチ側の**同期帯（フェッチ／プル／プッシュ）にあたるものは置かない**——あれは
  「リポジトリ全体に効く、一覧で選んだ行とは無関係な操作」だから固定帯に値するのであって、
  パスのコピー・エクスプローラ・名前の変更は1件に効く軽い操作で、同じ格に並べると重みが嘘になる。
  よって**1件ぶんの操作は全部行の右クリックへ集約**する（切替・ピン留め・名前変更・パスコピー・
  エクスプローラ・一覧から削除。現在のワークスペースの行も一覧に居るので特別扱いは要らない）。
  上に置くのは一覧の見せ方を変えるものだけ、フッターは「この一覧に無いものを足す」＝ワークスペースを増やす
  （ブランチ側の「＋ 新しいブランチ」と同じ位置）。**いま開いているワークスペースへのフォルダー追加は置かない**
  ——一覧に対する操作ではないため。持ち場はエクスプローラの「フォルダーをワークスペースに追加」ボタン。
  - 一覧の行は**1行1件**（名前・最終利用の相対時刻・消えたフォルダの「見つかりません」だけ）。
    並びは**ピン留め→最終利用の新しい順**。**パスと現在のワークスペース名は画面に出さない**——前者は行を2段にして
    出せる件数を半分にし、後者はタイトルバーのボタンと一覧の ● と重複するだけなので、どちらも ToolTip に回す。
    現在位置の ● は文字ではなく `Ellipse`（フォント次第で潰れる）。
  - 絞り込みは名前・パスの部分一致（空白区切りは AND）。キーボードは 絞り込み欄 →↓→ 一覧、Enter で切替、
    Esc で絞り込みクリア／閉じる。
  - フォルダー（ルート＋マルチルートの追加ぶん）は行の下に出す。**行のホバーで現れる「🗂」で1行ぶん**、
    絞り込み欄の隣の「🗂 パス」で**一覧まとめて**（＝パス一覧として読むモード。表示中はアクセント色で点灯）。
    行からパスを外したぶんの逃げ道。常時出す印は置かない（マルチルートの行にも）——名前より印が目立つ
    一覧になるため、ピン留めと同じくホバーで出す。「ルート」の印はマルチルートのフォルダー群にだけ添える
    （1つしか無い行では区別にならない）。**開いた状態は保存しない**（`IsExpanded` はその場かぎり）。
  - フォルダー行の右クリックで、そのフォルダー1つに効く操作（パスをコピー・エクスプローラで開く・
    ワークスペースから取り除く。ルートは取り除けないので無効）。取り除きは、**アクティブなら
    生きている `IWorkspaceService.RemoveFolder` 経由**（`FolderRemoveRequested` → ShellWindow →
    `FolderTreeViewModel.RemoveFolderFromWorkspace`。永続化は `RootStateChanged` → `SaveActiveWorkspaceSnapshot`
    の既存経路）、非アクティブならスナップショットを直接直す。フォルダー行は ListBox の項目にはせず
    見出し行の下に描くので、クリックしてもワークスペースは切り替わらない（`FindRow` が `Tag="folder"` で打ち切る）。
  - 一覧はワークスペースの**親フォルダで階層化しない**。ブランチの `feature/…` と違い、実際のワークスペースは
    `C:\Projects` 直下に集中していて、畳んでも「ほぼ全部入りのノード1つ」にしかならないため。
    整理は絞り込みとピン留めで行う。
  - `IWorkspaceService.AddFolder` は既存フォルダーと同一・祖先/子孫のパスを捨てるので、
    `FolderTreeViewModel.AddFolderToWorkspace` は**追加できたかを bool で返し**、呼び出し側（FolderTree の
    「フォルダーをワークスペースに追加」ボタン）が理由をトーストで出す（以前は黙って何も起きなかった）。
  - **一覧の選択（`SelectedWorkspace`）は切替を起こさない**——矢印キーでたどるたびにワークスペースが
    切り替わってしまうため。切替は `ActivateWorkspaceCommand`（クリック／Enter）だけ。
  - ピン留め（`WorkspaceSnapshot.Pinned`）と表示名（`CustomName`。フォルダ名を上書きせず別に持つ。
    `CaptureInto` は保存のたびに `Name` を実フォルダ名へ戻すため）は**索引（`workspaces.json`）側が正**。
    未読込のワークスペースへ切り替えると `state.json` の実体に差し替わるので、`Activate` がそこで
    索引の値を引き継ぐ（さもないと次の保存で消える）。マルチルートの追加フォルダーも詳細を読まずに
    一覧へ出せるよう `WorkspaceSummary.AdditionalFolders` として索引に持ち、この項目より前に書かれた索引
    （null＝未確認）は一覧を開いたときに一度だけ詳細から拾って書き戻す。
- 状態は `WorkspaceStateStore`（`%APPDATA%/Loomo/workspaces.json` の索引＋`workspaces/{id}/state.json` の詳細）に保存。
  `WorkspaceSnapshot` が
  RootPath・各ペインのタブ（`TerminalTabSnapshot`/`EditorTabSnapshot`/`BrowserTabSnapshot`）・アクティブタブ・
  Editor/Terminal 内部分割（`ViewportNodeSnapshot`：向き・入れ子・比率・表示タブ・フォーカス葉）・トップレベルの
  ペインレイアウト（`PaneNodeSnapshot`）・レイアウトモードの `ActivePane`・`StageSnapshot`（舞台/俯瞰）を保持。
  `workspaces.json` は一覧用の索引で、詳細は `workspaces/{id}/state.json`。`SaveActiveWorkspaceSnapshot` がタブ操作・
  レイアウト変更・終了時に `CaptureInto` でスナップショットを更新して書き出す。
- ワークスペース切替 `SwitchWorkspaceAsync` は現ペインのタブを Detach→対象の保存済みタブ/レイアウトを復元。
  各ワークスペースのライブなタブ集合はメモリ上（`_terminalWorkspaces` 等）にもキャッシュし、再切替で素早く Attach する。
- フォルダを開くと FolderTree のルート・エージェントの作業ディレクトリ（`TerminalService.SetWorkingDirectory`）も同期。

### 24.3 素材の流れ（ペグボード⇄コンポーザ⇄ターミナル⇄エディタ）

**目的**: §23 の作業台（コンポーザ）と道具掛け（ペグボード）を孤立パネルから「ペイン間を流れる素材」へ。

**共通語彙（2026-08-02）**: 素材を動かす操作は、どのペインでも次の5語だけを使う。同じ行為が
「聞く」「調べる」「挿入」「ピン」と言い換えられていたのを揃えたもの（覚え直しを不要にするのが目的なので、
**新しい動詞を足すときは既存5語で言えないかを先に確かめる**）。

| 語 | 意味 | 例 |
|---|---|---|
| **送る** | 素材を別のペインへ渡す（受け側は開くだけで実行しない） | 「AIへ送る」「ブラウザへ送る」「エディタへ送る」「ターミナルへ送る」「コンポーザへ送る」「AIワークフローへ送る」 |
| **開く** | その素材の実体を表示する | 「エディタで開く」「ブラウザで開く」「差分を開く」 |
| **比較する** | 2つの状態を差分で見る | Diff ペインへの経路 |
| **残す** | ペグボードへ置いて後で使う | 「＋ クリップボードを残す」「＋ エディタの選択を残す」「＋ ペグボードへ残す」 |
| **実行する** | その場で走らせる | 「ターミナルで実行」「▶ 実行」 |

なお「ピン留め」は**一覧内での固定**（ペグボードのカード上部固定、ワークスペース/フォルダーの固定）にだけ使う。
「ペグボードへ入れる」意味では使わない（同じ語で2つの操作を指していたため）。

- **ペグボード→ターミナル**: カード右クリック「ターミナルへ送る」＝可視ターミナルのプロンプトへ入力のみ
  （FolderTree「ターミナルへ送る」と同じ流儀。フォルダーは作業場所に設定、ファイルはパスを入力）。
  **複数行はコンポーザへ流す**（プロンプト暴発防止）。
- **ペグボード→コンポーザ**: 「コンポーザへ送る」＝本文末尾へ追記して表示。
- **コンポーザ→ペグボード**: ヘッダー「＋ ペグボードへ残す」で本文を残す（組んだコマンドの再利用）。
- **エディタ→ペグボード**: パネルの「＋ エディタの選択を残す」（`SelectedText`）。
- **ドラッグアウト**: カードはテキスト（file はファイル参照も）としてドラッグ可能（外部アプリへも落とせる）。

### 24.5 アドホック比較（Diff ペインの第3のソース・2026-08-09）

**目的**: §24.3 の語彙表にある「**比較する**＝2つの状態を差分で見る」を、Git とは無関係な
**その場の素材**（クリップボード・選択範囲・ディスク上のファイル）に広げる。「コピーしてきた案は、いま
手元のコードとどこが違うのか」を確かめるのに、いちいち一時ファイルを作って外部ツールへ出す必要をなくす。

- **ソースは `Git` / `比較` の2つ**: Diff ペインのヘッダーのラジオがそれ
  （`DiffSource` 列挙。`DiffSessionViewModel.Source` が正本で、`IsGitMode`/`IsCompareMode` は
  ラジオ用の相互排他プロキシ。false 書き込みは捨てる）。**旧「AI変更」ソースは撤去した**（2026-08-21。下記）。
- **素材は `DiffComparison`**（左タイトル/左本文/右タイトル/右本文＋出どころの `FilePath`）。左＝旧・右＝新。
  差分本体は git パッチではなく素材の全文2つから作る（`DiffFileItem.Comparison` を持つ項目がその経路）。
- **入口（すべて「Diffへ送る」）**。右クリック1回につき **「Diffへ送る」は必ず1項目**——選択範囲用と
  ファイル用で2つ並べると同じ名前が2度出てどちらが何を送るのか読めないため、行き先が複数あるときだけ
  子メニューに畳む（`BuildDiffSendMenu`。行き先が1つならそのまま平の項目にして無駄な一段を作らない）:
  - エディタ（選択あり）→ 「Diffへ送る」＞「選択範囲とクリップボードを比較」／「ファイル全体と
    クリップボードを比較」／「保存済みの内容と比較」（最後のは未保存の編集があるときだけ）
  - ターミナルの選択 → 行き先はクリップボードだけなので平の「Diffへ送る（クリップボードと比較）」
  - エクスプローラー → 「Diffへ送る（クリップボードと比較）」／ファイルを2つ選んで「選択した2つを Diff で比較」
    （先に選んだ方が左＝旧。バイナリは `BinaryFileDetector` で弾く）
  - Diff ペインの一覧 → 行の右クリック「クリップボードと比較」（変更中のファイルの現物と突き合わせる）
- **比較はストックされる（2026-08-09 改訂）**。作った比較は消えず一覧に積み上がり、**閉じるまで残る**
  ——見比べたいものは1件とは限らず（案A・案B・保存前後…）、次の比較を作った瞬間に前のが消えるなら
  「並べて見比べる」ができない。`DiffSessionViewModel._comparisons`（新しいものが先頭）が正本で、
  一覧の各行が1件の比較。**同じ素材を二度送っても増えない**（`DiffComparison` は record ＝値等価で弾き、
  既にある行を選び直す）。閉じる口は3つ：一覧の行末の `✕`、行の右クリック「この比較を閉じる」／
  「比較をすべて閉じる」、ヘッダーの「✕ 比較を閉じる」。閉じたら**その位置の次（無ければ手前）**へ
  選択が寄る（閉じても一覧の同じあたりを見ていられる）。一覧の見出しは比較モードだけ件数を出す
  （`FileListHeader`）。**永続化はしない**のは変わらない。
- **「今どの比較か」は選択中の行**（`DiffFileItem.Comparison` → `CurrentComparison`）。素材を1つ覚える
  作りだと複数ストックに追随できない。一覧は更新のたびに作り直されるので、選び直しは表示名やパスではなく
  **素材の参照**で引く（比較はパスを持たないことがあり、同じファイルの比較を複数積めるため）。
- **比較中の操作**: ヘッダーの「⇄ 左右入替」「クリップボードで再比較」（右だけ今のクリップボードに差し替え）。
  どちらも**積み増しではなく今見ている比較の同じ位置での置き換え**（入れ替えるたびに行が増える・飛ぶと
  見失う）。差分本体の上に**どちらが左でどちらが右か**の帯（`CompareCaption`）を出す
  ——ファイル名では分からないため。
- **Diff 本体の右クリック**（左右並び・統合の両方）: 「この行をエディタで開く」（`DiffRowLineMapper` が
  表示行→新側行番号を求める。git パッチは `@@` から、全文差分は「… N 行省略 …」の畳み込み分も数える）、
  「選択範囲をクリップボードと比較」。
- **自動更新との関係**: git の通知で走る更新は、比較モードでは同じ一覧を返すので何も起きない
  （`RefreshAsync(force)` は比較を作り直す・閉じるときだけ組み直しを強制する）。比較の素材は保持されるので、
  `Git` へ切り替えて戻れば同じ比較が残っている。**永続化はしない**（その場の素材なので終了で消える）。
- テスト: `DiffComparisonTests`（ストックの積み増し・重複の排除・閉じたあとの選択・左右入替の置き換え・
  見出し・表示行→ファイル行の対応）。

#### 24.5.1 「AI変更」ソースの撤去（2026-08-21）

Diff ペインの第2のソースだった **AI変更**（`write_file`/`edit_file` の前後全文をインメモリの
ファイル変更ジャーナルに溜め、そこから差分表示・巻き戻しをする）を**まるごと削除した**。
Diff は §24.3 の語彙で言えば人間が**読む**場所であり、AI の書いた差分は Git の作業ツリー差分として
そのまま読める——同じものを二重に持つ経路（記録の上限・巨大ファイルの取りこぼし・ジャーナル側だけの
巻き戻し・記録クリア）はその分だけ部屋の道具を増やしていた。

消えたもの: `Loomo.Core/Diff/FileChangeJournal.cs`（`IFileChangeJournal`／`FileChangeRecord`）、
`ToolExecutor` のツール成功時の前後全文の記録、`DiffSource.Ai`／`IsAiMode`／`DiffFileItem.IsAi`・`CanRevert`、
`DiffSessionQuery.LoadAi`、`DiffSessionCommandHandler.RevertAiAsync`／`ClearAiChanges`、
ヘッダーの「AI変更」ラジオ・「元に戻す」「記録をクリア」ボタン・一覧の右クリック「AI 変更を元に戻す」。
AI の変更の巻き戻しは Git の「変更を破棄」（行・範囲単位も可）が担う。

**差分の古びを Git 側で塞いだ**（同時）。ジャーナルの `Changed` が消えて自動更新は
`GitService.RepositoryChanged` だけになったが、`GitRepositoryMonitor` が 1.5 秒ごとに比べていたのは
`git status --porcelain=v2 --branch` の**出力テキスト**だけだった。porcelain v2 の行が持つのは HEAD と
index の object id で、作業ツリーの内容は入らない——すでに `1 .M` と出ているファイルがもう一度
書き換わっても出力は1バイトも変わらず、見ている差分が編集前のまま固まる（これは AI に限らず、
**人間がエディタで編集し直したときも同じ**だった。保存で Diff を更新する経路は元々無い）。
署名に変更ファイルの**サイズと更新時刻**を混ぜて（`BuildWorkingTreeStamp`）両方まとめて塞いだ。
stat は変更ファイルだけ・1000件で頭打ち。読めないパス（消えた・引用符付き）は印を付けない＝無変化扱い。
テスト: `GitWorkingTreeStampTests`。

### 24.6 差分本体の構文色（エディタと同じ字句解析・2026-08-09）

**目的**: 差分は「追加／削除」しか色が無く、同じコードをエディタで読むときと**見え方が別物**だった。
Diff は §24.3 の語彙で言えば読む場所なので、読むための色はエディタと揃っている必要がある。

- **字句解析はエディタと同一**（`Editor.Core` の `SyntaxEngine`／拡張子で言語判定）。色は
  `EditorSyntaxColors` が持つ `EditorTheme` のトークン色＝**エディタの配色設定そのもの**で、外観設定を
  変えると `ShellWindow.ApplyAppearanceToOpenTabs` が同じテーマを配り直し、Diff も塗り直す（`Changed`）。
- **旧側と新側は別の文書として解析する**（`DiffSyntaxHighlighter`）。＋行と−行を1本の流れに混ぜると、
  片側にしか無い引用符やコメント開始で**それ以降の行がまとめて壊れる**（消した `/*` のせいで残り全部が
  コメント色）。「文脈行＋削除行＝旧」「文脈行＋追加行＝新」を組み直して別々に解析し、表示行へ配り直す。
- **プレフィックスは剥がして解析し、桁をずらして返す**。統合表示の git パッチ行は `+`/`-`/空白の1文字を
  含み（比較の行は本文そのもの＝`DiffSessionViewModel.UnifiedHasPatchPrefix`）、剥がさずに解析すると
  行頭のキーワードが識別子に化ける。返すトークンは表示行の桁に揃える（描く側で数え直さない）。
- **追加／削除は背景色で示す**。トークン色が乗る行では前景の緑・赤をやめる（前景を潰すと構文色が読めない）。
  ± の別は統合表示の行頭記号・左右の行番号ガター・中央ゲターの帯が担う。
- **色を付けないもの**: git ヘッダ・`@@`・省略マーカー（ソースコードではない）、片側だけの詰め物、
  拡張子から言語が決まらないファイル、出どころのファイルが無い比較、`MaxLines`(10,000) 行超の差分
  （左右の全文表示は1ファイル分の行を丸ごと持つため、組み立てが重くなる手前で頭を打たせる）。
  コンフリクト解消表示（Ours/Theirs）はまだ対象外。
- **Run はまとめる**: 同じ色の隣り合う区間は1つの `Run` にする——1ファイル分の行を一度に組むので、
  記号や識別子ごとに Run を作ると `FlowDocument` の要素数が跳ね上がる。
- テスト: `DiffSyntaxHighlighterTests`（桁ずれ・旧新の分離・色を付けない行・上限）、
  `DiffSessionViewTests`（Run 分割が行の文字列を保つ＝選択・コピーが壊れない）。

### 24.7 選択テキストからソースの場所へ（「エディタへ送る」・2026-08-22）

**目的**: §24.3 の語彙表の「**送る**」を、**その場に出ている文字列**へ広げる。ビルドエラー・スタックトレース・
grep 出力・Git の diff 見出しに出ているパスは、それ自体が宛先である。選んで右クリックすればその行へ着地する
——「エラーを読む→ファイルを探す→行を探す」を部屋の中で閉じる。

- **入口は既存の選択メニュー**（`ShellWindow.SelectionActions.cs` の `AddSelectionMenuItems`）。並びは
  **AIへ送る／ブラウザへ送る／エディタへ送る／Diffへ送る**。ターミナルとエディタの両方の右クリックに出る。
- **読み取れないとき・実在しないときは項目自体を出さない**（`BuildEditorSendMenuItem` が null を返す。
  `DescribeOpenLinkInWindow` と同じ作法——押せるのに何も起きない項目を作らない）。見出しには宛先を出す
  （`エディタへ送る（Program.cs:42）`）。
- **書式の解釈は `Loomo.Core/Files/SourceLocationParser.cs` の1箇所に集める**（純粋関数・UIにもファイルにも
  触れない）。`path:12:5`、MSBuild/C# の `path(12,5): error …`、Python の `File "…", line 12`、
  Node/JS の `at f (…:12:5)`、末尾に診断文が続く `path:12:5: error: …`。引用符・囲み・末尾句読点は落とし、
  複数行を雑に選んだときは**1行目だけ**を見る。**Windows のドライブレター（`C:\…`）を行番号の区切りと
  読まない**のが罠で、`:` の後ろが区切り文字か終端であることまで見て判定する。
- **Git の diff 接頭辞**（`a/` `b/` `i/` `w/` `c/` `o/`）は剥がす候補を作るだけで、**剥がす前のパスが実在すれば
  そちらが勝つ**（`a/` という実在フォルダーを壊さないため）。判断は実在確認をする側が持つ。
- **マルチルート**（`SourceLocationResolver`）: 相対パスの基準は
  ①ターミナルの作業ディレクトリ →②選択元の文書のあるディレクトリ →③その文書を担当するフォルダー
  （`FolderForOrPrimary`）→④`workspace.Folders` の全フォルダー、の順。プライマリだけを基準にすると
  **追加フォルダーのビルド出力から飛べなくなる**。
- **OSC8 ハイパーリンクも同じパーサへ寄せた**（`ShellWindow.Links.cs` の `OnTerminalLinkActivated`。
  旧 `TryResolveFilePath` は削除）。書式の解釈が2箇所に分かれるのを避けるのが目的で、副産物として
  OSC8 の相対パスもマルチルートで解決できるようになった。
- 着地は既存の `OpenPathInEditorAsync`（1始まりの行・列）。ペインの可視化は
  `OpenFileInNewEditorTabAsync` 内の `EnsureEditorPaneForOpenedFile` が担う。
- テスト: `SourceLocationParserTests`（各書式・ドライブレター・引用符・末尾句読点・複数行・接頭辞の
  剥がし／非剥がし／剥がす前優先、cwd 優先・追加フォルダー・文書基準・絶対パス・不存在・フォルダー除外）。

### 24.8 ディスク上の更新に追いつくプレビュー（EditorSupport の自動リロード・2026-08-22）

**目的**: EditorSupport ペインの**非対称**を解消する。Markdown プレビューは編集中の本文へその場で追従する
（`IEditorSupportIncrementalHtmlProvider.RenderBody`）のに、ファイルを `file://` で直接開く提供者だけが
取り残されていた——`.html` を直して保存しても表示は古いまま、手で開き直すまで動かない。外部のツールが
書き出す `.html`／`.pdf`／`.svg` も同じで、部屋の中に出しているものが現実と食い違ったまま残る。
「直したものがそこに出ている」は §24 の言う場所としての信頼そのものなので、ディスク上で変わったら
黙って読み直す。VS Code 1.133 の "Auto-reload HTML files in the integrated browser" 相当。

- **読み直すかどうかは提供者が宣言する**——`IEditorSupportUriProvider.ReloadOnFileChange`（既定 `false`）。
  `BrowserEditorSupport`（`.pdf .svg .html .htm .xhtml .mht .mhtml`）だけが `true`。ホスト側に拡張子の
  一覧を持たせない（二重に持つと必ず片方が古くなる）。**ファイル直開きだから読み直してよい、ではない**のが
  この宣言の意味で、`MediaEditorSupport` は `false` のまま（読み直すと再生中の動画が頭出しへ戻る＝事故）、
  `PochiEditorSupport` も `false`（図面の中身はページ読み込みではなく**ブリッジ**（`hostDoc`）で渡している
  ので読み直しても新しい内容は出ず、描きかけのキャンバスと取り消し履歴だけが飛ぶ。しかも `.pochi.json` は
  そこでの編集が保存で書き戻る先なので、自分の保存で自分の編集を巻き戻しうる）。
- **急所は `ShowUri` の `IsShowing` 短絡**。遷移の唯一の口 `EditorSupportWebViewController.Show` は、
  同じ URI を**読み終えて**載せていれば再ナビゲートを省く（§26.9 の同一性判断）。つまり
  `InvalidateEditorSupport()` をいくら投げても**何も起きない**——描画は組み上がって同じ URI に落ち、
  そこで捨てられる。だから明示的なリロード経路 `ReloadShowing(uri)` を足した。中身は初回描画の
  取りこぼし対策と同じ `ReloadCurrentPage`（ページの同一性は保ったまま `Reload()`＋応答監視タイマー、
  例外なら `Fail()`）で、HTML の再生成も一時ファイルの書き直しも通らないうえ、**失敗の畳み方が既存経路と
  ずれない**のが選んだ理由。`_page` の同一性を捨てて `ShowUri` へ流し直す手もあるが、同一性を捨てるのは
  失敗経路の作法（§26.5）で、成功しているページに使うと「同じページの二度目の失敗では止める」記憶まで
  巻き添えにする。載せていない（読み込み中・失敗後・別ページ）なら `false` が返り、そのときだけ
  `_editorSupportForceFullPage` を立てて通常の描画経路へ回す。
- **監視は 1 ファイルぶんだけ**（`Services/SingleFileWatcher.cs`）。`FileSystemWatcher` は単一ファイルを
  直接監視できないので、**親ディレクトリ**を `IncludeSubdirectories = false` ＋ `Filter = ファイル名`で張る。
  **再帰監視は絶対にしない**——このリポジトリは再帰監視で実際に足を撃っている（`DebouncedFolderWatcher` の
  コメント）。`.git` まで見張ると `git status` が `.git/index` を書き換えるたびに監視が発火して再読込が走り、
  また git を読む、という自己フィードバックループになって UI スレッドを刻み続けた。1ファイルを出すために
  リポジトリ全体を見張るのは、その危険を負ったうえに隠れている間もずっと払う無駄でもある。
- **デバウンス 250ms**。エディタの1回の保存は「切り詰め→書き込み→属性更新」のように複数イベントへ割れる。
  発火はスレッドプールなので、通知は必ず生成時の `Dispatcher` 経由で UI スレッドへ渡す。
- **見張るのは「いま出している 1 ファイル」だけ**（`Services/EditorSupportAutoReload.WatchTarget`）。
  対象が変われば張り替え、URI 提供者でない・宣言が `false`・ペインが見えていない、のどれかなら止める。
  **取りこぼしより「張りっぱなし」を避ける**——見えていない間の更新は、次に表示されたときの通常の描画で
  拾われる。張り替えの呼び出しは `InvalidateEditorSupport`（追従元・提供者が変わる合図）と
  `RebuildPaneLayout`／`RebuildStage`（見え方が変わる合図）と追従元の切り離しの3系統からで、
  判断は毎回 `CanRenderEditorSupport()` から取り直す冪等な関数なので、どこから呼んでも結論は同じ。
  同じ対象への呼び出しでは `FileSystemWatcher` を作り直さない（作り直すと入れ替わりの瞬間を取りこぼす）。
- **読み直すのは UI スレッドで、いま実際にそのファイルを出しているときだけ**
  （`EditorSupportAutoReload.ShouldReload`）。監視の発火からデバウンスを経て通知が届くまでの間に
  追従先が変わったりペインが隠れたりするので、**判断材料はそのときの状態から取り直す**。
- **切り離しウィンドウ（`Detach/DetachedEditorSupportView`）も対応する。**プレビューを別ウィンドウへ出すのは
  「見ながら直す」ためで、そこだけ古いままだと本体と食い違って見える。判断は同じ2つの関数を通し、
  監視の張り替えは `RenderAsync` の1か所（描画は表示・追従先・提供者が変わるたびに走る）。読み直し手段だけは
  違って、複製側は `IsShowing` の短絡を持たず**毎回 `Navigate` する**ので `Refresh()` をそのまま頼めばよい。
  画面から外れている間（`Unloaded`）と破棄時は止める。
- テスト: `EditorSupportAutoReloadTests`（宣言した提供者だけ見張る・Media/Pochi は見張らない・非 URI 提供者は
  対象外・非表示なら見張らない・綴り違いの同じパスは同一視・別ファイルでは読み直さない・通知が届くまでに
  追従先が変わった／ペインが隠れた場合は読み直さない・宣言を下ろせば両方効かない）、
  `SingleFileWatcherTests`（複数イベントを1回へ畳む・破棄で保留も捨てる・張り替えで前のファイルを見なくなる・
  親フォルダーが無ければ監視を持たない・同じ対象では作り直さない）。**実発火に依らせない**ため、
  判断は純粋関数へ切り出し、監視側は時計（デバウンス幅）と UI スレッドへ渡す手段を注入できるようにしてある。

### 24.9 意味的な選択の拡大／縮小（`selectionRange`・2026-08-22）

**目的**: 「いま読んでいるかたまり」を、字数ではなく**構文木**で掴めるようにする。キャレットから
`識別子 → 式 → 引数リスト → 文 → ブロック → メソッド → クラス` と広げ、縮小で**来た道をそのまま**戻る。
VS Code の `Shift+Alt+→` / `←`、Neovim 0.12 が内蔵化した `textDocument/selectionRange` と同じもの。
選ぶ操作は「AIへ送る」「ブラウザへ送る」「エディタへ送る」（§24.3／§24.7）や
リファクタリングの範囲指定（§32.4.1）の**入口**なので、ここが手作業だと後ろの動線が全部ぶれる。

- **出発点は「口はあるのに呼び出し元がゼロ」だったこと。** `LspDocumentHandle.RequestSelectionRangeAsync`
  （`Services/Lsp/LspDocumentHandle.cs`）も `ServerSupportsSelectionRange` も実装済みで、Loomo 側からの
  呼び出し元は**1つも無かった**。※死んでいたわけではない——`ILspDocument` 越しに **Editor 側**
  （`LspViewBridge` → `VimEditorControl` の `Shift+Alt+→/←`）が使う口である。ただしその実装は
  **Vim の `Normal/Visual` モード限定**で、(a) **Loomo の既定は `Vim.Enabled = false`**（Vim 無効時の
  エンジンは常時 `Insert` を装う。ホストにテキストキャレットを描かせるため）なので**既定では一度も
  発火せず**、(b) Vim を入れていても**編集中＝ Insert モードでは死んでいる**。「読みながら掴む」操作が
  モードで消えるのは道具として使えない。これが「Editor に属するものを Loomo へ複製しない」
  （§31.2 原則3）を承知のうえでホスト側に置いた理由で、あわせて Vim の入／切とモードに関係なく
  同じ挙動になり、コマンド Id（§31.2 原則6）と日本語の理由表示が付く。
- **置き場所はホスト。** LSP セッションの所有者は Loomo（§30）で、`foldingRange` を使う
  `ShellAppearanceCoordinator` や `codeAction` を組む `ShellWindow.Refactoring.cs` と同じ立場。
  配線は `Views/ShellWindow.SemanticSelection.cs`、判断は `Services/SemanticSelection.cs`
  （`SelectionSpan` / `SemanticSelectionChain` / `SemanticSelectionStack`）。
  **Editor ライブラリは変更していない**——既存の口（`LspDocument` / `SelectionAsLspRange()` /
  `SelectRange()` / `Caret` / `ShowStatusMessage()`）だけで足りる。
- **拡大は「いまより真に大きい範囲」だけを選ぶ。** サーバーが返す連鎖の先頭は「キャレットを含む最も内側」
  なので、すでにその範囲を選んでいると**先頭＝現在の選択そのもの**になる。`Contains`（同一を含む）で
  選ぶと同じ範囲を選び直して「押しても何も起きない」になるため、`StrictlyContains` で
  **現在の選択を真に含む最初の祖先**まで `Parent` を辿る。選択が無ければ連鎖の先頭（＝最も内側）。
  これ以上広げられなければ何もしない。
- **来た道はスタックで保証する**（`SemanticSelectionStack`）。縮小は連鎖を辿り直さず、**積んだ範囲へ戻す**。
  捨てる条件は3つで、ここが緩むと「縮小したらまったく関係ない範囲が選ばれる」という一番不快な壊れ方をする:
  対象が変わった（**ビュー参照** ＋ 文書 URI。分割ビューでは同じファイルが2枚出るので URI だけでは足りない）、
  **本文が編集された**（LSP 文書の版＝`ILspDocument.Version`。`didChange` のたびに進む）、
  **利用者が自分で動かした**（いまの選択が積んだ一番上と一致しない／起点にいるときはキャレットが起点から動いた）。
  連鎖もスタックが持つので、2段目以降の拡大でサーバーへ往復しない（同じ起点・同じ本文なら答えは変わらない）。
- **罠: 適用した範囲と読み戻した範囲は一致しない。** `SelectRange` は終端を含まない半開区間として受けるので
  LSP の range をそのまま渡してよいが、エディタは内部で**終端を含むセル範囲**として保持し、
  `SelectionAsLspRange()` はそこから戻す（`Editor.Core.Lsp.EditorSelectionRange`）。**行頭で終わる範囲**
  `(el,0)` は往復すると前の行の行末 `(el-1,len)` になる——ブロックやメンバー宣言の範囲はまさにこの形。
  1つに畳むと、「祖先探しの基準」か「利用者が動かしたかの判定」のどちらかが必ず壊れる（前者を読み戻した形で
  やると、外側の範囲が読み戻した内側を真に含むので**同じ段をもう一度選ぶ**）。だから1段につき
  `Applied`（＝次の祖先を探す基準）と `Observed`（＝一致判定の基準）の**両方**を積む。
- **非同期結果は世代管理する**（§31.2 原則5）。応答を待つ間に文書・本文・キャレット・フォーカスされた
  ビューが動きうるので、`_semanticSelectionGeneration` に加えて「同じビューか・同じ URI か・同じ版か・
  選択とキャレットが動いていないか」を戻ってきた時点で取り直して照合し、**古い応答で選択を書き換えない**。
- **使えないときは黙らない。** LSP 未接続、サーバーが `selectionRange` 未対応、この位置では範囲が返らない、
  これ以上広げられない／縮められない、戻れる範囲がない——すべて `ShowStatusMessage` で理由を出す。

- **キーは `Shift+Alt+→` / `Shift+Alt+←`**（VS Code 準拠。`editor.selection.expand` /

- **パレットと右クリックメニューからも同じ実装へ**（§31.2 原則6）。パレットは
  `BuildPaletteCommands` の「エディタ」カテゴリ（パレットの一覧は `CommandCatalog` から自動生成されるのでは

- **対象はフォーカスされているエディタ。** `Keyboard.FocusedElement` から視覚木／論理木を遡って

- テスト: `SemanticSelectionTests`。連鎖から次を選ぶ側（先頭が現在の選択と同じ／内側なら真に大きい祖先まで
  飛ばす・選択が無ければ最も内側・これ以上広げられなければ null・空の連鎖／1点だけの連鎖／同じ範囲の
  連続段／途中の空範囲）と、来た道の側（拡大→拡大→縮小→縮小で来た道を戻る・全部戻すと起点のキャレット・

### 24.10 Markdown 差分のレンダリング表示（2026-08-23）

**目的**: Markdown の差分を**書いた形のまま**読めるようにする。`.md` の変更を読むとき、生のパッチ行は
記法（`|` の表・`#` の見出し・フェンス）と変更（`+`/`-`）が同じ1本の文字列に混ざっていて、
「文書として何がどう変わったのか」がいちばん見えにくい。Diff は §24.3 の語彙で言えば**読む場所**なので、
Markdown のときだけ「テキスト／描画」を選べるようにした。

- **切り替えを出すのは Markdown のときだけ**（Diff ペインのヘッダー、表示形式（左右／統合）の隣。
  `DiffSessionViewModel.CanRenderMarkdown` ＝ Markdown（`MarkdownBlockDiff.IsMarkdownPath`）かつ
  **コンフリクト解消表示中でない**）。他のファイルではトグルごと出さない——押せるのに何も起きない項目を
  作らないのがこのリポジトリの作法（§24.7）。コンフリクト中を外すのは、本文グリッドごと Ours/Result/Theirs へ
  置き換わっていて**押した先に描く場所が無い**ため。逆向きも同じで、**レンダリング表示中は「左右／統合」を
  出さない**（`CanChooseTextLayout`）——押すと差分の読み直しだけが走って画面は何も変わらない。
  **既定は今までどおりテキスト差分**。選択は**セッション内だけ**持ち、設定にも復元にも出さない
  （差分の見方は「今このファイルをどう読みたいか」であってワークスペースの状態ではない）。倒したトグルは
  ファイルを選び直しても倒れたままにしてある（Markdown を続けて見るときに毎回押し直させない）。
- **左右に2つのプレビューを並べない**。**新しい側を本文としてレンダリングし**、その流れの中に
  追加ブロックを ins（緑）・削除ブロックを del（赤・取り消し線）として混ぜる＝**1本の読める文書**にする。
  色は Diff ペイン本体（`DiffSessionView.xaml.cs` の Added/Removed ブラシ）と同じ値を CSS へ写している
  （WebView2 の中ではテーマ資源を引けないため。片方だけ変えると同じペインで追加の緑が2色になる）。
- **要点はブロック丸め**（`Loomo.Core/Markdown/MarkdownBlockDiff.cs`・UI にもファイルにも触れない純粋関数）。
  Markdown を行で切ると壊れる——表の途中で切れば表ではなくなり、コードフェンスの開きだけを取れば
  残り全部がコードになり、リスト項目の継続行だけを取れば宙に浮く。そこで**差分行から旧側（文脈＋削除）と
  新側（文脈＋追加）の2つの文書を復元し、それぞれを独立にブロックへ区切る**（区切りが差分の都合で割れない）。
  そのうえで両側の「変更を含まない・同じ差分行を占める」ブロックを**錨**にして突き合わせ、錨から錨までを
  1つの変更のかたまりとして Removed（旧側）／Added（新側）に吐く。
  - **リストは項目ごと**に切る（1項目直しただけでリスト全体が赤と緑になるのを避ける）。ただし同じリストの中で
    **同じ種別が続くブロックは束ねる**——項目ごとに描くと `<ul>` が項目の数だけ生まれて箇条書きに見えない。
    順序付きリストは、束ねたブロックの先頭項目の番号を**その項目の実際の序数**へ書き換える
    （分割した後続ブロックが 1 から数え直さないように。レンダラは先頭の数字を `<ol start>` にする）。
  - **入れ子の項目を兄弟と読まない**のが実装上の罠だった（`- 親` / `  - 子` の `  - 子` も
    CommonMark の「字下げ0〜3」に収まるので、素直に書くと子項目だけが ins になって親から切れる）。
    リストの字下げより深い行はすべてその項目の中身として扱う。
- **Markdown → HTML は既存のプレビューを再利用**（`MarkdownRenderer.RenderToBody` をブロックごとに呼び、
  器は `MarkdownPage.BuildPage`）。新しいパーサは持ち込まない。差分の色だけを本文先頭の `<style>` で足す
  （プレビュー側の CSS に差分の都合を混ぜない）。組み立ては `Services/MarkdownDiffPage.cs`。
- **差分の元データは既存の経路のまま**。git は**全文コンテキスト**のパッチ（`FullFileContext`。ハンクだけだと
  畳まれた文脈行が抜けて「Markdown として別の文書」になる）を `DiffUtil.FromUnifiedPatch` で差分行へ戻し、
  アドホック比較は素材の全文2つを `DiffUtil.ComputeFull` にかける。
  - **パッチ行の分類は「ハンクの中か」で変える**（`SideBySideDiff.ClassifyPatchLine(line, inHunk)`）。
    綴りだけで見ると、本文の `---` の削除行（パッチ上は `----`）と `+++` の追加行（`++++`）が
    **git のファイルヘッダと判定されて行ごと消える**。水平線・フロントマターの囲み・setext 見出しの下線が
    黙って落ち、旧側が「`Title` だけの段落」になって `<h2>` が `<p>` として描かれる——本文を再構成する
    この経路では誤りが見えない形で紛れ込むので、`@@` でハンク内を追跡し、中では**先頭1文字だけ**で
    決める（`\ No newline…` はハンクを終わらせないマーカー）。左右並び表示の誤配色も同時に直った。
  - **本文はハンクの中だけ**から拾う。ハンクの外の行（`diff --git`、git が返したエラーメッセージ）を
    文脈行にすると `fatal: …` が `atal: …` として文書へ紛れ込む。
- **頭打ち**は構文色と同じ行数（`MarkdownDiffPage.MaxLines` は `DiffSyntaxHighlighter.MaxLines` を**参照**する。
  値を写すと片方だけ動いて静かにズレる）。超えたらレンダリングを諦め、**理由をその場に出す**（黙って空白に
  しない）。理由は3種類に分ける: 大きすぎる／差分が無い／**差分として解釈できなかった**（ハンクが1つも無い＝
  git のエラーや読み取り失敗の注記。「差分はありません」と言い切ると理由が消える。テキスト差分なら原文が読める）。
- **表示のホストは部屋の他のプレビューと同じ流儀**（`DiffSessionView.MarkdownRender.cs`）。WebView2 は
  `IEditorSupportViewFactory` で作り（`LoomoWebView2` ＝0サイズで落ちない）、生成 HTML は
  `EditorSupportNavigationService` で一時ページへ書いて `page.loomo` から開く（`NavigateToString` の
  約2MB上限を避ける）。mermaid の `assets.loomo`、相対パス画像の `preview.loomo` も同じ仕込みで、
  基準フォルダーは**マルチルート**：`FolderForOrPrimary` でそのファイルを担当するフォルダーから引く。
  **WebView2 はモードを切ったときに初めて作る**——テキスト差分しか見ない間はブラウザプロセスを増やさない。
  一度作ったらセッション中は常駐する（切り離しの複製プレビューと同じ判断。往復のたびに数秒払わせない）。
  ページから出ていく遷移は受けない（本文のリンクを踏んで差分が消え、戻る口も無い行き止まりを作らない）。
  - **リンクは部屋の既存の振り分けへ流す**。ページ側 JS はリンクの既定遷移を止めて `linkClicked` を
    投げるので、繋がないと**本文のリンクが完全に無反応**になる。`DiffSessionView.MarkdownLinkClicked` →
    `ShellWindow.HandleEditorSupportLinkClickedAsync`（URL＝ブラウザ／ファイル＝エディタ）。
  - **タスクリストのチェックボックスは押せなくする**（CSS の `pointer-events: none`）。プレビューでは
    押すとソースを書き換える仕掛けだが、ここは読む場所で書き戻す先が無い——見た目だけ変わって
    「直した」ように見えるのが最悪の見え方（`data-line` もブロック内オフセットなので行が合わない）。
  - **WebView2 を捨てたら仮想ホストの「マップ済み」の記憶も捨てる**（`EditorSupportNavigationService.ResetPreviewHost`）。
    実マップは core に付いているので、ウィンドウ移動やブラウザプロセスの落ちで core を作り直すとマップは
    消えるのに記憶だけ残り、`UpdatePreviewHost` が「同じフォルダーだから」と何もしない＝**同じファイルなのに
    相対パス画像だけ全部壊れる**。EditorSupport 側（`DiscardView`）も同じ穴だったのでサービス側で塞いだ。
  - **読込の世代**は HTML・理由・マップ先を**1つのレコードで運ぶ**（`MarkdownDiffRender`）。別々に置くと、
    割り込んだ古い読込が基準フォルダーだけ別ファイルのものへ差し替える。テキスト差分へ戻すときの
    リセットも世代チェックの内側で行う（外だと、遅れて再開した古い読込が新しい表示を消して真っ白にする）。
- **ブロックレベルの生 HTML は開きから閉じまでで1ブロック**（`ScanHtmlBlock`。CommonMark の HTML ブロック
  相当だが、**対応する閉じタグまで**見て、同じタグの入れ子は数える）。ブロックごとに独立して HTML へ
  変換するので、README でよくある
  `<details><summary>…</summary>` … `</details>` の間で切ると**開いたタグがそのブロックの中で閉じず**、
  以降のブロックがまるごと折りたたみの内側へ入る（差分の大半が見えなくなる）。閉じが見つからなければ
  CommonMark と同じく空行まで。インラインの `<b>` や自動リンクを始まりと読まないよう、タグ名は
  CommonMark の HTML ブロック（type 6）の一覧で絞る。
- **既知の制限（ブロック単位で変換することの代償）**。プレビュー（1文書を通しで変換）とは次の点で
  描画が変わる。どれも「構造を壊さない」ことを優先した結果で、直すには通し変換＋位置対応が要る:
  - フロントマターは `StripFrontmatter` がブロック内で閉じるため取り除かれず、`<hr>`＋段落として出る。
  - `[[toc]]` はそのブロックの中の見出しだけを拾う（文書全体の目次にならない）。
  - 脚注の定義と参照が別ブロックだと、参照が地の文のまま残る。
  - setext 見出し（`Title` と `---`）は段落＋水平線として描かれる。
  - 4スペース字下げのコードは空行でブロックが割れて `<pre>` が2つになる。
  - 閉じていないコードフェンスは、その側の残り全部を1ブロックが飲み込む（以降の錨が無くなり、文書の
    残りが赤＋緑になる）。プレビュー本体の解釈とは一致しているので許容し、回帰に気づけるようテストで固定。
- テスト: `MarkdownBlockDiffTests`（段落・見出し・連続する追加のまとまり・コードフェンス・表・リスト項目・
  項目の束ね・入れ子と継続行・順序付きの番号・水平線／新規／削除／同一／空・全文パッチ経由・
  **本文の `---` 削除／`+++` 追加が落ちないこと・フロントマターの囲みの削除・ハンク外の行を本文にしない・

### 24.11 Git の比較基準（作業ツリー／ブランチ／分岐点・2026-08-23）

**目的**: 「このブランチで自分が入れた変更を全部見たい」に答える。それまで Git パネルと Diff ペインは
作業ツリーの変更を **HEAD（とインデックス）に対して**しか見せられず、`main` を基準にした差分が取れなかった。

- **基準は3つ**（`GitCompareBaseKind`）。**作業ツリー**（既定・従来どおり）／**ブランチと比較**／
  **分岐点と比較**（`git merge-base <選んだブランチ> HEAD`）。選択の正本は
  `GitCompareBaseViewModel`（**Singleton**）で、サイドバー Git パネルのヘッダーと Diff ペインの
  ヘッダーが同じ状態を見る＝どちらで切り替えても**変更ファイル一覧と差分本体の両方**が同じ基準になる
  （`GitRootSwitchViewModel` と同じ共有のしかた）。
- **二点記法（`git diff <base>`）を使う。三点記法（`<base>...HEAD`）ではない**。三点記法は
  「分岐点 ↔ HEAD」で**未コミットの変更を含まない**——「入れた変更を全部」に、まだコミットしていない編集が
  入っていなければ嘘になる。だから分岐点は `merge-base` を自分で解決してから同じ二点記法で引く
  （＝`base...HEAD` ＋ 未コミット分）。
- **未追跡ファイルは基準比較の一覧に出さない**。`git diff` は未追跡を見ないし、まだ git に足していない
  ファイルは「基準に対してこのブランチが入れた変更」ではない（作業ツリー基準では従来どおり
  「バージョン管理外ファイル」として出る）。**リネームは `--find-renames` で1件**にまとめ、
  旧パス付きの `R` として扱う（差分は新旧両方のパスを pathspec に渡す）。
- **一覧の引数には末尾の `--` が要る**。git は「revision かパスか」が曖昧な引数を拒むので、
  `docs` / `main` / `test` のようにブランチ名と同名のディレクトリが直下にあるだけで
  `fatal: ambiguous argument` になる。付け忘れると一覧が空＝**差分があるのに「変更なし」と嘘をつく**
  （`merge-base` 基準は hash なので踏まない＝「ブランチと比較」限定で静かに壊れる）。あわせて
  **pathspec は `--literal-pathspecs`** でグロブを止める（既定では `a[1].txt` の差分に `a1.txt` が混ざる。
  同じ理由で既存の `GitDiffService` の作業ツリー差分にも付けた）。
- **一覧の取得失敗は握りつぶさない**。`GitCompareChanges(Files, Error)` で理由を運び、Git パネルは
  一覧の上、Diff ペインは一覧の空メッセージに出す（基準そのものを解決できなかった理由は
  基準選択 UI 側が出す＝同じ理由を2箇所に出さない）。
- **基準に依る操作／依らない操作を取り違えない**（§24.7 と同じ「押せるのに何も起きない項目を作らない」）。
  ステージ／アンステージ／変更の破棄／行・範囲単位の適用／コミット対象チェック／コミットは
  「作業ツリー vs インデックス／HEAD」の概念であって `main` との比較には**存在しない**ので、
  基準がブランチ／分岐点のときは**項目ごと出さない**（無効化ではない。Diff の「選択した行を破棄」も
  `Visibility` で消す）。判定は純粋な `GitCompareCapabilities.For(kind)` 一箇所で、
  **ビューのゲートもコマンドのガードも同じ record を見る**（`GitPanelViewModel.Capabilities` /
  `DiffSessionViewModel.UpdateCanDiscard` / 各 `[RelayCommand]`）。素の bool を各所に置かない
  ——4番目の種別が来たときに触る場所を1つにするため。ファイルを開く・エディタへ送る・差分を開くは
  基準に依らないので、この record には現れない（常に出す）。
- **既定ブランチの推定**は `origin/HEAD` → `main` → `master` → `origin/main` → `origin/master` の順で
  **実在するもの**（`GitCompareArgs.PickDefaultBranch`）。リモート追跡が無いリポジトリでも壊れない。
- **失敗は黙って作業ツリーへ落とさず理由を出す**。空リポジトリ（HEAD 無し）・基準ブランチ不在・
  merge-base 無し（無関係な履歴）は `GitCompareResolution.Error` として一覧の空メッセージ／
  選択 UI の下に日本語で出る。
- **古い差分が残らないこと**: `GitRepositoryMonitor` のポーリング署名は `git status` の出力と作業ツリーの印
  （§24 の `BuildWorkingTreeStamp`）だけなので、**基準の切替はそこに現れない**。だから
  `GitCompareBaseViewModel.Changed` を Git パネルと Diff ペインの両方が購読して自分で読み直す。
  Diff 側は `DiffFileItem.CompareBaseFile`（基準 ref と変更の組）を一覧の同一判定
  （`DiffSessionQuery.SameFiles`）にも含める——ここを見ないと「基準だけ変えたら一覧の見た目は同じ」で
  早期 return してしまい、古い基準の差分が残る。既知の限界として、**Loomo の外で** fetch して
  リモート追跡ブランチだけが動いた場合は分岐点の変化に自動では気づかない（アプリ内の
  フェッチ／プルは `GitMutationExecutor` が通知するので追従する）。
- **復元**: 選択（種別＋ブランチ）はワークスペースごとに `WorkspaceSnapshot.GitCompare` へ保存する
  （§24.4）。null の旧データは作業ツリー基準。復元は **`FolderTree.LoadRoot`（＝`OpenFolder`）のあと**に
  置く——前だと Git の対象フォルダーがまだ切り替わっておらず候補が空で返り、保存した枝が既定ブランチへ
  すり替わる（起動経路は `deferHydration: true` なので、そこでこそ踏む）。VM 側も、候補が空のうちは
  復元値を捨てず `_desiredBranch` に預けて候補が揃った時点で再適用し、**候補があるのにその中に無い
  ＝本当に消えた枝**のときだけ諦める。
- **候補の差し替えで選択を失わない**: WPF の `Selector` は `ItemsSource` を差し替えると選択をクリアし、
  TwoWay の `SelectedItem` へ null を書き戻す。放っておくとブランチが1本増減しただけで基準が既定へ
  勝手に移るので、差し替え直後に残っている選択を明示的に戻す（`ApplyBranchOptions`）。
  通知の抑止は**同期区間だけ**を包む——await を跨いで抑止すると、git を待っている間の切替操作まで
  飲み込んで「押せるのに何も起きない」になる。
- 実装: `Loomo.Services/GitCompareModels.cs`（種別・選択・解決結果・許される操作）、
  `GitCompareArgs.cs`（既定ブランチ推定と git 引数の組み立て＝純粋）、`GitNameStatusParser.cs`
  （`--name-status` の解析。コミット範囲の一覧と共有）、`GitCompareService.cs`（解決と照会）、
  `Loomo.App/ViewModels/GitCompareBaseViewModel.cs`、`Views/GitCompareBaseView.xaml`。
- テスト: `GitCompareBaseLogicTests`（既定ブランチ推定・引数の組み立て＝末尾 `--`／リテラル pathspec・
  `--name-status` の解析＝追加/削除/変更/リネーム/空白と日本語のパス/壊れた行・基準ごとに許される操作）、
  `GitCompareServiceTests`（実 git：ブランチ不在・空リポジトリ・デタッチ HEAD・無関係な履歴・
  分岐点が相手の変更を出さないこと・未コミットが含まれること・未追跡が出ないこと・リネーム・
  **ブランチ名と同名のディレクトリ**・取得失敗の理由・短縮名の重複除去）、
  `GitComparePanelTests`（一覧と差分本体が両方切り替わる・作業ツリー操作が消える・amend を立てたままでも
  コミットできない・理由が出る（パネルと Diff の両方）・通知・既定ブランチの自動選択・
  消えたブランチの解除・**候補が読めていない間も復元値を失わない**・**候補差し替えで選択が戻される
  Selector の書き戻しに耐える**・リポジトリ切替で選択が残る・更新が割り込んでも最後は新しい基準・
  復元の往復）。Git パネルと Diff ペインには実アプリと同じく**同じ VM インスタンス**を渡す
  （「どちらで切り替えても両方に効く」が本機能の中心的な不変条件なので、配線から守る）。

### 24.12 ファイル操作の取り消し（エクスプローラーの Undo／Redo・2026-08-23）

ツリー（サイドバー）とファイル一覧ペインで行った**作成・名前の変更・移動・コピー・削除**を、
1手ずつ戻せる／やり直せるようにした。エクスプローラーで当たり前にできること（Ctrl+Z）が
部屋の中だけできない、という穴を塞ぐもの——**うっかりを恐れずに整理できる**のが「場所としての信頼」
（§24.4）の一部。

- **履歴は部屋に1本**（`Services/FileOperationHistory.cs`・DI シングルトン）。ツリーとファイル一覧は
  もともと操作の実体を `FolderTreeCommandHandler` で共有している（§26.10）ので、履歴もそこで共有する。
  どちらのペインで行った操作も、どちらのペインからでも同じ順に戻せる。**ペインごとに履歴を持たせない**
  ——「どっちのペインで消したか」を人間が覚えている前提の Undo は使い物にならない。
- **記録はハンドラ、逆操作は履歴**。前向きの操作には検証（名前の妥当性・ワークスペース配下への限定・
  同名衝突の「 - コピー」一意化）が要るが、逆操作は「さっきの状態へ戻す」だけなので確定済みのパスを
  そのまま使う。**ワークスペース配下への限定を逆操作へ持ち込まない**のが要点——外から持ち込んだ
  ファイルを移動で受け入れた直後の Undo（＝ワークスペース外の元の場所へ戻す）が拒否されてしまう。
  限定は「エージェントの手綱」であって、人間が作った直前の状態へ戻す邪魔をするものではない（§10）。
- **削除の Undo は本物のゴミ箱から戻す**（`Services/RecycleBin.cs`）。Windows には復元の公開 API が無い
  （`FOF_ALLOWUNDO` は“元の場所を覚えて捨てる”だけ）。シェル COM の動詞を叩く手はローカライズされた
  動詞名（「元に戻す(&E)」/「Restore」）を名前で探すことになり環境で壊れるので、ゴミ箱の実体
  （`<ドライブ>\$Recycle.Bin\<SID>`）を直接読む：捨てられた項目は本体 `$R…` とメタデータ `$I…`
  （元のパス・削除日時）の対で置かれているので、**元のパスが一致する最新の `$I`** を選び、対の `$R` を
  元の場所へ move して `$I` を消す。同一ボリューム内の move なので中身のコピーは起きない。
  見つからない（ゴミ箱を空にされた・完全削除された）ときは、その理由をそのまま出して**戻さない**。
  逆に「作成／コピーの取り消し」も `Delete` と同じくゴミ箱経由にしてある——**Loomo が消したものは
  必ずゴミ箱に居る**、を一点だけの約束にしておくと、Undo が失敗した後の逃げ道が常に1つに定まる。
- **一括操作は1手**。複数選択の削除、複数ファイルの貼り付け、1回のドロップは `BeginBatch()` でくくり、
  Undo 1回でまとめて戻す（戻す順は記録の逆順——`a→b`／`b→c` のような連鎖を正順で戻すと衝突する）。
- **中途半端に戻さない**。1手ぶんを適用する前に全件を検証し（対象が在るか・行き先が空いているか）、
  1件でも通らなければ何も動かさずに理由を返す。大文字小文字だけを変えた名前の変更（`a.txt`→`A.txt`）は
  「行き先に居るのが自分自身」なので空きとみなす。
- **失敗した一手を履歴から落とさない**。履歴は覗くだけにして、通ってから降ろす（`Step`）。検証で弾かれるのは
  日常的（戻す先に別のファイルが置かれている等）で、そこで一手を失うと「片付けてからもう一度 Ctrl+Z」が
  できなくなるうえ、**次の Ctrl+Z がひとつ前の無関係な操作に効く**。検証を通ったあとに I/O が失敗した
  ときだけは、動かせた分を反対側へ・残りを元の側へ割って置き直す（`SplitStep`）——履歴とディスクが
  食い違ったままにしない。
- **作成のやり直しは中身ごと戻す**。作ったあとにエディタで書いた内容は「作成」の記録には入っていないので、
  Redo が素直に空ファイルを作り直すと**書いたものへ戻る道が無くなる**（Undo で捨てた実体はゴミ箱に居るのに）。
  `Recreate` はまずゴミ箱からの復元を試し、無ければ本来の意味どおり空で作り直す。
- **UI**：ツリー／一覧の右クリックメニューの「元に戻す（削除 3件）」「やり直す（移動「a.txt」）」
  （次の一手が無ければ**項目ごと隠す**・見出しは `Opened` で組み立て）と、**そのペインにフォーカスが
  ある間だけ効く** Ctrl+Z／Ctrl+Shift+Z／Ctrl+Y。エディタの Undo とは別系統なので、ウィンドウ全体の
  ショートカットにはしない。結果は必ずトーストで言葉にする（`元に戻しました: 名前の変更「a.txt」`）
  ——戻した先が今見えていないフォルダー（別ルート・ワークスペース外）ということがあるため。
- **戻した結果はツリーとタブへ即座に流す**（`ApplyHistoryResult`）。移動は `EntryRenamed`、削除は
  `EntryDeleted` を通常の操作とまったく同じ経路で出すので、開いているエディタタブが追従／クローズする。
  監視（`DebouncedFolderWatcher`）任せにしないのは、通常のファイル操作と同じ即時性にするため。
- **持ち越さない**：履歴は最大50手、永続化しない（アプリを閉じたら消える）。パスを記録した先の実体が
  外部で動いていれば、上の検証で止まる。`.gitignore に追加` は**ファイル操作ではない**（中身の編集）
  ので履歴に載せていない。
- 実装: `Services/FileOperationHistory.cs`（履歴・逆操作・一括）、`Services/RecycleBin.cs`（復元）、
  `Services/FolderTreeCommandHandler.cs`（記録）、`ViewModels/FolderTreeViewModel.FileOps.cs`／
  `ViewModels/FilesColumnViewModel.cs`（結果の反映）、`Views/FolderTreeView.*`／`Views/FilesColumnView.*`
  （メニュー・キー）。テストは `FileOperationHistoryTests`（作成・名前の変更・移動・コピー・フォルダーの
  移動・一括・Redo の破棄・行き先が塞がっている／対象が消えている・**失敗した一手が履歴に残る**・
  **作成のやり直しで中身が戻る**・上限・大文字小文字・**実ゴミ箱からの復元**）と `FolderTreeContextMenuTests`（Undo でタブ追従の通知が飛ぶ）。

### 24.13 Git のリモート操作と履歴の検索（2026-08-25）

**目的**: ローカルの Git 操作（インタラクティブ rebase・3-way マージ・ハンク単位ステージ）は揃っている
のに、**リモート側と「探す」が空白**だった穴を塞ぐ。とくに履歴を書き換える手段を持ちながら
**その結果を送る手段が無い**（強制プッシュが無い）のは、道具として噛み合っていなかった。

- **強制プッシュは `--force-with-lease` 固定**（`GitBranchService.PushAsync(force)`）。素の `--force` は
  「自分が最後に見た後に誰かが積んだコミット」を黙って消すが、lease は追跡 ref が自分の知っている
  位置から動いていたら拒否する。リベース・amend・スカッシュの後に押す操作なので、**安全側しか出さない**。
  上流が無い（＝リモートにまだ無い）ブランチには lease を付けない——上書きする相手がいないため。
  入口は「1クリック目には出さない」——同期帯の「▾」メニューとブランチの右クリック（サイドバーは
  プッシュボタンの右クリック）で、確認ダイアログは `Views/GitBranchDialogs.cs` に一本化する
  （同じ操作が2箇所にあるので、取り返しのつかない操作の説明文が場所によって違う、を防ぐ）。
- **絞り込みは git へ押し下げる**（`GitLogQuery` ＋ `CommitLogFilter.ApplyTo`）。以前は読み込み済みの
  ページ（200件）をクライアント側で篩うだけで、**それより古いコミットは何を打っても出てこなかった**。
  作者・本文・日付は `--author` / `--grep` / `--since` として git に渡す。押し下げないのは
  `hash:` と `ref:`（git に対応する絞り込みが無い）と、**16進数に見える素の検索語**（ハッシュ前方一致で
  1件を手繰る使い方を本文検索に化けさせない）。素の検索語は**本文検索**として渡す——git は作者と本文を
  AND で見るので「どちらでもいいから一致」は1回の呼び出しでは表現できず、実際の用途のほとんどが
  件名探しであるため（作者は `author:` か作者ドロップダウンで指定する）。
- **日付の意味のずれは窓で吸収する**。一覧に出しているのは**作成日時**（`%ad`）だが、`--since`/`--until` が
  見るのは**コミット日時**で、rebase を通ると両者はずれる。git へ渡す窓は前後1日広げ、**最終判定は
  表示している日時で**クライアント側が行う（git 側は「そのページを引くか」を決める粗い篩）。
- **作者の選択肢は足すだけで消さない**。作者で絞り込むと一覧はその作者だけになるので、そのつど
  作り直すと選択肢が1件に痩せて**他の作者へ切り替えられなくなる**。スコープ（ブランチ／パス／
  リポジトリ）が変わったときだけ捨てる。顔ぶれが同じなら同じインスタンスを返す（§24.4 の「更新で
  ビュー状態を壊さない」）。
- **ファイル履歴はリネームを追う**（`--follow`）。追わないと「名前を変えた日」で履歴がぷつりと切れて、
  それ以前が無かったことになる。`--follow` は pathspec 1件でしか使えないので**ファイルのときだけ**付け、
  それでも git が拒んだら**外して引き直す**（履歴が丸ごと空になるより、追跡なしで出す方がよい）。
- **読み込みは重なる前提で書く**。絞り込みの再問い合わせ・リポジトリ変更の通知・スコープ切替が
  それぞれ独立に読み直しを呼ぶので、素直に書くと2本が同じ一覧へ追記して**行が二重に出る**。
  世代番号で追い越された古い読み込みを捨て、一覧を空にするのも git から返ってきた後にする
  （先に消すと読み直しのたびに一瞬空になる）。
- **特定リビジョンのファイル**（ファイル履歴中のコミット右クリック）：「この版を開く」（エディタの
  仮想ドキュメント）／「今と比べる」（§24.5 のアドホック比較に載せる＝左右入替や行ジャンプがそのまま
  効く）／「この版へ戻す」（`checkout <rev> -- <path>`。作業ツリーとインデックスだけが変わり、
  **履歴は書き換えない**）。そのコミットに無いファイルは「空ファイル」と偽らず理由を返す。
- **プルの取り込み方**（マージ／リベース／早送りのみ）と**クローン**。クローンは**リポジトリの外で走る**
  唯一の git 操作なので、作業ディレクトリを明示できる入口（`GitCommandRunner.RunInAsync`）を足し、
  タイムアウトも別（30分）にする。取得後はワークスペースへ**追加**する（いまのフォルダーは閉じない）。
- **リモートと上流の管理**：リモートの追加／URL 変更／削除（Git ペイン左下の一覧）、上流の設定／解除、
  **リモートブランチの削除**（`push <remote> --delete`。`git branch -d` では追跡参照が消えるだけで
  リモート側は残るので、別の操作として出す）。`origin/feature/foo` の分解は登録済みリモート名との
  **最長一致**でしか正しく切れない（`GitRemoteRef`）——最初の "/" で切ると `origin/main` という名前の
  ローカルブランチを作ってしまう。
- 実装: `Loomo.Services/GitLogQuery.cs`（引数の組み立て＝純粋）、`GitRemoteRef.cs`、`GitCloneService.cs`、
  `GitBranchService.cs`／`GitDiffService.cs`／`GitHistoryService.cs`（操作）、
  `Loomo.App/ViewModels/GitHistoryViewModel.cs`（押し下げ・世代・作者候補）、
  `Views/GitBranchDialogs.cs`（確認と入力）、`Views/GitSessionView.*`／`GitPanelView.xaml`／
  `BranchSwitcherView.*`（導線）。
- テスト: `GitLogQueryTests`（引数・押し下げの線引き・日付の窓・リモート名の分解・クローン先の名前）、
  `GitRemoteAndRevisionTests`（**実 git ＋ローカルのベアリポジトリ**：リモート CRUD・上流・リモート
  ブランチ削除・amend 後の通常プッシュ拒否と強制プッシュ成功・**他人が先に進めていたら lease が止める**・
  早送りのみの失敗とリベースでの成功・リビジョンのファイル取得／差分／復元・押し下げがページ外へ届く・
  `--follow`・クローン）、`GitHistoryFilterTests`（VM：一覧そのものが絞られる＝git へ渡っている証拠・
  作者候補が痩せない・スコープ切替で引き直す・リネーム追跡・コミットへ手繰るときは絞り込みを外す）。
  実 git を大量に起こすテストは `GitProcessTests` コレクションにまとめて互いに直列化する
  （WPF のビューを組んで描画を待つテストと同時に走ると、CPU を奪って巻き添えで落とすため）。

### 26.3 ステージモード（UI名「集中」＝舞台＋袖＋俯瞰）
> `ShellWindow.Stage.cs` / `ShellWindow.StageCards.cs`。タイトルバーのビュー・スイッチャー内で
> 「集中」「分割」をアイコン付きのセグメント2択にし、選択中の説明を直下に1行だけ出す
> （UI 名に「表示」は付けない。モード名として並ぶので字数が増えるだけ）。
> 「舞台」「袖」は内部概念と説明上の愛称として残すが、通常操作では「メイン画面」「ほかの画面」という結果の分かる語を優先する。

- **新規ワークスペースの既定は「集中」**。既存ワークスペースは各スナップショットに保存された最後の表示モードを
  そのまま復元する（「場所」としての信頼を壊さない）。ビュー・スイッチャーでも既定の「集中」を左、自由配置の
  「分割」を右に並べる。

- **舞台（ステージ）**：1ペインを全面に立てる。**袖（ウィング）**：残りの有効ペインを右端に `VisualBrush` の
  ライブミニチュアとして縮小表示する（袖カードは実コントロールを子に持たず、舞台サイズにレイアウト済みの
  非表示ホストを描くだけ＝袖表示のためにペインを動かさない）。**俯瞰（オーバービュー）**：全カードを一望する
  Exposé 風レイヤ（クリックで舞台へダイブ）。
- レイアウトモード（タイル／`PaneHost`）とは**表示の差し替えだけ**で切替わり、レイアウトツリー（`_root`）には
  一切触れない。レイアウトへ戻せば元のタイル配置・比率がそのまま戻る。
- ソロ中に `FocusPane` が呼ばれると対象が自動で舞台に立つ（AI がファイルを開いた・差分を出した等の既存フローが
  そのまま「舞台の自動転換」になる）。
- 有効セッション集合（`_enabledSessions`）はタイル配置（`_root`）と独立し、通常はより広い。Main に出ている有効
  セッションは Main に、出ていない有効セッションは袖に出る（無効はどちらにも出さない）。
  **新規ワークスペースの既定の顔ぶれは `DefaultEnabledSessions`**（Editor / Terminal / Browser / EditorSupport /
  Git / Diff）＝`ShellWindow.Stage.cs`。`StageOrder` は**並び順**であって既定の顔ぶれではない——ここを兼ねさせて
  いた頃は初手から袖が11枚並んでいた。IDE / TS IDE / AI / 検索 / ファイル一覧は用があるときに呼ぶ面なので
  既定では出さない（ビュー・スイッチャーの目のトグル、コマンドパレット、「AI へ送る」等の導線から出せる）。
  保存済みワークスペースは自分の `EnabledSessions` を復元するので影響を受けない。
- **袖のタブ（すべて／メイン／サブ）**：袖が10枚を超えると一覧として読めなくなるため、袖の顔ぶれを
  タブで絞れる。並びは **すべて → メイン → サブ**、既定は **すべて**（＝従来どおり全部出す。タブを
  足しても既存の見え方は変わらない）。所属は**固定**で、ユーザー設定でもワークスペース状態でもない
  ——`StageModeCoordinator.MainGroup` が唯一の定義：**メイン＝エディタ／ターミナル／ブラウザ／Git**、
  それ以外（エディタサポート／Diff／AI／IDE／TS IDE／検索／ファイル一覧）が**サブ**。
  切り替えるのは「どれを見るか」だけなので、保存するのも選択中のタブ（`WorkspaceSnapshot.ActiveWingTab`）
  だけ。ソロ／レイアウトの両モード共通で効き、`WingCandidates()`（タブで絞る前）と `WingKinds()`
  （絞った後）を分けてあるのが要点——**袖を出すか畳むかは前者で決める**。後者で決めると、選択中の
  タブが空になった瞬間に袖ごと畳まれ、タブに戻れなくなる。
- **袖の列数（設定「外観」→「袖（右端の画面一覧）の列数」）**：1列（既定）／2列。2列は同じ袖幅で倍の
  枚数が視界に入る代わりにカードが小さくなる。行は `ArrangeWingRows` が自前で組む——`UniformGrid` は
  行の高さを袖の高さで等分してカードが縦に間延びし（1列でも起きる）、`WrapPanel` は実効幅の1px差で
  回り込みが変わるため。カード幅は縦スクロールバーぶんと列間の隙間を先に引いてから割る
  （引かないと右端が切れる）。設定は `AppearanceSettings.WingColumns`。**永続化は DTO 経由**
  （`SettingsStore.PersistedAppearance` に足さないと `settings.json` に載らない）で、変更時は
  `AppearanceChanged` → ホストの `RebuildWings` で即時反映する。
- 復元：`StageSnapshot` に Pane / Overview を保持（舞台と俯瞰を開いたまま離れたらそのまま戻る・§24.4）。
  俯瞰復元中は背後のペインへキーボードフォーカスを送らず、内部の現在地だけ舞台ペインへ揃える。
  袖の活動バッジは §24.1。
- **WebView2 は 0 サイズで配置されると落ちる**（`Direct3D11CaptureFramePool.Recreate` が E_INVALIDARG＝
  「パラメーターが間違っています」の `ArgumentException`。握りつぶしてもフレームプールが壊れたまま次のフレームで
  アクセス違反に至るので、**0 を渡さない**しか手が無い）。袖の描画元を組む
  `ArrangeThumbnailSource` は `host.UpdateLayout()` で**ウィンドウ全体のレイアウトパス**を走らせるため、
  組み替え途中のペインが一瞬 0 高さ/0 幅で配置される——ペインを袖へ移した瞬間に落ちていたのはこれ
  （実測ログ：袖構築中に Browser ペインの WebView2 が `360x0` で配置された）。
  対策は `LoomoWebView2`（`WebViewArrangePolicy.Clamp` で配置サイズを 1px 以上に保つ）で、
  アプリ内の WebView2 は**すべて**これを使う。Browser は本体を再配置せず、同じURLを表示する袖専用の
  `LoomoWebView2` をカード内でライブ縮小する。EditorSupport は他のペインと同じ `VisualBrush` のライブ描画元を使うため、
  Browser / EditorSupport とも袖・俯瞰で内容の更新がそのまま反映される。`StageSourceArea` は Main 列だけでなく
  袖まで列スパンし、袖を広げて Main が仮想幅 800px 未満になってもライブ描画元が祖先クリップされない。
  袖幅は 180〜800px（既定250px）で調整でき、ライブ描画元も最大カード幅を下回らない800pxで組む
  （2026-08-01修正）。

### 26.5 EditorSupport の更新パイプライン（2026-08-04 再構成）

**症状**：EditorSupport ペインの中身が古いまま更新されなくなる（アプリ自体は動く）。単発の不具合ではなく、
更新経路の構造が生み続けていた。真因は3つ。

1. **中途半端な適用が残る。** `UpdateEditorSupportAsync` が `await` をまたいで
   「ヘッダーボタン → ビジュアル表示切替 → WebView の pending → タイトル →（await）→ ナビゲート」と
   UI をバラバラに書いており、連番カウンタで追い越しを検出した側が黙って `return` していた。
   結果「タイトルは新しいファイル・中身は前のファイル」がそのまま残る。
2. **要求が消える。** 描けない状態（ペイン非表示）では単に `return` していたので、その更新は失われた。
3. **粘着ガード。** WebView2 側が `_navigatedUri` / `ReadyPageKey` / `_loadingPageKey` を*成功時だけ*
   更新する設計で、`NavigationCompleted` が来なければ状態が `Loading` のまま固まり、
   同じページを二度と読み直さなかった（`2950bb8` の PDF 固着も同型）。

**構造**：

- **入口は `ShellWindow.InvalidateEditorSupport(reason)` ただ一つ。** タブ切替・本文変更・保存・
  ペイン可視化・舞台切替・ピン／スライド切替・キャレット移動・LSP 準備待ちポーリングは全部これを呼ぶ。
- **`EditorSupportUpdateLoop`（`Services/`・UI 非依存）** が同時1本へ直列化する。走行中の要求は畳んで
  完了後にもう一周し、実行中の描画は `CancellationToken` で止める（中断された要求は次周回へ差し戻すので
  取りこぼさない）。**描けない状態なら描かずに要求を保持**＝ dirty フラグ。可視化された時点で必ず1回描く。
- **`EditorSupportFrame`（`Services/`）を1個組み立て、`ApplyEditorSupportFrame` が同期で丸ごと適用する。**
  `await` をまたいで UI を書かないのが規約で、部分適用が型として起こり得ない。中身は
  `WebContent` / `VisualContent` / `OutlineContent` / `PanelsContent` / `NoticeContent` の5ケース
  （`PanelsContent` は構造ツリーを作り直さず②呼び出しパネルだけ差し替える＝折りたたみを保つ）。
  重い処理（`Pipeline.PrepareAsync`・ビジュアル提供者の `UpdateAsync`・LSP 解析）は<b>載せる前に</b>済ませる。
- **WebView2 は明示的な状態機械。** `EditorSupportPageId(Uri, PageKey)` × `Idle/Loading/Ready/Failed` で、
  遷移は `EditorSupportWebViewController.Show` 1か所。失敗経路（例外・ナビゲーション失敗・
  **12秒の応答監視タイマー**）は必ず `Fail()` を通って同一性を捨てるので、次の要求は必ず作り直しになる。
  `ReadyPageKey` は `Ready` のときだけ鍵を返す＝本文差し替え（`setBody`）が成り立つ場合の唯一の定義。
  差し替え先が消えていたら `NeedsFullPage` を返し、ホストが `_editorSupportForceFullPage` を立てて
  ページ全体で組み直す（1回で収束）。同じページの二度目の失敗では再試行しない（無限リトライ防止）。
- **解決は `EditorSupportResolver` 一本。** 「ブラウザで開く」が `EditorSupportRegistry` を直に引いていて
  Hex/コードのフォールバックが抜け落ちていたのを揃えた。
- **ディスク上の更新への追従は §24.8。** `Show` が同じ URI の再ナビゲートを省く（`IsShowing`）ため、
  `file://` 直開きの提供者だけはこの更新ループでは新しい内容へ変わらない。専用のリロード経路がある。

**回帰テスト**：`EditorSupportUpdateLoopTests`（不可視中の要求保持／走行中要求の非喪失／実行中描画の
キャンセル／例外でループが止まらない／描画内からの再要求がちょうど1回で収まる）。可視表現の境界は
従来どおり `EditorSupportRenderPolicyTests`。**残っていた3つの穴は §26.9 で塞いだ。**

### 26.6 LSP 応答の上限時間（2026-08-04）

コードアウトラインの LSP 呼び出しは**すべて上限時間つき**（`CodeEditorSupportAnalysis.RequestTimeout`＝8秒、
`WithLimitAsync`）。documentSymbols / prepareCallHierarchy / incomingCalls / outgoingCalls / references の
5本が対象で、`CancellationToken` も更新ループから通っている。

言語サーバーが黙ると `await` は**永久に戻らない**。以前はそこで描画が止まり、ペインは古い内容を抱えたまま
になっていた（§26.5 の「固まる」の残り半分）。期限切れは「シンボルが無い」とは区別して
`LspNoticeModel.BuildTimeout` の専用案内へ落とす——空アウトラインで出すと、解析が終わって何も無いのか
返事が来ていないのかが利用者に判らない。コールドスタートの構造再取得ループも、期限切れを見たら
打ち切る（応答しないサーバーへ6回×8秒を投げても遅くなるだけ）。キャンセルは期限切れとは別扱いで
`OperationCanceledException` として伝わり、更新ループが次の周回でやり直す。

**回帰テスト**：`CodeEditorSupportTimeoutTests`（無応答→期限切れ報告／応答→素通し／キャンセルは
期限切れではなくキャンセルとして伝わる／期限内なら遅い応答も勝つ）。

### 26.7 ビジュアル提供者＝工場と表示インスタンス（2026-08-04）

`IEditorSupportVisualProvider` は**状態を持たない工場**で、`CreateVisual()` が表示インスタンス
`IEditorSupportVisual`（`View` ＋ `PrepareAsync` ＋ `ContentEdited`）を**呼ぶたびに新しく**返す。
実体の所有者は表示面ごとの `EditorSupportVisualHost`（ペイン本体と切り離しウィンドウが1つずつ持つ）。

直した2つの欠陥：

1. **複製が原理的に不可能だった。** 提供者がビューを1つだけ抱えていた（`GetOrCreateView`）ため、WPF の
   単一親制約でそのビューは同時に1か所へしか載せられず、切り離しウィンドウでは
   「この種類のプレビューは複製に未対応です」と出すしかなかった。表示面ごとに実体を作る形にして、
   CSV グリッド・画像・Hex も複製できるようになった（複製側のグリッド編集も追従元へ書き戻る）。
2. **UI スレッドで重い読み込みができてしまった。** 旧 `UpdateAsync` は「UI スレッドで呼ばれる」としか
   決まっておらず非同期である必要も無かったので、Hex と画像は**同期にファイルを読んでデコードして**いた
   （大きなバイナリで実際に固まる）。`PrepareAsync` は「バックグラウンドで走り、UI へ触れるのは
   戻り値の反映関数だけ」と分けたので、重い処理を UI スレッドへ書く余地が契約から消えた。

検索ハイライトは提供者ではなく表示インスタンス側の口（`IEditorSupportSearchHighlightTarget`）になり、
条件の保持と配布はホストの役目。実体は遅延生成なので、**あとから作られた実体にも**作成時に現在の条件が渡る。

**回帰テスト**：`EditorSupportVisualHostTests`（表示面ごとに別実体／同一面では使い回し／条件が後発・
先発どちらの実体にも届く／編集通知の中継／破棄）。

### 26.8 共有ステータスバーの追従（2026-08-04）

分割しても下端に1つだけ出す共有バー（`EditorSharedStatusBar`）は、**どのエディタも自分の都合で書き込む**
（`VimEditorControl.SyncStatusBar` に「自分が現在のエディタか」の判定は無い）。エディタが自発的に押し出すのは
キーボードフォーカス取得時だけなので、サイドバーのタブ一覧をクリックして切り替えると——フォーカスは一覧に
残るので——誰も押し出さず、前のタブのファイル名・行数が残った（1つ遅れ）。

`ShellWindow.SyncEditorStatusBar` を活性化の2経路（`ActivateEditorTab` / `SetActiveEditorTab`）の両方から呼ぶ。
活性化の最中は再ペアレント・実体化が走り、その過程で**裏になったコントロール**が `UpdateAll` 経由でバーを
書き戻すため、直後の1回では上書きされる（実測）。落ち着いてから（Background 優先度）、その時点でもまだ
アクティブなら押し直す。

**本来の直し方は Editor パッケージ側**で共有バーに「持ち主」を持たせ、持ち主以外の書き込みを届かせないこと。
ここはホストから押し戻しているだけなので、活性化と無関係な非同期処理が後から書き戻す余地は残る。

### 26.9 追い越しの歯止めとページ状態機械の分離（2026-08-07）

§26.5 の再構成後も「固まる」が残った。テストが押さえていたのは**要求が消えないこと**だけで、
**要求が処理され切ること**を誰も見ていなかった——直した3つはすべて「描かれないまま誰も気づかない」で終わる。

1. **追い越しの飢餓。** 走行中の描画は新しい要求で無条件にキャンセルされていたので、
   要求の間隔が描画時間より短いと**永久に一度も描き終わらない**（LSP は1本で最長8秒＝§26.6、
   編集は300ms・キャレットは150msのデバウンス）。歯止めは2つ。**キャレットだけの要求は内容の描画を
   捨てさせない**（本文の組み立てはキャレット移動では古くならず、②パネルは直後の周回で差し替わる）。
   加えて**連続2回追い越したら次の1回は必ず描き切らせる**（要求は `_pending` に残るので直後にやり直す）。
2. **戻ってこない描画に道連れにされる。** `await _render(...)` に期限が無く、WebView2 の初期化や
   巨大ファイルの読み込みが返らないとループは走行中のまま閉じ、以後どの要求も**二度と描かれなかった**。
   キャンセルを伝えたのに `AbandonAfterCancel`（5秒）を過ぎても返らない描画は見限って次へ進む
   （正常な描画に期限は設けない）。
3. **自分以外のトークンのキャンセルを握りつぶしていた。** `catch (OperationCanceledException)` が
   無条件だったため、初期化の打ち切り等で中断された描画が「静かに描かれなかった」で終わっていた。
   自分のトークン由来でなければ他の例外と同じく `onError` へ出す（診断ログに残る）。

**`EditorSupportPageState` の切り出し**：固まる／固まらないを決めているもう半分は WebView2 の状態機械
（本文差し替えが成り立つ条件・失敗の打ち切り）なのに、`CoreWebView2` を抱えたまま `Show` の中にあって
**テストから一切触れなかった**。判断だけを純粋クラスへ移し、`EditorSupportWebViewController` には
WebView2 呼び出しとタイマーを残した（振る舞いは変えていない）。

**`EditorSupportRenderFlow` の切り出し**：描画本体（言語サーバーが未準備・無応答・構造が空・

やはりテストできなかった。抜けなかった理由は描画の**両端**——追従元タブから本文とキャレットを読むところと
UI へ書くところ——が WPF だからで、その両端だけを押し出せば真ん中は素の非同期処理として残る。

- 入力は `EditorSupportRenderRequest`（タブから読む値の**スナップショット**。`await` をまたぐ間に本文も

- `ShellWindow.EditorSupport.cs` は 452行 → 323行。`CaretInfo` 依存も外へ出した
  （`CurrentMemberLine1` / `ShouldRefreshCallPanels` に行・桁を渡す版を足した）。

**回帰テスト**：`EditorSupportUpdateLoopTests` に4本追加（キャレット要求は内容の描画を捨てない／
要求が来続けても飢餓にならない／応答しない描画を見限る／無関係なキャンセルは報告される）、

### 26.10 ファイル一覧ペイン（エクスプローラのペイン化・2026-08-13）

> `Views/FilesPaneView.xaml(.cs)` / `ViewModels/FilesPaneViewModel.cs` / `ViewModels/FilesPaneModels.cs`。
> 列挙の真実は `WorkspaceStateStore.PaneKind.Files`、復元状態は `WorkspaceSnapshot.Files`。

**サイドバーのツリーを置き換えるものではない。** ツリー（`FolderTreeViewModel`）は**階層を把握する**道具、
この面は**集合を処理する**道具——1フォルダーぶんを平らに並べ、サイズ・更新日時・種類で並べ替え、名前で
絞り込み、まとめて選んで動かす。「さっき触ったのはどれか」「何が重いか」はツリーの構造では出せない。
検索がサイドバーとペインの両方に居るのと同じ立て付け（§26.1 の `Search`）で、**両立が正解**。

なぜペインにするか（＝サイドバーの拡張では足りない理由）:
- **サイドバーは7パネルの排他表示**なので、ファイルを触っている間は Git も検索も見えない。整理は
  「一覧を見ながら Git 状態も見たい」作業なので、排他がいちばん邪魔をする場所だった（§24.1 の周辺視野）。
- **面積が要る**。列を持つ表はサイドバー幅では出せない。素材の D&D（§24.3）でも、行高16pxのツリーは
  ドラッグ元として的が小さい。
- **復元の対象になる**（§24.4）。レイアウトツリーに乗るので、現在地・並べ替え・隠しファイル表示が
  `workspaces.json` に入り、開いたまま離れたらそのまま戻る。
- 「エクスプローラーで表示」＝**部屋の外に出る**導線が常設されていたが、その理由の大半（並べ替え・
  絞り込み・一括操作）をここで引き取れる。

**設計上の約束**
- **操作の実体はツリーと共有**する。作成・名前変更・削除（ゴミ箱）・貼り付けは同じ
  `FolderTreeCommandHandler`、クリップボードの受け渡し（ファイルドロップリスト＋`Preferred DropEffect`）は
  新設の `Services/FileClipboard.cs`（ツリー側も同じものへ寄せた）。分けると「切り取りが片方だけ移動に
  ならない」類の食い違いが必ず出る。右クリックの項目名・並び・キー（Ctrl+C/X/V/D・F2・Delete）も
  ツリーに揃える。
- **名前変更・削除は同じ受け口へ流す**。`EntryRenamed`/`EntryDeleted` を `ShellWindow` が購読し、
  ツリーからの操作とまったく同じ経路で開いているエディタタブを追従／クローズさせる。
- **Undo／Redo の履歴もツリーと共有**する（§24.12）。この面で消した／移したものを、ツリー側の Ctrl+Z で
  同じ順に戻せる。
- **現在地はワークスペースフォルダーの中だけ**（`workspace.Contains`）。「上へ」は所属フォルダー自身で
  止まり、パンくずもそこが先頭になる——書き込みが `ResolvePath` でワークスペース外へ出られない以上、
  上を見せても行き止まりにしかならない。ワークスペース外のブラウズ（読み取り＋取り込み）は将来の話。
- **マルチルート**：所属フォルダーは `FolderFor` で決め、相対パスのコピーもそのフォルダー基準
  （プライマリ固定にすると追加フォルダーのファイルが「..\..\」だらけになる・§32.10）。フォルダーが
  2つ以上のときだけ切替行を出す。
- **並びの規則**：フォルダーは常に先（並べ替え列に関わらず）。名前は**数字を数として読む**自然順
  （file2 < file10）。同値のときは必ず名前昇順で決める＝監視更新のたびに並びが揺れない。日時・サイズは
  選んだ直後だけ降順から始める（「新しい方・大きい方を見たい」が普通なので）。
- **絞り込みは持ち越さない**。現在地・並べ替え・隠しファイル表示は保存するが、絞り込み文字列は保存
  しない——あれは今この瞬間の道具で、翌日戻って一覧が虫食いになっている方が事故になる。
- **更新は差分適用**。同じパスの行は既存インスタンスのまま位置と値だけ直す（作り直すと選択と
  スクロール位置が飛ぶ・§UI密度の原則）。監視は `DebouncedFolderWatcher`（`.git`/`bin`/`obj` 等は除外
  ＝§UIジャンクの再発防止）。
- **縦スクロールバーは内容に重ねて描く**（`FilesOverlayScrollViewer`）。レイアウト幅を取らせると、
  スクロールバーの有無で見出しと行の列が 7px ずれる。列幅と右端の逃げ（`FilesRowInset`）は
  リソースに1つずつ置き、見出しと行の両方から引く。
- **詳細表示の列幅は、既定では中身に合わせて自動で決まる**（`ColumnWidthsAreAuto`）。フォルダーを
  開くたびに、名前以外は中身ぴったり・**名前が残りを受け持つ**（余れば広がり、足りなければ名前から
  削る＝名前だけが省略して読める列）。自動のあいだはペインの幅にも追随する。**掴んで動かした時点で
  「ユーザーの指定」**になり、以後そのフォルダーは幅・並び・表示を覚える
  （`FilesColumnSetting`／`FolderColumnSettings`）。自動のままのフォルダーは**覚えない**——開き直せば
  同じ幅になるので、訪れたぶんだけ workspaces.json を太らせない。
- **`GridLength.Auto`（＋`SharedSizeGroup`）ではだめ**：見出しと行は別々の `Grid` なので Auto は
  行ごとにバラバラになり、揃えるには共有スコープが要る。そこまでやっても**実体化された行しか
  測らない**ので、3000件のフォルダーでは先頭で名前列 103px、末尾までスクロールすると 326px——
  スクロールするだけで列が動く（実測）。だから幅は**開いた時点で全行から決めて固定する**。
- 幅を変えるのは**見出しの境目に重ねたつまみ**（`FilesColumnGrip`）で、当たり判定は境目をまたぐ 9px
  ——狙うのは境目の線であって「見出しの右端」ではないので、はみ出させないと掴もうとしたクリックが
  隣の列の並べ替えになる。掴めるところではポインタが ⇔ に変わり、区切り線は常に見えている
  （見えない当たり判定は無いのと同じ）。**ダブルクリックでその列の中身に合わせる**（そこは指定扱い）。
  **掴んでいる間は保存しない**——1px 動くたびに workspaces.json を書き直させず、離した時に1回だけ書く。
  列ツールのポップアップには「幅と並びを既定に戻す」＝自動へ戻す入口を置く。
- **幅の実測**（`FilesColumnView.ContentWidth`）：見出しといま出ている行（絞り込み中は残っている行だけ）
  を測る。**文字の大きさは `Fs*` をその場で引く**——UI の文字サイズは設定で配り直されるので（既定でも
  16px÷13px ≒ 1.23 倍）、`Typography.xaml` の素の数字を焼き込むと**既定の設定ですら測り足りず、
  合わせたはずの列が見切れる**。1行ずつ `FormattedText` を作ると 3000件で列1つ 220ms かかるので、
  ふだんは**グリフの送り幅を1文字ずつ覚えながら足す**（同じ3000件が 4ms）。その書体に無い文字
  （絵文字など＝別フォントで描かれる）を含む行だけ `FormattedText` へ落とす。
- **使える幅の物差しは一覧（`EntryList`）の幅**で、見出しの帯ではない——列がはみ出すと帯の
  `ActualWidth` は「はみ出した合計」を返すので、狭くなったことに気づけない。

**入口**：タイトルバーのビュー・スイッチャー（「ファイル一覧」）、コマンドパレット、コマンド
`pane.files`（既定キーは割り当てない——ツリーと役割が違うだけで毎回使う起点ではないため、欲しい人が
設定画面で付ける）、ツリーの右クリック「ファイル一覧で表示」。

#### 26.10.1 カラム（1／2／4）と、外の場所（2026-08-13）

**ペインは容れ物、中身はカラム**。`FilesPaneViewModel` は `FilesColumnViewModel` を**常に4つ**持ち、
ヘッダーのセグメント（1／2／4）で先頭から必要数だけ見せる。2カラムは左右、4カラムは 2×2。
カラムは現在地・履歴・並べ替え・絞り込み・選択を**それぞれ独立に**持つ——2枚並べる目的が
「左から右へ移す」なので、状態を共有させたら意味がない。

- **実体（VM／View）は作り直さない**。VM はイベントの購読を起動時1回で済ませるため、View は
  スクロール・選択・行の実体化を捨てないため。
- **増やしたカラムは「まだ出ていない場所」を開く**（`OpenUnshownPlace`）。同じフォルダーが2枚並ぶのでは
  並べた意味がない。優先順は「場所」ポップアップと同じ近い順で、**①ワークスペースに登録した
  フォルダー（マルチルート）→ ②ピン留め → ③基準カラムの直下 → ④基準と同じ場所**。
  2/4カラムを開く動機はたいてい「登録したフォルダーを並べて見る」なので、そこが先頭。
- **見えていないカラムの現在地は覚えない**（保存もしない）。隠れている間の状態を持ち回すと、
  増やしたときにどこが出るかが履歴で決まって読めなくなる——出すたびに今の「場所」から選び直す。
- **操作対象のカラム**（`ActiveColumn`・枠がアクセント色）はクリックとフォーカスで移り、隠れたカラムが
  対象のままにならない（キーの行き先が見えない場所になる）。ツリーの「ファイル一覧で表示」もここへ届く。
- カラム間のドラッグは**移動**が既定（`_internalDrag` は View インスタンスではなく型で持つ——
  掴んだカラムと落としたカラムが別インスタンスなので、インスタンス変数だと外部ドロップ扱いになる）。

**ワークスペースの外も、中と同じように扱える。** 現在地の制限（`Contains`）を外し、実在する
フォルダーならどこでも開けて、そこで作成・名前変更・削除・貼り付けもできる。
**ワークスペース配下への限定は「エージェントの手綱」（§10 のパストラバーサル防止）であって、
人間のファイラに被せるものではない**——`FolderTreeCommandHandler.Unconfined` を使い、
`ResolvePath` を通さない（AI の `write_file`／`edit_file` は従来どおり通るので、エージェント側の
防御は変わらない）。ツリーはワークスペースしか映さないので既定の限定つきのままにしてある。
パンくずは、ワークスペース配下なら所属フォルダー名が起点、外ならドライブから並ぶ。
ピン留めだけはワークスペースの持ち物として保存されるので外では留められない（外はクイックアクセスで辿る）。

**場所（📁）**＝ツールバー左の1つだけのボタン。ワークスペースフォルダー／**ピン留め**／
**Windows のクイックアクセス**／ドライブを、近いものから順に出す。クイックアクセスの実体は
Jump List のバイナリなので、`Shell.Application` COM のシェル名前空間
（`shell:::{679F85CB-…}`）越しに読む（`WindowsFilePlacesProvider`・失敗したらその節だけ諦める・
30秒キャッシュ）。

**ピン留めはツリーと共有する。** 持ち主は `FolderTreeViewModel`（ピンを `workspaces.json` へ
永続化しているのはこちら）で、ペインは `IFolderPinStore` 越しに**同じインスタンス**を見る
（DI で具象＋interface の二重登録）。持ち主を2つにすると「片方で留めたのに、もう片方には出ない」が
必ず起きる——LSP サーバー表を1つに寄せたのと同じ理由。ピンは**ワークスペースの持ち物**なので、
外のフォルダーは留められない（外はクイックアクセスで辿る）。

**ツールバーに置かないもの**：「上へ」「絞り込み欄」。上へはパンくず（親を押す）と Backspace、
絞り込みは一覧で **`/`** を押すと下端にバーが出る（エディタの検索と同じ入り方。Esc で解除、Enter で
一覧へ戻る）。「更新」と「隠しファイル表示／非表示」はペイン共通ヘッダー右端のボタンに置き、更新は F5
からも実行できる。狭いカラムで最初に潰れるのはパンくず＝「今どこにいるか」なので、常設の入力欄でそこを
食わない。
**絞り込みが効いている間はバーを開いたままにする**——閉じると、虫食いの一覧を見て「ファイルが
消えた」と読み違える（件数は下のステータスにも「N 件を非表示」と出る）。

パンくずの各フォルダー項目を選ぶと、VS Code 型の階層ピッカーを開く。そのフォルダー直下の
フォルダーをルートに表示し、子フォルダーは展開矢印から辿れる。次のパンくずに対応する項目は
選択状態で示すので、パンくずが横幅に収まらない場合でも現在位置の周辺へ直接移動できる。

**まだ無い**：他ペインへの D&D 受け渡し、git 状態の色付け、クイックアクセスへのピン留め（Windows 側）。
