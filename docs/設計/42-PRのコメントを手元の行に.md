# §42 PR のコメントを手元の行に（レビューと手元のコードを1手でつなぐ）

> 作成日: 2026-11-03 / 状態: **第1段実装済み**（Azure DevOps）。Editor の注記の印（`SetNoteMarkers`）は Editor パッケージの
> 改修で、公開とピンの更新を待って main に入る。続き＝GitHub の PR、印の吹き出しの中での返信の下書き（書き込みはしない）。
> 関連する正本: Azure DevOps の PR を読む部品・読むだけの決まりは §24.27.1、全リポジトリのカタログは §40、ワークツリーは §24 の
> ワークツリーの節、ブラウザの右クリックは §24.3。

## §42.1 なぜエディタか（ブラウザサポートから移った理由）

ブラウザサポート（§41）を「ページを拡張する」方向で作り直そうとして調べた（2026-11-03）。定番の拡張機能・IDE 連携で価値が
あるのは一覧を並べるものではなく、**ページとローカルの間を1手で飛ぶ**もの（行番号の「IDE で開く」・LocatorJS・Sentry の
スタックトレース → コード）。そして Azure DevOps では、Visual Studio 2022 17.10 が利用者の要望で「PR のコメントを手元のファイルの
中で見て対応する」を入れている。嬉しいことの大半は**手元のコードを書いている場所に PR の情報が来る**ことで、ブラウザの脇の面に
置く理由は弱い。ページが本当に要るのは「ページのコメント → 手元」の1手だけで、それもペインではなく右クリックの1項目で足りる。

## §42.2 エディタに出す（`PullRequestCommentController`）

- **どの PR か**：開いたファイルが属する**ワークツリーのブランチ**の、進行中の PR。`feature/x` のワークツリーのファイルには
  `feature/x` の PR、`pr/123` のワークツリーには PR 123、main の本体には何も出ない。同じリポジトリのワークツリーを並べても
  取り違えない。ワークツリーとブランチは git を起こさず `.git`（ワークツリーではファイル `gitdir: …`）と `HEAD` を読む
  （`GitWorkTreeHeads`）。PR はそのワークツリーのリモート（`AzureDevOpsRemote`：HTTPS・SSH・visualstudio.com・/tfs/）から
  `pullrequests?searchCriteria.sourceRefName=refs/heads/<ブランチ>&status=active` で引く（GET のみ）。3 分は覚えておく。
- **行**：スレッドの行は PR の版（`lastMergeSourceCommit`）の行。手元が進んでいたり編集中だったりするとずれるので、PR の版の
  その行の中身を、手元で前後の行も含めて一番よく合う所に探す（`ReviewLineAnchor`。±400 行・`}` のような行は前後で見分ける）。
  見つからなければ行番号のまま付け、吹き出しに「ずれているかもしれない」と添える。PR の版は `git show <版>:<パス>`（手元に
  無ければ行番号のまま）。編集したら手が止まって 1 秒後に付け直す——打鍵ごとに本文を写さない（§31.15）。
- **見た目**（Editor の注記の印）：テストの印の列の右隣に吹き出し。未解決は塗り、解決済みは淡い輪郭、同じ行に 2 つ以上なら数。
  そのファイルにスレッドが無ければ列ごと出さない（幅 0）。
- **乗ると**：スレッドごとに状態・誰が何と書いたか。**画像も出す**——Azure DevOps に貼った画像（`![…](…/attachments/…)`・
  `<img>`）は認証の要る URL なので、PR を読むのと同じ接続で取る。PAT を付けて取りに行くのは**組織の URL の下だけ**（コメントは
  人が書いたもので、よそのホストに PAT を送らない。`AzureDevOpsWorkItemClient.IsUnderOrganization`）。
- **押すと**：ブラウザのペインがページのそのスレッド（`…/pullrequest/N?_a=files&path=…&discussionId=…`）へ移る。返信・解決は
  人がページで行う——**読むだけ**（§24.27.1：共有の PAT で書き込む口は持たない）。

## §42.3 ページのコメントから手元を開く（ブラウザの右クリック）

Azure DevOps の PR のページでコメントを右クリック →「手元で開く — <ワークツリー>（<ブランチ>）の <ファイル>:<行>」。

- **どのスレッドか**：右クリックした要素から外側へ、各段の**表示文字だけ**を自前のスクリプトで読み（ページからの合図は受けない
  §41.2）、REST で読んだスレッドの本文と照らし合わせる（`ReviewThreadLocator`：Markdown の記号・リンク・画像と空白を落として
  比べる。内側の段で1つに決まればそれ、外側で2つ以上を含んだらそこで止める）。決まらなければ URL の `discussionId`。
  **ページの作り（DOM）には頼らない**——画面が作り変わってもコメントの文字は変わらない。答えのファイルと行はいつも REST から。
- **どこで開くか**：PR の元のブランチをチェックアウトしているワークツリー → Loomo がレビュー用に作った `pr/<番号>`
  （`ReviewWorktreeChooser`）。どちらも無ければ**黙って本体を開かず**、「手元の本体で開く（ブランチは main。PR の … ではない）」
  と書いた項目にする。手元にクローンが無ければ項目を出さない。
- **行**：§42.2 と同じく中身で合わせる。
- メニューは deferral で待たせるので 3 秒で打ち切る。PR の中身は 2 分覚えておき、PR のページを開いた時点で先に読んでおく。
