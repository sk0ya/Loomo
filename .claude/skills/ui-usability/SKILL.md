# ui-usability — 使う人の手順から作り、自分で確かめてから渡す

Loomo は人間の作業場（部屋）。機能が揃っていても、手順が分からない画面は使われない。
これまでの欠けはほぼ同じ形をしている（2026-11-16 の「自分のテーマ」は 1 日に 6 回作り直した）：

| 欠け | 原因 | このスキルのどこで止めるか |
|---|---|---|
| 「6 色」「基本」のように中身の分からない見出し・入口の置き場所のずれ | データの形（スキーマ）から画面を作った | §1 の手順の台本・§2 の用語 |
| 16 進が「#F8F9F/」と欠ける・説明が全部「…」・既定の白いボタン | 本文 16px で撮って見ていない | §3 の静的チェック・ハーネス |
| 自動保存・切り替え・元に戻すの流れの不具合 | テストと静止画だけで、本体を操作していない | §3 の本体での実操作 |
| 既存の個別設定を隠して「改悪」 | どちらにも読める指摘を自分で解釈した | §1 の「先に聞く」 |

**物差し**：NN/g の 10 ヒューリスティクス、Microsoft の Windows アプリの指針（設定・文章・キーボード）、
認知的ウォークスルー（新しく来た人が画面の手がかりだけで次の操作を見つけられるか）を、Loomo の約束に合わせて §2 にまとめた。

---

## 1. 作る前：手順の台本を書いて合意を取る

**新しい画面・ダイアログ・入口の置き場所の変更・既存の機能を消す／隠す／まとめる変更**では、コードを書く前に
次の台本を書いてユーザーに見せ、合意を取る（文言の手直しや、欠けを直すだけの変更なら要らない）。

```
■ 誰が・何をしにここへ来るか：（例：同梱のテーマに「ほんのり」足りない人が、エディタの配色だけ自分で作る）
■ 入口：どこから・何回押して着くか（例：外観パネルの「エディタのテーマ」欄の隣の「自分で作る…」→ 1 回）
■ 最初に目に入るもの：（開いた瞬間に分かるべきこと 1 つ）
■ 手順：1. …  2. …  3. …（押す・打つ単位。それぞれ「画面の何を手がかりに次へ進むか」も書く）
■ 終わり方：保存はどうなるか（その場で効く／自動保存／明示の保存）・取り消し・閉じ方（Esc）
■ うまくいかないとき：読めない・空・長すぎる・失敗したとき、何が見えて、どう戻るか
■ 揃える先：同じ種類の既存の画面（窓は SettingsWindow、ボタンは Controls.xaml のスタイル …）
■ 既存の分け方への疑い：今の設定・画面の分け方は、この手順に合っているか（ただし既存の機能は残す前提）
■ よその道具の解き方：似た道具 2〜3 個が同じことをどう見せているか（必要なら Web で調べる）
```

- 台本は 1 画面に収まる長さで書く。手順が 5 手を超える・説明しないと分からない段があるなら、作る前に作りを考え直す。
- **どちらにも読める指摘**（「〜に疑問はなかったのか」など）で、既存の機能を消す・隠す・まとめる方へ動く前に、
  AskUserQuestion でどちらの意味か確かめる。
- 下書きの当たりを見たいときは、緩い XAML（x:Class なし）を書いて `--xaml` でハーネスに描かせ、台本と一緒に見せてよい。

## 2. 作るときの決まり

### 言葉（NN/g #2「利用者の言葉」・Microsoft の文章の指針）
- 見出し・ラベルは**中身をそのまま**書く。×「6 色」「基本」「意味のある色」「画面の土台」→ ○「エラー・警告・成功とターミナルの色」。
- 内部の名前（enum 名・クラス名・§番号・設定の鍵）を画面に出さない。
- 見出しは短い名詞。ボタンは「何が起きるか」の動詞（「保存して〇〇に使う」より「〇〇に使う」）。ボタンの文字はできるだけ短く。
- 同じ物は画面をまたいで同じ語で呼ぶ（NN/g #4）。
- 説明はツールチップか、見出しの下の 1 行へ。全部を常に出さない（NN/g #8）。

### 状態と逃げ道（NN/g #1・#3・#5・#9）
- 処理中・保存した・失敗した、が画面で分かる。自動保存なら、保存されたことが目に入る。
- 設定は変えたらその場で効かせる（確認ボタンを要求しない：Microsoft の設定の指針）。
- Esc で閉じる・元に戻す・取り消せる。消す操作は、確認するか、取り消せるようにする。
- エラーは「何が起きたか・なぜか・どうすればよいか」を責めない言葉で書く。**黙って既定に落ちない**
  （読めないテーマが黙って既定の配色になっていた、などはエラーとして見せる）。
- 注意は該当する場所に出す。画面の下にまとめて積まない。

### 見せ方（NN/g #6・#8・Loomo の約束）
- 選択肢は見せる（覚えさせない）。色・設定は「どこに効くか」を見せる（例：タイルにカーソル→プレビューで囲む）。
- 高密度・予約幅なし・ツリーは既定で折りたたむ。更新でビューの状態（選択・スクロール・開閉）を壊さない。
- 〜Support 系の面は情報を並べず、同じ中身の見せ方を変える。
- 人のフォーカスを奪わない。Ctrl+T / Ctrl+W は部屋の動線なので取らない。

### 部品（Loomo の約束）
- ボタン・トグルには必ず Controls.xaml のスタイルを当てる（暗黙のスタイルが無いので、当て忘れると既定の白いボタンになる）。
  どれを使うかは `style-gallery` シーンで見比べる：主の操作 FlatButton／従の操作 SecondaryButton／アイコン IconButton（ToolTip 必須）／
  ペインヘッダー PaneHeaderToolButton・PaneHeaderGhostButton・PaneHeaderDangerButton／切り替え SegmentGroup＋SegmentToggle。
- 別窓は SettingsWindow（自前のタイトルバー）に載せる。Windows 既定のタイトルバーで部屋から浮かせない。
- 文字サイズは `{DynamicResource Fs*}`（生の数値を書かない）。文字の入る部品に固定の Width/Height を付けない（MinWidth・Auto）。
- 色はパレットの鍵（Bg / Panel / Fg / FgDim / Accent / AccentFg / Border / SelectionBg / Error / Success …）を DynamicResource で使う。

### キーボード（Microsoft のキーボードの指針）
- マウスで押せるものはキーボードでも操作できる。Tab の順番は見た目の順番と同じにする。Enter と Space で押せる。
- フォーカスが見える（再テンプレートでフォーカス枠を消さない）。
- 一覧・ツリーの中は矢印キーで動く。子の 1 つずつを Tab 止まりにしない。

## 3. 作ったら：渡す前に自分で確かめる

順番に全部やる。できなかった段は §4 の報告で「何を・なぜ見ていないか」をはっきり書く。

### a. 静的チェック（数秒）
```powershell
pwsh tools/ui/Test-XamlChanges.ps1            # 作業ツリーの変更（コミットの前）
pwsh tools/ui/Test-XamlChanges.ps1 -Base HEAD~1   # コミット済みの範囲
```
足した行に、生の FontSize・直書きの色・Style の無い Button・ToolTip の無い IconButton・文字の部品の固定幅が無いかを見る。
見本の中で「実物の px を写す」ための直書きのように、わざとのものは理由をコメントに書いて残してよい。

### b. 単体描画ハーネス（全テーマ×文字サイズで撮る・欠けを自動で拾う）
```powershell
dotnet build tools/ViewHarness -c Release      # 起動中の Loomo が Debug の出力を掴んでいても通るよう Release
dotnet run --project tools/ViewHarness -c Release --no-build -- --list
dotnet run --project tools/ViewHarness -c Release --no-build -- --scene <名前> --themes Dark,Light,HighContrast --font 16,20 --out <scratchpad>/vh
```
- 変えた View のシーンが無ければ `tools/ViewHarness/Scenes/` に足す（`IScene` を実装するだけ。例は `StyleGalleryScene`）。
  実物の View ＋実物の VM を使い、足りない依存だけスタブにする。**設定・テーマ等を %APPDATA% へ書かない**（一時フォルダーの SettingsStore 等を渡す）。
- `Steps` で状態を作って撮る：**空の状態・長い名前／長い値・エラー・選択中・ピッカーやメニューを開いた状態**。
  状態は VM のコマンドやプロパティで動かす（合成のマウスイベントは実機の検証にならない）。
- `findings.txt`（文字の欠け・枠に切られた文字・はみ出し・スタイル漏れ・名前の無いボタン・生の文字サイズ・3.0 未満のコントラスト）を 0 にするか、
  わざとのものは理由を説明する。
- **PNG は全部 Read で自分の目で見る**（`-marked.png` は指摘の場所を赤枠で囲んである）。自動で拾えるのは見た目の事故だけで、
  並びの悪さ・用語の悪さ・何をする画面か分からない、は目で見ないと分からない。
- 緩い XAML の下書きは `--xaml <file>`。

### c. 本体での実操作（手順の台本どおりに）
```powershell
dotnet build sk0ya.Loomo.sln                   # Loomo が bin を掴んでいたら sk0ya.Loomo.App を止めて建て直してよい
Import-Module ./tools/ui/LoomoUi.psm1 -Force
Get-LoomoWindow                                # 窓の一覧
Save-LoomoShot -Title '設定' -Path <scratchpad>/s01.png      # 撮る（前面化しない・画像の px がクリック座標）
Invoke-LoomoClick -Title '設定' -Name '自分で作る…'           # UIA の名前で探して実クリック（SendInput）
Invoke-LoomoClick -Title '設定' -X 420 -Y 310                 # 画像から読んだ座標で実クリック
Send-LoomoKeys -Title '設定' -Keys 'Tab Tab Enter'; Send-LoomoKeys -Title '設定' -Keys 'Esc'
```
- §1 の台本の手順を 1 手ずつ実際に操作し、各手のあとに撮って Read で見る。終わり方（保存・取り消し・Esc）と、うまくいかないときの道も通す。
- **キーボードだけでも 1 回通す**（Tab の順番・フォーカスが見えるか・Enter/Space/Esc）。
- 各手で認知的ウォークスルーの 4 つを問う：
  1. 人はこの手でやりたいことを、そもそもやろうとするか
  2. 正しい操作がそこにあると気づけるか（見えているか）
  3. その操作が、やりたいことにつながると分かるか（ラベルが合っているか）
  4. 操作したあと、前に進んだと分かるか（状態が見えるか）
- **人が Loomo を使っている最中**（ユーザーがこの Claude Code を Loomo の端末で動かしているのが普通）は、クリックやキーを送る前に
  ひと声かけるか、ユーザーが離れているときにやる。撮るだけなら前面化しないので邪魔にならない。
  入力は前面が Loomo でなければ送らずに止まる（誤爆を防ぐ）。
- WebView2（ブラウザ・プレビュー・面）の中や素の ItemsControl の行は UIA に出ない。画像から座標を読んで押す。

## 4. 渡すとき：報告の型

コミットメッセージとチャットの報告に、次をこの形で書く。
「未確認」の一言で済ませず、見ていない所は**何を見てほしいか**まで書く。

```
確かめたこと：
- 静的チェック：指摘なし（または：〇〇は理由があって残した）
- ハーネス：<シーン> を Dark/Light/HighContrast × 16/20px、状態 <空・長い名前・エラー…> で撮って見た。指摘 0 件
- 本体：台本の手順 1〜N をマウスで、1〜N をキーボードだけで通した（撮った画像：…）
見ていないこと（見てほしいこと）：
- 〇〇は△△のため本体で動かせていない。□□を押して××になるかを見てほしい
```

迷ったら、使う人がこの画面に初めて来たつもりで §1 の台本を読み直す。
